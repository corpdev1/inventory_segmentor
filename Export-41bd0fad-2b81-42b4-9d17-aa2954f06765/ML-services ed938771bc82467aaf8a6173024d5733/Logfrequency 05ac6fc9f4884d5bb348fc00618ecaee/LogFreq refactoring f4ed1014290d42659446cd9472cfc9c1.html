  • One other design would have preprocessor writes partial sums directly into influxDB. logfreq-detector would retrieve aggregated data from influxDB (aggreg done on-the-fly).

    Design 2 using database to store history counts

  • Preprocess pods:
    • Group by [ component, window of size X, loglevel ] and compute Count
    • take delayed points case into account by using watermark
    • Add partition number to the result and send to influx
    • should output each partition’s latest processed ts with count
  • scheduler
    • get db’s real latest ts(decision by all partitions) for each component, this latest ts should be same latest ts output by preprocess pods
    • assure send component with sequential increasing ts to kafka, (ts ≤ db latest ts)
  • LF pod:
    • each time consume one kafka msg(ts, component), it query db to calculate stats(avg, std, etc) for this component for its loglevels
    • group by [ component, window_start_ts, loglevel] of last X hours to ts, compute stats of Count
    • since we query db history data to get stats, LF pod can be stateless service
    • for every min for each component, db query load is too much? if too much, we can cache some history stats in local memory, and retrieve recent data to calculate recent stats
    • different pod output should be written to some storage(ex: influxdb), then another service to get the ordered result for next service( necessary need ordered result)

cons:
