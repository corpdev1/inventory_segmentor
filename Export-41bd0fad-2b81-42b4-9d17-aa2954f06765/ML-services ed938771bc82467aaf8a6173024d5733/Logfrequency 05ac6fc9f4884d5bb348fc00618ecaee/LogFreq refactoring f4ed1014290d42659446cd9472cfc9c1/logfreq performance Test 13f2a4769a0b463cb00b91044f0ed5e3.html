Scaling strategy

if topic number increase to 400 topics each pods, (you can observe from scheduler or LF pods or influx), then need

  1. scale scheduler to 0 replica
  1. let current LF pods finish the rest points in LF_triggers,
  1. then remove measurement topic_partition in bucket logfreq ,
  1. then restart scheduler let it output to a new topic ex: LF_triggers_new with more kafka partitions,
  1. then also change LF deployment to take input from this new topic, use parition number for replicas number for this LF deployment

potenital cons for this scaling strategy is when incoming data has a surge number of new topics, then old topic LF_triggers has too many new topics, LF pods don’t have enough pod number resource to consume them or take very long time

green-blue support

  1. scale scheduler to 0 replica
  1. remove measurement topic_partition in bucket logfreq
  1. restart scheduler let it output to a new topic ex: LF_triggers_new with more kafka partitions

for LF side potential solutions:

potential solution1:

Keep old LF consume from old topic, and Deploy another LF with new name which consume from new topic

issues:

  1. we need to create a new flux yaml for this new LF, once old LF finish, we delete the old yaml ? which seems also make version control complicated for different cluster using kustomization.yaml
  1. if new LF generate output to same output topic, it impact the timestamp order for same component

potential solution2:

scale existing LF pods number to partition number = (old topic partition number + new topic partition number) or just new topic partition number

existing LF need to be restarted to take new topics into account, and existing pod can read old topic partition and also new topic partition, which increase burden for the pod, and cause same output timestamp order issue and confuse model for non-continuous timestamp

don’t think solution2 is a good choice

solution3

introduce topic_switch_timestamp, if old LF consume arrive at topic_switch_timestamp, it will automatic swtich to new topic, and in the new topic, schduler has generated timestamp starting from topic_switch_timestamp, then we scale up pods number

this solution can avoid the case when too many points in the old topic and old LF need long time to finish them

Decision: we choose solution3

In conclusion:

case1: if lag is small, do following:

  1. scale scheduler to 0 replica
  1. let current LF pods finish the rest points in LF_triggers,
  1. then remove measurement topic_partition in bucket logfreq ,
  1. then restart scheduler let it output to a new topic ex: LF_triggers_new with more kafka partitions,
  1. then also change LF deployment to take input from this new topic, use parition number for replicas number for this LF deployment

case2: if lag is big, and you don’t want to wait like case1, do following:

  1. Scale scheduler to 0 replicas
  1. Set topic_progress_check as true for LF flux config yaml, then LF will restart(or you restart it, make sure new config is taken by it) and it will update timestamp once for each consumed topic to measurement topic_process_ts, topic_progress_state, it will skip all topic with timestamp already updated, and quite quickly arrive at the end of input LF_triggers(you can use grafana to check if lag become 0)
  1. launch scheduler/delete_measurement.sh to delete topic_partition and topic_progress_state measurement
  1. Put new topic with more partitions(ex: LF_trigger1) to scheduler config yaml, let scheduler scale back to 1,then scheduler will generate timestamp bigger than the value in measurement topic_process_ts to new example topic LF_trigger1
  1. configure new topic and set topic_progress_check as false for LF yaml, restart
