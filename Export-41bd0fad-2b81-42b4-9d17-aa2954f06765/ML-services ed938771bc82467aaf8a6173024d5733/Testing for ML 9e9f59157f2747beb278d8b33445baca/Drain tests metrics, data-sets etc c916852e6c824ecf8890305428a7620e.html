Drain tests: metrics, data-sets etc

Found ideas about what metrics to use from these papers:

Tools and Benchmarks for Automated Log Parsing, Zhu et al, arxiv 2019

Self-Supervised Log Parsing, Nedelkoshi et al, arxiv 2020

Navigating the Data Lake with Datamaran: Automatically Extracting Structure from Log Datasets, Gao et al, arxiv 2018

The first paper cites the third paper. The third paper may involve human interaction, depending on how challenging the data-set is.

Later, “Logan: A Distributed Online Log Parser” was also referred.

Accuracy

  • Requires manually labelled data: This paper used 2K samples per data-set, across 16 data-sets.
  • Parsing accuracy: Check whether the event template is assigned to the correct ground truth template group. This is a strict criterion.
  • Edit distance based accuracy: Levenshtein distance is more forgiving than parsing accuracy. This looks like a more reasonable metric.
  • Splitting a bigger cluster into smaller parts is still ok. Merging clusters is more problematic. This is our practical observation.

Assessing clustering quality

  • Mutual information.

Edit distance based metric

The paper, Self-Supervised Log Parsing, Nedelkoski et al, arxiv 2020, uses the edit distance score to measure the dissimilarity between the parsed and the ground truth log templates.

The Logan paper has ideas that can help to improve Drain:

  • Masking is limited to URLs and numerical tokens like dates, timestamps and IP addresses. Also, they have a logic based on number of numeric and alphanumeric characters, which will mask numeric IDs. There is no masking regarding quoted text.
  • The matching tolerance defined in III.G and how it is used in III.D (to match with a new sequence) and III.F (to decide whether an existing template has to be updated or a new template has to be created) could be useful in reducing the creation of templates with more and more wild-card tokens in Drain. These nice properties have been noted in our earlier experiments, also, as noted here and the results on standard data-sets based on the above loss, show Logan to be performing comparably or better.

Robustness

  • Robustness across different types of logs.
    • Will work with a small set of labelled logs across different data-sets. For e.g., 2K logs per data-set for 16 data-sets.
  • Robustness on different volumes of logs.
    • Requires labelled data for all the data-set sizes that are tested. Volume based test for robustness used data-sets for which ground truth data was available for the entire data-set (HDFS, BGL and Android).
    • The links to the entire labelled data-sets are not yet found.
  • For some algorithms, parameters tuned on a small set of log samples cannot fit well to large volumes of log data.
