General flow

  1. Logs are being streamed to PacketAI from any supported source
  1. Client visits grok dashboard to check the current grok coverage of his infra and identifies next topics to provide groks for
  1. Client visits Grok Wizard page and prepares groks
  1. We automate the whole process by recommending groks from knowledge base shared across clients → grok preparation reduced to grok validation

Grok Wizard UI

Purpose: user can build / update (CRUD) groks

In order to do so he needs to do the following steps:

  1. Client selects the scope he wants to cover with groks by using filters
  1. Once a log source is selected:
    • The corresponding log data is gathered using filters on ES the same way we do it for log UI
    • Log clustering to group similar logs is performed
    • Clusters of logs are shown to the user along with recommended groks matching the cluster representative (one log example out of the group of similar logs)
  1. Groks are needed to be provided for each cluster. A grok debugger is available for in-place grok verification.
    • User is informed about required and reserved field names that are expected by log patterns: loglevel, content and status_code
    • A drop-down menu with matching groks is shown next to each log cluster in order to recommend groks to the user with respect to the following order:
      1. User-defined groks
      1. Default groks without GREEDYDATA groks
    • Groks, suggested to the user have metrics next to them to clearly indicate user how well the current grok fits the given log line
      • We need a metric that computes goodness-of-fit between a non-degenerate grok (aka: not a GREEDYDATA) and a set of lines (aka: a cluster). 100% score would mean all log lines are successfully parsed for the 3 key tokens (aka: loglevel, content and status_code). Less than 100% means some lines are not correctly parsed.
  1. User should validate groks by clicking on “Validate”
  1. Templates preview to allow the user to see the resulting log patterns: cache logs to have an instant preview
    • In case of no-match for some log line during the preview → collect failed logs, form a new cluster with “unmatched logs” and ask to provide groks
  1. Repeat steps 3-4 until reaching the desired quality of log patterns
  1. Client deploys groks
    1. A grok validation verification is performed before the actual deployment → warning is thrown explaining why the provided grok is not valid

Grok Dashboard

The dashboard provides with metrics to track grok health

Grok coverage API (consumed by Grok Dashboard)

R (Read) grok operations

  1. Grok coverage per cluster, namespace, component : returns the percentage of selected (filtered) log lines that have groks [with time window]
    1. Answers : out of 100 log lines received that match filters, which fraction has groks?
  1. Number of logs failed to be parsed : returns the percentage of logs that failed to be parsed [with time window]
    1. Answers : out of 100 log lines received for which groks are available, which fraction has failed grok parsing?
  1. Overall percentage of grok coverage with respect to incoming log rate [with time window]
    1. Answers : out of 100 log lines received, which fraction has groks?
  1. Overall percentage of per-component grok coverage with respect to incoming log rate [with time window]
    1. Answers : out of 100 components received, which fraction has groks?

Grok Dashboard UI

Ideally, 100% of a client log lines are parsed successfully by a logstash grok → we call this “100% grok coverage”

This UI aims at providing user:

  • An overview of the current status: how well are current logs covered?
  • Actionable insights: which components need attention, and for which reason (1/ no groks at all 2/ some failed grok parsing)

Grok dashboard key UI controls

The UI has the following controls:

  • It lets the user select a time window using a date picker (default time window: last 24h or last 1h)
  • It lets the user select using one of more filters: namespace, cluster, component (default filter: none)
  • It displays KPIs of covered / uncovered / failed lines (failed means “badly parsed”) using a UI visualization
  • It supports sorting by any of the data fields (to rank by components that groks in priority)
  • It supports displaying absolute or percentage values

Grok dashboard key data

  • It retrieves KPI raw values using the Grok Coverage API like:
    • an API response with log line counts for covered / failed / total → {”covered”:c, “failed”: f, “total”:N}
    • a similar API response when grouping results by components → {"compID1": {”covered”:c1, “failed”: f1, “total”:N1}, "compID2": {”covered”:c2, “failed”: f2, “total”:N2}, ...}
    • → note that we should always have covered + uncovered = total and that failed ≤ covered ≤ total
    • → note that it is possible to rely only on the aggregated API response to reconstruct N, f and c by summation.

Grok dashboard KPI visualization

Grok Wizard UI API

In order to provide the functionality we would need to introduce the corresponding APIs:

CRUD grok operations

Currently we have the following APIs

  • read_groks read groks with provided filters (AND filter logic)
  • update_groks update groks with provided filters using upsert
  • delete_groks delete groks with provided filters
  • validate_groks perform grok validation
  • cluster_groks perform log clustering to group similar logs together
  • template_groks returns the template preview with provided groks
  • read_groks_all read all groks with provided filters (OR filter logic)

Log clustering

The flow is the following:

  1. Fetch logs from source selecting with filters for the time range (now - lookup, now)
  1. Read deployed groks for given selection
  1. Perform log clustering
  1. For each cluster representative (log line example of the group of similar logs) generate a list of recommended groks that match the log line
  1. Return the resulting clusters along with matching groks

Templates preview

  • In case of log parsing failure with provided groks we need to collect failed logs, perform clustering and return them asking to provide with groks. Clustering is performed within failed log lines

Grok validation

Validate grok against log line. Currently the grok is valid if:

  • The grok is not an empty string
  • The grok contains the required field content
