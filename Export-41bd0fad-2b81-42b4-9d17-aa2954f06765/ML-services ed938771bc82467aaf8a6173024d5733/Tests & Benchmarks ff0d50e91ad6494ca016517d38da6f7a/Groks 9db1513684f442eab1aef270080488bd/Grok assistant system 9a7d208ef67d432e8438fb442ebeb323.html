Objective

The objective of this project is:

for any topic/component logs, try to generate all representative groks in an automatic way with minimum human manual annotation.

Basic idea and architecture:

step1: generate some representitive logs and allow user input groks for those reprentative logs

reason to do this:

without this step, system will miss match general case grok for some more complex case message

for example: if system firstly take one general grok like following for first message

%{IP:ip} %{greedydata:content}

then it maybe match second message(more complexity) like

55.3.244.1 GET /index.html contentstuff

and content would be `GET /index.html contentstuff` which is not good, because it should be

%{IP:ip} %{httpmethod:method} %{URL:link} %{greedydata:content}

%{IP:ip}: grok token

55.3.244.1 contentstuff

how to do this:

inspired by drain's first layer using number of token, here try to pick some representive logs with different token numbers, and allow user input grok for those logs. Now i use hierachical clustering to pick one representive log for each cluster (if token number difference is <3, i consider as same cluster)

point to improve:

need to measure if this is good, or there is better method

step2: use these seed groks as existing groks and its grok tokens for grok assistant system to scan all existing messages,

if message is matched with one existing grok, and extracted content don't contain grok token, system continue check next message,

if not, we generate some candidate grok and propose to user, and allow user input grok for this message

new input grok and its vocabulary will be added to system to enrich the vocabularys and grok list

some important points:

  1. step1 clustering to pick some representitive logs and evaluation ⇒ harry
  1. for one input message, need to pick one grok from existing grok list for it, now method(also method of logstash on production) is:

    match message with most complicated grok, then second complicated grok, etc

    until found one matched grok, then return, and here the complexity is based on number of vocabulary

    we need to evaluate if current method is good or not, if not try to figure out one better matching method:

    for example match the message with every existing grok, then pick the best based on some criteria

some rules when we create a new grok pattern

  1. please reserve variable `content` for content grok token
  1. While specifying grok patterns, mention both SYNTAX and SEMANTIC information, i.e., %{SYNTAX:SEMANTIC}. For e.g., %{GREEDYDATA} is not acceptable by the grok-bot, it should be %{GREEDYDATA:semantic_name}.
  1. Name standard entities in the following uniform manner. It will be useful when we later develop ML algorithms based on such entities.
    1. date-time data as logdatetime.
    1. log-level data as loglevel.
    1. content data as content.
    1. trace data as logtrace. For e.g.: nodereservations-service_reservations-service of Affluences. In the raw log, this part could be called trace or stack or traceback or detail.
  1. Group the formats that are similar but differs on some field using the option field of regexes. For example, this grok :%{SYSLOGTIMESTAMP:logdatetime} %{SYSLOGHOST:[system][hostname]} %{DATA:[system][program]}(?:\[%{POSINT:[system][pid]}\])?: %{GREEDYMULTILINE:content}" has pid as optional which is better than creating two groks, one with pid and one without pid
  1. You can get some insights from this page to build groks.
  1. Caution about the content starting with a " symbol. If by using %{GREEDYDATA:content} if the " symbols are also pulled into the content, then it is a problem for the Drain algorithm. The Drain algorithm categorizes logs of a given number of tokens according to the first token or the last token or no tokens. Our current tokenizer will make the first " as the first token of the content, which will make several different contents similar. Consider "%{GREEDYDATA:content}.

some points:

grok assistant system now is a system able to scan all messages of any topic, and interact with user(marwen) to input groks for first log message, then it can split the grok into grain grok into db as vocabulary.

then it will use existing grok patterns to match next messages, and also give the match result a

score(called specific pattern score), if failed match, it will use its vocabulary to propose grok candidates for user to choose. User can choose or modify or input a new grok, then the system can do add the new groks to existing groks, and also split it to grain groks to enrich vocabulary
