Improving the clustering part

@Hariprasad Kannan wrote:

The clustering part in the grok-bot can be improved, so that a more optimum number of representative raw logs can be presented to the user.

Right now, the clustering is based on the number of tokens, with agglomerative clustering (based on a threshold of 3). The tokenization is based on a separator and " based left/right delimiter.

Possible problems with this approach:

  • This can lead to the grouping of not similar logs together.
  • This can lead to similar logs not being grouped together because of difference in the variable part.
  • Raw logs with several tokens which in fact have general grok patterns (based on GREEDYDATA) can be shown very early by the grok-bot. Thus, more complex cases get missed. e.g., this can happen with raw logs that are only traces.

With masking, the following approaches could be taken:

First approach to try:

  • Use re.subn() to substitute a pattern in the raw log and also, to keep track of how many times it was substituted.
    • Note: There are strings for which substrings are first masked followed by the entire string being masked with another pattern. Thus, the present approach doesn't use re.subn(). Instead, the masks are counted in the final masked raw log.
  • Thus, each raw log can be represented by a vector (of size equal to the number of patterns) of number of times each pattern was found in the raw log.
  • We can first group raw logs based on this vector representation. We can follow this step with the existing clustering approach applied on each cluster, to better catch unique cases.

The final approach that was tried is as followed:

  • Apply masking and represent a raw log as a vector of counts for the following patterns: 'DATE', 'TIME', 'TIMESTAMP', 'EMAIL', 'QUOTEDTEXT', 'LEVEL'
    • QUOTEDTEXT is a custom masking function that deals with quoted text in a more global manner, which is suitable for finding grok related structure in the raw log.
  • Cluster raw logs according to this vector. Right now, only exact matches is considered.
  • Within each cluster, further apply current clustering approach (separator + delimiter based tokenization and agglomerative clustering based on number of tokens).

Further approach to try:

  • Further we can represent each log by a sequence: pattern_1, #other tokens, pattern_2, #other tokens, pattern_3, #other tokens, ...
  • Using this representation we can further group raw logs if they have matching patterns in the same order and only a limited variability in the number of other tokens between two consecutive patterns.

Other ideas to try:

  • Adapt the threshold in the agglomerative clustering according to the particular case.
  • The = symbol is a very reliable indicator of key-value pairs of information in the raw logs in many cases.
    • Possible issue: presence of nested = symbol in the message, trace etc.
  • Look at pairs of delimiters: "...", {...}, [...] etc.
    • Possible issue: Pairing the double quotes is tricky.
