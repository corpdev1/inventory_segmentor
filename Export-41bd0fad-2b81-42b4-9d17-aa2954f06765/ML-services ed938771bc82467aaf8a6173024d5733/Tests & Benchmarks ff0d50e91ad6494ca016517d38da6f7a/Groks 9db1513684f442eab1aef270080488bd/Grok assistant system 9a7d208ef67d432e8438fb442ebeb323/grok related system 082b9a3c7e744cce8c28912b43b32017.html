grok related system

This system is designed for following Business logic and usage:

  1. slack bot interaction with client
  1. internal checking and updating new groks for kubenete logstash production groks for different clients
  1. Internal user use grokbot to generate groks for failed parsed messages or new topic

Functional spec:

  1. ML grok service offer 2 apis:
    1. POST /parse/{message} : return grok or failure (Used by slackbot service)
    1. GET /get_groks/{client_infra}: return ordered grok list (Used by admin UI)
  1. Grokbot DB store different clients groks generated by grokbot, it has 2 reasons:
    1. current grokbot is based on ES ingest api
    1. grokbot2.0 enable new feature: use existing other client groks to help generate grok for new client topic, so it require sharing different client groks easily, so i choose to put them into same DB

Technical spec:

  1. grokbot DB, ML grok service, slackbot service are in EC2 machines of same VPC with limited access

Some alternative choice and question:

  1. Let logstash or admin UI directly connect to Grokbot DB ?

    pros: no need to update new groks from groks db to current mongodb, no grok data consistency issue between two DB

    cons: need to refactor in dev side to connect to this Grokbot DB

  1. put grokbot DB, ML grok service, slackbot service in staging kube instead of EC2 ? what is the pros and cons ? or it is not important, we just choose one standalone environment for now

    pros for EC2: EC2 instance kibana, ES data checking from remote is easier, no need to do new kube yaml, docker-compose.yml is ready now
