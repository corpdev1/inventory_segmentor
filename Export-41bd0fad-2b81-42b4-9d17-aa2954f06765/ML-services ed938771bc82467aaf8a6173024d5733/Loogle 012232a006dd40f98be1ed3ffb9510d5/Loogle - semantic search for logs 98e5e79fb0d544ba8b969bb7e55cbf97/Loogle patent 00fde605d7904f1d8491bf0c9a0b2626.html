Problem

Logs are important to keep track of complex systems. logs are necessary for troubleshooting complex systems when incidents happen. One of the most essential operations on logs is search. Today, most log management tools offer search features including text search and regex search. However, these types of search is times-taking and often does not result in complete retrieval of information. In addition, the fragmentation of the “data store” market led to a multitude of query languages, which makes it harder for teams to align on one tool and for individual practitioners to use multiple tools.

Loogle

Design

To solve this problem we designed Loogle as a natural language semantic search engine for logs, which allows engineers to search logs with english (or other languages) queries, similar to searching Google for example.

There are 2 types of queries

  • Search queries (stated as questions or just sentences), require translation of NLQ (Natural Language Query) to DSL (Domain Specific Language). Sometimes, these queries require summarisation of results too.

    For example, one may ask:

    • what IP address connects most to our service? → search
      • traditional: compose a ES query for example
      • gpt3 can translate NLQ to DSL
      • gpt3 can interpret the result in NL
    • what was the timestamp of the first connection of IPx to our app? → search
      • same as above
    • when did the abnormal latency start? → search
      • traditional: compose a ES queries with keywords
      • can replace “abnormal” by a keyword list like “error, warn, fatal” then compose a keyword search then display results in NL
    • what is going on with rabbitmq? → search, summarisation
      • filter-in logs of rabbitmq
      • summarise
  • Questions that involve reasoning over data

    Some questions cannot be answered by just syntactically querying the logs with SQL. You need reasoning over the log text to answer them. This would have been straightforward if it were easy to train the model directly on large amounts of logs. To solve this we need an algorithm that transforms a given semantic query into a sequence of queries in a way to avoid the need to train the model on a large volume of logs.

    How long has the kafka data node X in recovery mode? (note, there is no field data node in the index schema, so the question is purely content oriented) - NOTE: for the semantic parts, leverage templates to compress model input AND/OR accelerate the sql search by deviding sql search into:

    1. if query does not contain named entity → searching templates
    1. if query contains named entity → searching logs

    → search for log entries that contain “data node X”

    → determine which log entries refer to “recovery mode”, semantically

    → once you have the syntactic RESULT_1, you run the query again on it (syntactically or semantically)

    Examples

    • QUERY = which kafka data nodes are offline?

    → RESULT_1 = SQL search for ‘kafka’ OR ‘kafka node’ OR ‘kafka data node’ AND ‘offline’

    → RESULT_F = run QUERY on RESULT_1

    • QUERY = is kafka data node X in recovery mode?

    → RESULT_1 = SQL_search (‘kafka’ OR ‘kafka node’ OR ‘kafka data node’ AND ‘recovery’ AND X)

    → RESULT_F = run QUERY on RESULT_1

    • QUERY = for how long X has been in recovery mode?

    → RESULT_1 = SQL_search (‘recovery’ AND X)

    → RESULT_F = run QUERY on RESULT_1

    • is logstash ingesting data now?

    → RESULT_1 = SQL_search (’logstash’ OR ‘ingesting data’ OR ‘ingesting’, WHERE TIMESTAMP < NOW-5min)

    → RESULT_F = run QUERY on RESULT_1

    or

    → RESULT_1 = SQL_search (’logstash’ OR ‘ingesting data’ OR ‘ingesting’)

    → RESULT_F = run QUERY on RESULT_1

    • does logstash have issue to talk to ES?

    → RESULT_1 = SQL_search (’logstash’ AND ’ES’ OR ‘elasticsearch’ AND severity=’error’)

    → RESULT_F = run QUERY on RESULT_1

Obtaining RESULT_1

RESULT_1 is the result of a syntactic search over logs to limit the scope to only the log entries that refer the “QUERY scope elements”.

Architecture

Inference

  • logs of monitored components arrive to kafka, one topic per component
  • logs are stored in ES
  • if the query is context-related, semantic search will translate the query to DSL, execute the DSL query and summarise the result
  • if the query is content-related, semantic search will translate the query to DSL, execute the DSL query to limit the scope, then summarise the result
  • or maybe there is no difference, in both cases, semantic search will translate the query to DSL, execute the DSL query,
    • if the result is < prompt_size then run the query purely semantically on the result
    • if the result is > prompt_size then just display the result

Fine-tuning

  • to translate the query to DSL, a model is fine-tuned on dataset of NLQ-DSL
  • to enhance the model for semantic search, a dataset of query-answer should be constructed and fed to model
