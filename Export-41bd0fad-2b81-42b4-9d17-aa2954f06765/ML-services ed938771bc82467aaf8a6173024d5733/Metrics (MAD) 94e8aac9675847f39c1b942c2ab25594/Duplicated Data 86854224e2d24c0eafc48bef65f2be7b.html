Docker metrics

27 July 2020

Problem: Sometimes we encounter a problem of missing/duplicated metrics while receiving data from John.

MAD logic: The current pipeline acts as following: it extracts the list of metric names to expect from the first received message and make a check each time it receives a new message if we've received everything as expected. In case of unexpected input the logic is following:

  • If we received more metrics than expected:
    • If there is no missing metrics: we ignore any new metric and output the message to minima
    • If there are missing metrics: we skip the message and do not output a message to minima
  • If we received less metrics than expected: we skip the message without outputting to the minima
  • If we received exactly the same number of expected metrics, but we miss some expected metrics: we skip the message and do not output a message to minima
  • If we skip 10 messages in a row: we reset the metric set along with all the models

MAD solution: In order to tackle this issue, we propose the following solution:

  • If we received less metrics than expected, we duplicate the previous value for the missing metric and output the message to minima
  • If we received duplicates, we calculate and use the average value for duplicated metrics and output a message to minima
  • If we received new metrics 10 times in a row, we skip the message without outputting to the minima and we reset the metric set along with all the models

Other solutions:

In the future (while dealing with big infrastructure where new components are created/deleted), if we want to trim the metric set we could transfer all internal parameters used for mean, std etc calculation for further usage...

3 August 2020

After implementing the proposed logic we were still receiving unexpected metrics for the host metrics. We tried to decrease the tolerance to unexpected metrics from 10 to 2 in order to test and see if the list of metrics to expect will stabilise after some period of time.

After careful investigation, we found that the problem comes from the system metrics: the initial list of metrics to expect had grown from 91 metrics to more than 7000 metrics after one night. During the test we were receiving new metrics containing previously unseen subjects with veth in it (example veth307f280 veth462c87f veth58ff55d veth6deff3d veth8444aca veth95e24c5 vethac333c6 vethbf3616b vethd54a963 vethe723d06) every 5 messages. In common case the veth devices are virtual Ethernet devices: could be a Docker / vmware / vitrualbox interface to the network.

Later, @Luca Ruggieri made a note on the docker we bring up on ExMachina: one of those Docker was ElasticSearch which was never really coming up and always restarting. Every time the ElasticSearch container was restarted, a new virtual network was created and, on the ML side, we were noticing a lot of different veth network name in the system-raw topics.

This is caused from the VM not being high enough for ES. To fix it he suggested to run the following command:

  • sudo sysctl -w vm.max_map_count=262144

which is not permanent and if we restart the server it has to be used again.

Since this issue could happen easily in a client server on which we have no control, we decided to get rid of subjects by summing up the corresponding metrics along all the subjects.

10 August 2020

After investigation with entire team, we understood that the problem comes from daemon Docker component since the input message for this component includes not only daemon metrics, but also all container metrics. Since MAD metric names composed as subject|dataset|metric once a container restarted we will receive metrics with new subject hence we are experiencing the increase in metrics when it actually is not the case.

For example: if we had 3 containers and restarted 2 of them, MAD will be expecting metrics from 5 containers to come. As a result, we will never receive metrics with the old container ids. As a result, we can expect metric set increasing regularly which will cause problems as for model accuracy and increase of CPU usage.

As a solution, we decided to do the following:

  1. Remove container ids (subject) for container metrics
  1. Aggregate container metrics which are coming with Docker daemon metrics by taking the average values
