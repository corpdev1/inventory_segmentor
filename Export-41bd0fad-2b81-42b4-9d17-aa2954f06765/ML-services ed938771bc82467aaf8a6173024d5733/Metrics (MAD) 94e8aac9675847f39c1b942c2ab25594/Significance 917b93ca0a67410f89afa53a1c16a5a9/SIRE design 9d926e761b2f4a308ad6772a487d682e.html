@Valentin Lapparov wrote

Each metric point could be described by exactly 3 values after it is processed by MAD:

  • tit_iti​﻿ - timestamp
  • viv_ivi​﻿ - metric value
  • sis_isi​﻿ - anomaly score given by MAD

The goal of Significance of Anomaly Model is to update MAD anomaly scores regarding past anomalies . Currently, we are alerting client if MAD anomaly score if greater than some fixed threshold (usually 70%) but this score could (and should) be adapted regarding how "severe" the observed anomaly compared to what we've already experienced.

The decision of either to process the anomaly score for a point at time tit_iti​﻿ or not could be done by simply comparing MAD anomaly score sis_isi​﻿ with some fixed threshold (here we decide if a point is abnormal enough to take it into consideration by SIRE).

Next, we calculate the duration of anomaly and it's deviation from "normal". Based on these two values we calculate how "severe" this anomaly and update the anomaly score accordingly.

About duration: for each abnormal point we can calculate it's duration once we've fixed the timestamp where the anomaly started. For example, given 5 anomaly points happened at time T, T+10, T+20, T+30, T+40 we will have the following durations: 10, 20, 30, 40, 50.

In order to decide when an anomaly period ends we could introduce some rules like "an anomaly period ends after X minutes without any new abnormal point" etc.

Workflow

Currently we are calculating anomaly duration and deviation inside of MAD and in order to calculate the relevance score we need to have information about past anomalies for a given metric. In order to achieve it we need to organize a database index, where we will store all abnormal periods and related information for every metric and then we will fetch this data in separate microservice to calculate the relevance score.

The output dictionary of MAD contains duration_deviation field which looks like the following: 

{
	"metric_1":
		{
		    "deviation": float,
		    "duration": int,
		    "start": int,
		},
	"metric_2":
		{
		    "deviation": float,
		    "duration": int,
		    "start": int,
		},
	...
}
  1. We can extend its fields by adding infraID, agentID, componentID, metric_nameand send it to Kafka topic called relevance_score. The relevance score will be calculated in a separate micro-service called SIRE.
  1. Once a new message in relevance_score Kafka topic is received, SIRE is triggered. It parses the input message and extracts the metadata.
  1. It fetches data from ES index where all past abnormal periods for this particular metric are stored which is then used for significance score calculation.
  1. SIRE stores the input message in the ES index.
  1. Once the relevance score is calculated, it is sent to Kafka topic from where Minima alerting will be triggered. A user should probably have the ability to reduce or increase the alerting frequency by increasing or decreasing relevance score threshold from Minima. Hence, an appropriate functionality is needed from Minima.

Latest update (24.03.2021):

Final architecture looks as follows:

  1. The following information is sent from MAD to ES index called relevance_score. 
{
	"timestamp": int,
	"source": infraID-agentID-componentID,
	"metric_1":
		{
		    "deviation": float,
		    "duration": int,
		    "start": int,
		},
	"metric_2":
		{
		    "deviation": float,
		    "duration": int,
		    "start": int,
		},
	...
}

2. SIRE is triggered every X seconds. It pulls the latest documents from ES based on last treated timestamp and source. Next, SIRE fetches past historical data from ES index where all past abnormal periods for this particular metric are stored which is then used for significance score calculation.

3. SIRE stores the timestamp and source of last treated document (metadata).

4. Once the relevance score is calculated, it is sent to Kafka topic from where Minima alerting will be triggered. 

output = {
    "timestamp": timestamp,
    "infraID": infraID,
    "agentID": agentID,
    "componentID": componentID,
    "metric_name": metric,
    "relevance_score": score,
    "anomaly_start": anomaly_start,
    "anomaly_end": anomaly_end,
}
