Intro

As for @January 6, 2022 we have collected 59 feedbacks (currently we do not backup Mongo data, hence only feedbacks for the last 2 weeks are available) from November 25, 2021 5:50:00 PM till January 4, 2022 2:46:40 PM:

Not an anomaly                                     49
Warning (might generate a bigger issue)             4
Debug (would be useful for troubleshooting)         2
Info (good to know about)                           2
No business impact                                  1
Critical (it harms our infrastructure/business)     1

If feedback label is Not an anomaly or No business impact we call such feedback as negative. Otherwise it is called positive.

After mapping feedback comments into these two categories we have the following feedback distribution:

Negative: 50
Positive: 9

Data exploration

Feedback vs issue related features

Plotting averages over feedback given by the client we can see:

  • Issue duration is higher for Critical and Warning feedback, whereas it is absent for Debug, Info and No business impact. We also see, that duration might be misleading and should not be considered solely while determining if an issue was significant since this feature is also high for issues with Not an anomaly feedback
  • Issue duration, number of affected and correlated components as well as the number of anomalies is higher for Critical and Warning feedbacks
  • Debug, Info and No business impact look very similar that indicates us that No business impact should be probably suppressed since it is not very informative for ML purposes

Positive feedback vs issue related features

  • There is a slight difference between these two classes: values are higher for positive feedbacks

Positive feedback vs metric names

  • Most of FP are coming from docker#memory metrics → an additional work for noise suppression is required for these metrics

Positive feedback vs issue related features grouped by metric name

SIRE-region related data

Regarding sire regions related data no useful insights were found due to lacking data and a few positive data points.

The only valid metric for analysis is the resident set size indicates that smaller abnormal duration and deviation have more importance to the client. It seems to be contre-intuitif.

Note:

  • for categorical variables (like metric names) the notion of ≤ 0.5 means False, and ≥ 0.5 means True. For example, docker#diskio#summary#service_time > 0.5 means that the metric name is docker#diskio#summary#service_time
  • scaled_absolute_delta has to be calculated for each metric for the given component. Data for metric X from component Y and infrastructure Z could be extracted from ml.dbscan Mongo collection by the following query: 
{metric: X, 
$and: [{source:{$regex: Y}}, {source:{$regex: Z}}], 
absolute_delta: {$exists: true} }

Finally, the scaled_absolute_delta is defined as:

scaledΔ=Δ−min(D)max(D)−min(D)scaled \Delta = \frac{\Delta - min(D)}{max(D) - min(D)}scaledΔ=max(D)−min(D)Δ−min(D)​﻿ if min(D)≠max(D)min(D) \ne max(D)min(D)=max(D)﻿

0 if min(D)=max(D) and min(D) = 0min(D) = max(D) \text{ and min(D) = 0} min(D)=max(D) and min(D) = 0﻿

1 if min(D)=max(D) and min(D) > 0min(D) = max(D) \text{ and min(D) > 0}min(D)=max(D) and min(D) > 0﻿

Where DDD﻿ is an array of absolute_delta values for a given metric
