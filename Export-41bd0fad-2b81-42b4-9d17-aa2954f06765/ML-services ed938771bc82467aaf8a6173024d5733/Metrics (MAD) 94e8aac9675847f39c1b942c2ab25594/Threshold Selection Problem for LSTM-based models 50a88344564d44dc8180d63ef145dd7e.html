Threshold Selection Problem for LSTM-based models

@Valentin Lapparov wrote

In AIOps, while dealing with anomaly detection people usually use ML models trained on historical data and use them to predict the next state regarding data they have. Then, one should decide when the difference between the real observed value and one predicted by the model is significantly different to alert about an abnormal state.

While dealing with metrics, we cannot set a unique threshold for all metrics as far as they are measured in different units. Some metrics are measured in percentages, some in bytes etc..

So there is a necessity for an approach that would provide a possible threshold for different types of metrics regarding their historical data.

At PacketAI, we are currently tracking the following list of metrics (with the corresponding unit):

  1. system.cpu
    • system#cpu#total#pct : percent %
  1. system.diskio
    • system#diskio#iostat#read#per_sec#bytes : The number of Bytes read from the device per second
    • system#diskio#iostat#write#per_sec#bytes : The number of Bytes write from the device per second
  1. system.memory
    • system#memory#actual#used#pct : The percentage of actual used memory
    • system#memory#swap#used#pct : The percentage of used swap memory
  1. system.network
    • system#network#in#bytes : bytes
    • system#network#out#bytes : bytes
    • system#network#in#dropped : The number of incoming packets that were dropped
    • system#network#out#dropped : The number of outgoing packets that were dropped. This value is always 0 on Darwin and BSD because it is not reported by the operating system.
    • system#network#in#errors : The number of errors while receiving
    • system#network#out#errors : The number of errors while sending
    • system#network#in#packets : packets in (bytes)
    • system#network#out#packets : packets out (bytes)

Possible thresholds metric by metric

  • For such metrics as cpu and memory that represent a number in percentage we could think about 15%-25% being a good threshold, but keeping in mind that cpu is given by 100% x Cores
  • For diskio which is in bytes per second and memory in bytes it is not obvious to establish a unique threshold.
  • We also have some dimensionless metrics (system#network#in#dropped, system#network#in#errors, system#network#in#packets etc) and for them, we need to know some additional information about what is a "good number" of errors, dropped and packets. This could be some fixed number or depending on the historical data.

Concept shift problem

There is also a problem of concept shift: if a client changes the infrastructure, LSTM models will not adapt to it. In this case, we need to retrain the model and provide with new threshold. It seems to be very hard to automate keeping in mind that we will need to collect new data and train on it which requires a lot of time (estimated amount of data would be at least 3 months in the beginning).

Conclusion

It doesn’t seem to be obvious to set up a good threshold for all possible cases as far as it depends on a particular infrastructure and data used for training. One of the possible solutions could be metrics normalization: if we have all values in percentages we could have established a threshold being within the range between 15% and 25%, but after making research for common solutions and talking with @Valentin Manes and @Marwen Sallem a task of metric normalization appears to be non-obvious.

Another possible solution could be giving users the possibility to change the threshold by themselves. It will simplify our lives as developers but could have harmful consequences on the product as far as they could set the thresholds being too high and miss an important alert.

The other very important point against the usage of the LSTM-based models applied metric by metric is that this approach doesn't take into account the overall picture and couldn't reflect the system's overall state. It is very unlikely that trouble on one metric will not be reflected by the others. It is preferable to have a model that takes into account all metrics at the same time and not one-by-one.

Lastly, and the most important, is the inability of the LSTM-models to overcome "concept shift" cases. If a user changes something in the infrastructure which would change metrics scale (which is likely possible) we will need to retrain our models and to set up new thresholds. It seems to be very hard to automate (we need to know when concept shift happens) and it will produce a lot of false positives (and/or false negatives, which is worst).

Possible solution

Calculate a z-score of prediction errors. This will allow us to compute the anomaly score regardless metrics units.
