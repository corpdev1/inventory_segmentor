Activation

  1. The activator service discovers component/topic to monitor and sends an activation message to Kafka topic metric-activator containing metadata specified here
  1. MAD argo sensor (argo events) reads from topic metric-activator and launches a MAD statefulset (one statefulset per data source)
  1. Detection starts within each pod

Detection process

For all terms please refer to the ML reference book

The following sequence of events is happening inside each MAD pod

  1. Initiate KafkaIO to listen from the Kafka topic from a specific data source (Kafka topic pattern: {infra}-{agent}-metric-{component}-stashed)
  1. MAD detector is loaded
    1. We first try to load the detector stored on s3 (path pattern: {S3 bucket name}/detector_state/{topic name}/stored_state.pickle): we restore the detector state and update class attributes (using __setstate__ and update_attribute)
    1. We initiate a new detector in case no detector state is stored on s3
  1. Store current MAD deployment information in MongoDB ml.mad_deployments collection. Data format
  1. We initiate the metric aggregator
  1. For each message in Kafka stashed topic:
    1. Evaluate stashed message against the validation schema
    1. Skip “old data points”: we keep track of the latest processed message timestamp and skip the message if the current message timestamp is less than the last processed
    1. In the case of “first point after start”- adjust the time between anomaly (used in SIRE-R - the noise-reduction technique)
    1. Aggregate metrics using the metric aggregator
    1. Detect anomalies:
      1. Compose the model input by iterating through the list of expected metric names
        1. Case: the list of expected metrics is empty (new deployment or restart)
          1. Compose the list of metrics to expect
          1. Compose the optimal weights
          1. Initiate metric transformer: we might apply a diff operator to the metric time series
          1. Initiate detector’s models: Skyline and Walter
          1. Update metric values
          1. Transform metrics using the metric transformer
        1. Case: the list of expected metrics is not empty
          1. Check the list of incoming metric names is as expected: we use the absorbing strategy while handling the unexpected metrics, i.e. we append new observed metrics to the existing list of expected metrics. In case of missing metrics, we remove them after self.missing_metric_wait_time seconds of no-showing up
          1. Update metric values
      1. Check if we need to restore Skyline stream array
      1. Check missing metrics and handle them in case if present
      1. Check metric delay
      1. Calculate anomaly scores: we apply an ensemble of detection algorithms. Each of the algorithms expects an n x k input array (where n- is the number of observed points limited to the self.max_possible_data_points data points and k- is the number of unique metrics). We are using Skyline and Walter models in production. See details about the models here.
      1. Adjust the weighted anomaly score in case we skip some detector outputs while calculating it
      1. Add missing metrics in the discount index dictionary used for adaptation
      1. In case of a detected anomaly:
        1. Calculate mean deviation, anomaly duration, and time-between anomalies (used for the adaptation to the new behavior)
        1. Update metric age
        1. Replace the last value in the metric data cache by discounted one
      1. Calculate the absolute delta
      1. Send DBSCAN data to ml.dbscan MongoDB collection (used for noise-reduction later on). Data format
      1. Calculate SIRE-p significance score
      1. Calculate DBSCAN significance score
      1. Get warmup status per metric: for each metric verify if we have collected enough data to start sending detection results (warmup period is finished). The warmup_period detector class attribute is the time (in seconds) of warmup. Usually set to 30000
      1. Compose final prediction based on SIRE-p, DBSCAN significance scores and metric warmup status. Currently, the point is abnormal if the anomaly is significant according to sire-p and dbscan and the warmup period is over.
      1. Compose output document with detection results and other metadata.
      1. If the warmup period is over and SIRE-R is enabled → send SIRE data to elasticsearch index
      1. Update model’s and data cache
    1. Treat the output:
      1. Compose the MAD output message following this structure
      1. Send all results to mlmetric Kafka topic ({infra}-{agent}-mlmetric-{component})
      1. Send messages containing anomalies to mlanomalies Kafka topic ({infra}-mlanomalies)
      1. Save MAD output to S3 and locally (if set to True)
    1. Commit Kafka offset
    1. Save detector state to S3

Deactivation

  1. The activator service discovers component/topic is inactive and sends a deactivation message to Kafka topic metric-activator containing metadata specified here
  1. MAD argo sensor (argo events) reads from topic metric-activator and deletes the corresponding MAD statefulset.
