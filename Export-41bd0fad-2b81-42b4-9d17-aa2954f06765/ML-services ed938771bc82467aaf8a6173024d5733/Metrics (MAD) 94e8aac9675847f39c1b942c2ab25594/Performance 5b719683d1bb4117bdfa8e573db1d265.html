Skyler

Detection time was assessed by generating random values from [0, 100) and applying Skyler to detect anomalies. Each test was performed on MacBook Pro (15-inch, 2019), 2,3 GHz 8-Core Intel Core i9, 16 GB 2400 MHz DDR4

1) Test: detection time for fixed window and variable input size

The window parameter for each model was set to 200. We made 210 iterations, where on each iteration a vector of size (1, n_features) was generated, appended to the list of metrics and evaluated for being an anomaly or not. Finally, after 200 iterations we end up with a matrix of size (200, n_features) which we then use to detect anomalies for a new vector of metrics.

Performance:

(here the number of features is equal to the number of metrics taken into the consideration)

2) Test: detection time for fixed input size and variable window

n_features was set to 100. The window parameter ranged from 10 to 2500 (possible values were:[10, 25, 50, 100, 200, 300, 500, 1000, 2500]). We made k + 10 iterations (where k was in range [10, 25, 50, 100, 200, 300, 500, 1000, 2500]), where on each iteration a vector of size (1, n_features) was generated, appended to the list of metrics and evaluated for being an anomaly or not. Finally, after window-size number of iterations we end up with a matrix of size (window, 100) which we then use to detect anomalies for a new vector of metrics.

Conclusion

Based on the test, we will use compute optimised EC2 instance for MAD and we should design a smart topic dispatcher at the client activator-detection.py

Finally, supposing we use machine with 4 cpu, 8G, then each machine can hold and process as much as 6 big topics (metric number > 600) the same time

Other factors: topic message frequency, more topic with less metric number

According to metric number and frequency and number of topic on one machine, we've designed load formule here:

Dispatch formula

Version 1:

Each Topic’s Load = Metric_number/600 * Frequency for 22.5K points in the future

(frequency can be defined like 1/message_inteval)

One CPU4 compute optimised EC2 max load = 6 * 1000/600 * 1/3 * 6/4=5

One CPU4 compute optimised EC2 current load = sum(topic_load) * num_topic/num_core

simulation:

for 4 topics(50,100,150,200,250,300) on CPU4 compute,total 24 topic, total load is 7/3*24/num_core > 5 which corresponds to our observation through pressure test where the detection arrive at 24 s for number of big topic

extension: for CPU8 compute optimised EC2 max load = 10

other idea:

  1. system can give alerting based on feedback when detection time > 10s, then the topic dispatcher will give the new topic to other idle node
  1. design a shuffle system to move topic's disk model to another node if current node is busy

Dispatch solution choice

  1. in house solution
  1. fargate (didn't find how to configure an auto group for it)
  1. use aws auto group
    1. use customized cpu utilisation as target
    1. disadvantage:
      1. example case: when we have 10 new topic and pass them to slave node, in the beginning the cpu utilisation is quite few because the models need to process 1 points, so according to the auto group's rule, all the 10 new topic can be in the slave node, but as the points accumulate to 22.5k window size, the 10 topic's load crush the node
