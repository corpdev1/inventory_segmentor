@Valentin Lapparov wrote (12/02/2021):

Here we describe the first version of seasonal metrics anomaly detection module (SAM)

Detailed description:

  1. Ideally we need to introduce a time series database which can aggregate values over specified time periods. This TS database should contain essential information about metrics which will allow to determine the source of data (from which component it came from: infraID, agentID, componentID), the timestamp, aggregation time period, and metric name. @dengke li is investigating either we could use Elastic Search for that purpose, otherwise we need to use some other database.
  1. SAM fetches data from TS database and extracts list of metrics to process as well as aggregation periods for each metric. Ideally a TS database should be able to aggregate data over specified period of time and return ready-to-use dataset.
  1. Anomaly detection happens here. For each metric indicated in the list of metrics to process we will perform an anomaly detection and send results as far as they are ready. We could think about different approaches to detect anomaly on seasonal data. One of the easiest ways would be to use Prophet package with specified period of seasonality since it provides not only with predicted values but also with lower and upper bound which is very intuitive for the user. Other possibilities for anomaly detection would be using the following approach(es): de-trend data with STL or SARIMA models (eliminate estimations of trend and seasonal components from initial data points) and perform anomaly detection on residuals with MAD algorithms. This approach requires more time to implement however it will lead to very fast calculations (which we don't necessary need since the period of aggregation is supposed to be big enough) in case if we will face an important number of metrics to process (hundreds of thousands).
  1. ML output is then sent to kafka topic of the following format: infraId-agentId-mlmetric-componentId-seasonal
  1. The results of anomaly detection algorithms for seasonal metrics should be plotted in a separate tab on Minima (according to @Marin Radman). In case we use Prophet, it could represent something like on the chart below, where we plot actual metric values aggregated over specified time region (black dots), a normal region (green area) and anomalies (red points).

In case we are using MAD for anomaly detection, we will be plotting usual charts with anomaly score and metric value.
