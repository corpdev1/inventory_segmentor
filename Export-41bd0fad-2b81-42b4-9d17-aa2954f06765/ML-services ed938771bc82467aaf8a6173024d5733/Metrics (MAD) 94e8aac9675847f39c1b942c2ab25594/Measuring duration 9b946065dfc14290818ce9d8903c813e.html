Measuring duration

@Hariprasad Kannan wrote:

Why is measuring the duration important?

  • Assign score in a better manner to anomalies which are short but greater than 1 unit.
    • Maintain the anomaly score better during the anomaly.
    • Handle the situation where a return to normal is seen as an anomaly.
  • Recognize long anomalies and ask the user whether it is a long anomaly or a concept shift.

Here is an approach that could be used for measuring the duration of an anomaly, which uses the output of MAD and which doesn't use any additional parameters to tune. It is an extension of MAD.

When an anomaly is detected, the MAD model should be frozen till a non-anomalous point is again discovered. The data collected during this anomalous period could be used at the end of the anomalous period to adapt the model.

In order to implement this approach we should take care of the current manner in which MAD is implemented:

  • Streaming setting.
  • Vector execution in Python.

Here we will see how to implement this approach while accommodating these settings.

To freeze Skyline:

  • Freezing the detector and maintaining the vector operation is possible with minimal computational cost.
  • We can maintain a set of recent normal behavior values for all metrics. For metrics with anomaly, we can impute normal behavior and pass that value for streaming calculation of statistical moments like mean and variance, when the detector is frozen during the occurrence of anomaly.
  • We will also keep track of the actual values happening during this time. We will use them to adapt the model once the anomaly is over.

    How to do this in a streaming setting, when a vector of values has to be passed to MAD?

    To answer this question, we have to see how MAD processes the input vector. The vector size is equal to the number of metrics, with a value for each metric.

    MAD processes the vector at two places:

    1. For making the prediction.

    2. For updating the statistical moments like mean and variance.

    Right now, the same vector is used for both computations. Instead, if we supply the correct vector for each of these computations, we can still freeze the model and adapt it later, when the anomaly is over. To do this we will maintain three vectors.

    Generally, to update the mean in a streaming setting, we can take the following approach. The following approach can be extended for higher order moments like variance.

    Suppose, μm\mu_mμm​﻿ is the mean of mmm﻿ samples seen so far and suppose, we have nnn﻿ anomalous samples of mean ηn\eta_nηn​﻿.

    We will supply three vector:

    1. A vector to the module for detection, which will have the actual values, in order to get the anomaly score. Whether an anomaly is happening or not this vector will have the actual values.
    1. A vector, ψn\psi_nψn​﻿, to the module for computing statistical quantities, which can take three different types of values.
      1. During an anomaly for a metric it will have normal values imputed in the metric which has the anomaly.
      1. At the point of time when an anomaly ends, it will have the value ηn\eta_nηn​﻿, which is the mean of the anomalous value.
      1. During the rest of the normal behavior (including when an anomaly is detected), it will carry the actual value of the metric.
    1. A vector needs to be additionally supplied to the module computing statistical quantities. It is needed to properly perform the adaptation, when an anomaly ends for a metric. This metric will be zero most of the time, it will be non-zero only when an anomaly has ended for a metric and it will have the mean of the imputed normal behavior values that was supplied during the anomaly (we will call it νn\nu_nνn​﻿). This imputed normal behavior has to be removed from the statistical quantities, when the anomaly ends.

To freeze Walter:

There are two possibilities.

First way

  • Add and immediately delete vectors, once an anomaly starts.
  • Later we can insert all the points sequentially in one go.
  • This approach will incur computational cost. At the same time, according to the paper deleting an anomalous point is less expensive because its depth is lesser.

Second way

  • We can check whether the following points are duplicates or near duplicates of the first anomalous point. This will be computationally cheaper but we need to figure out how this check can be done. According to the paper they talk about a radius around the anomalous point.

  • Will it be good enough to aggregate over larger windows, say, 30 seconds, to compensate for increase in computational cost?

@Marwen Sallem wrote :

  • Are we making the assumption that an anomalous period is actually anomalous ? If we freeze the models, we might end up freezing it from adapting to a normal behaviour. For instance, imagine we have an application that uses an API from time to time (say once a day). This will stimulates the metrics related to network and will cause an anomaly regarding MAD, but it's a normal behaviour regarding the business case.
  • We measure the duration to know if an anomalous period is more severe. In my point of view, this should be done out of the box no matter is the output from MAD. If we think that MAD is adapting quickly, we can play with the adaptation coefficient and the threshold for a severe duration. This will make it easier to play with two parameters (or selecting them automatically using algorithms) rather than changing the way MAD is working.

Overall:

  • I think instead of freezing MAD we could try with a longer adaptation period, which theoretically converges to a frozen model if we will tend the adaptation period to infinity. The point of @Marwen Sallem is also very important since we are not adapting to new behaviour while MAD is frozen (which could be crucial in case of normal behaviour or a False Positive cases from MAD). Secondly, I still not convinced that we should rely on the user to inform us about the concept shift when in this case we will potentially be outputting anomalies for a long period of time which will lead to the storm of alerting messages and potential computationally expensive operations of insertions (while we were doing pressure tests with @dengke li, we observed that inserting 30 points in Walter is very expensive and takes time so if we will do the sequential inserts from time to time we will become late and will not be able to provide predictions in real-time)
  • You assumed that MAD processes the vector at two places (1. For making the prediction. and 2. For updating the statistical moments like mean and variance.) but in fact, if you look at the current implementation, we add an anomalous point to the dataset, update MAD model (= update streaming arrays and add this point to Walter tree) and then do the prediction (= we calculate mean, std etc from streaming arrays and compare it with mean, std of the tail of our dataset which contains the last point which could be anomalous) so we use a slightly different approach and it should be modified in order to implement this idea of the freezing MAD model
  • Also, I think that are inventing a wheel here: we could try to calculate the duration with our current means (which are already implemented) and see if it is sufficient for our needs.
