Product Objectives

  • detect log (sequence) anomalies in real time
  • point to the root cause of log anomalies in real time

Inputs

  • IT logs from potentially tens of different sources

Output

  • probability of a log (sequence) anomaly

(note, the output of the LSTM behind deeplog is either a probability of anomalous template or probability of anomalous template sequence)

Possible architectures

  1. Single task architecture: one Dlog model per log source

in this design, we deploy one Dlog model instance per log stream (i.e per IT component). Example:

Pros

  • Complete isolation of the pipeline of data, from source to deeplog output → easy troubleshooting
  • one-task learning → higher accuracy
  • Straightforward RCA
  • Fine-grained pipeline → extensible architecture. Eg, easy to add user control over what and what not to monitor using dlog.
  • Fine-grained pipeline → abstractable architecture. Eg, easy to build more abstract pipelines if needed in the future (eg, one dlog model per collection of data sources - all syslogs together for example)

Cons

  • expensive in compute resource. What's the size and cost of one Dlog instance?
  • requires system level scalability (i.e distribution)

2. Multi-task architecture: one Dlog model for all log sources

in this design, we deploy one dlog instance to process logs from all sources. Eg:

Pros

  • easy to build and maintain on a system level
  • multi-task learning → captures inter-dependancies
  • cheap in compute resource

Cons

  • requires separate encoding of templates to enable RCA (if anomaly, encoding indicates the source)
