Anomaly Detection in Log data

High level description

  • Log Parsing (Template Extraction)
    • Logging is a printf in the code to print it's state, for instance, printf("* bits are received", [128]) that print 128 bits are received on the console
    • The log, hence, contains a template (* bits are received) and a parameter list ([128])
    • Log Parsing (or Template Extraction) is the way of extracting the templates knowing only raw logs
    • Many algorithm exists in the literature. In this work we use mainly Drain
    • Drain output a list of Templates that we can use to map each logline

  • Types of Anomalies :
    • Outlier Log Line (OLL)
      • When we use Log Parser on the Training Phase we obtain a list of EventIds as described here
      • The OLL, in this case, is detected when the logline could not be mapped to one of the extracted templates
      • For example, the Log Parser outputted this list of templates at the Training Phase
      • Then the following loglines :
        • received 128 from 10.55.47.10 is considered as Normal because we can map it to the template received * from *
        • server 10.55.88.69 is shutting down is considered as Anomaly because we can not map it to none of the discovered templates
    • Abnormal Log Frequency ALF
      • Abnormal Log Frequency is simply detecting an abnormal number of loglines in a slot of time
      • For instance, let's consider the number of logs at a slot of time, normally the number should be in the range of blue interval as we have learned from history (cf. figure )
      • However, the actual number of loglines differs significantly from the predicted number (or normal number). At this point we raise an anomaly
    • Abnormal Event Sequence ALS
      • Abnormal Event Sequence is detected when a sequence of Loglines never happened before/doesn't make sense to happen
      • For example, if we consider this sentence : I will eat pizza every <>, where each word is a template
      • Historically, this sequence make sense when <> = Everyday, Every Week, Each Month, . So if we train a model on many sentences like this one, the model will predict a word that refers to TIME
      • However, if the truth is instead something we shouldn't expect (something from the predictions of the model), this is raised as Anomaly. For example, if <> happens to be a word like Dog, Cat or anything that make the sentence lose it's meaning
    • Abnormal Event Pattern
      • Abnormal Event Pattern is when there exists an unusual set of templates types (patterns) in the logs

We want to catch:

  • outlier log line anomaly
    • When we see train the model for the first, we shall use a Log Parser which in our
  • abnormal log frequency
  • abnormal event sequence (deeplog)
  • abnormal event pattern (logCluster)

Pipeline options

  1. log lines → Drain → log templates (events) → (flag outlier events based on number of occurrences) → (event, number of occurrences per time window) matrix → LSTM for anomaly detection
  1. log lines → Drain → log templates (events) → (flag outlier events based on number of occurrences) → (event, number of occurrences) matrix → distance based clustering for anomaly detection
  1. log lines → Drain → log templates (events) → (flag outlier events based on number of occurrences) → one event per time point → LSTM for anomaly detection (Deeplog)
  1. log lines → Drain → log templates (events) → (flag outlier events based on number of occurrences) → event sequence by time window → LSTM for anomaly detection
  1. log lines → word2vec or doc2vec → log vectors (events) → (flag outlier events based on a similarity distance) → event sequence by time window → LSTM for anomaly detection
  1. log lines → train Drain → structured logs → train Jessy → Jessy model for template inference (extraction) → LSTM for anomaly detection
  1. the logRobust pipeline (log lines → Drain → semantic embedding with fasttext → attention based biLSTM for supervised anomaly detection)

  1. Consider sequences of events. Sequences could be meaningless when system are parallel & multithreaded which causes a difference in the event time reception. This is a proove from LogCluster paper : Many tasks of an online service are multi-threading, which causes interleaving logs even for the same user request. This is because Furthermore, a typical online service system consists of many distributed servers. The logs generated by each server are later consolidated and stored at a HDFS-like central place. However, due to the clock drift problem, the timestamps of events produced by different servers may loss synchronization, causing many different permutations of events for the same execution sequence. Therefore, in our work we do not consider the permutations of a log sequence.
  1. Time window of sequences of events will not guarantee the same sequences each time. For instance, we could end up with E2,E1 / E4,E1 and E2/ E1,E4,E1. This will make the training blurry

Mike

Type: script

Purpose: Reduce the amount of templates outputted by Drain

Intro:

After exploring the output of Drain, which is a set of templates obtained from a file with raw logs, we observed that sometimes Drain creates two different templates for logs, which, in fact, come from the same template (the ground truth-one).

As an example you could think about the situation when the variable part of the log did not changed during the considered period of time.

Example:

If we have the following sequence of logs:

Teardown UDP connection A for B to C duration 12 bytes MA
Teardown UDP connection D for E to F duration 15 bytes WE
Teardown TCP connection A for B to C duration D bytes 1 MA DC
Teardown TCP connection D for E to F duration G bytes 2 FM RD

Drain will produce the following two different templates:

Teardown UDP connection <*> for <*> to <*> duration <*> bytes <*>
Teardown TCP connection <*> for <*> to <*> duration <*> bytes <*> <*> <*>

But in fact the ground truth template would be the following one (we replace 3 <*> at the end by one as far as this is a variable part):

Teardown <*> connection <*> for <*> to <*> duration <*> bytes <*>

Unfortunately, Drain cannot handle such cases and merge templates automatically. That's why we introduced Mike which will get rid of undesired witnesses templates.

How it works?

It looks for a cosine similarity between vector representations of templates and merges similar ones

  1. Mike transforms templates to vectors:
    1. He creates vocab - a dictionary of tokens from a corpus of templates and excludes ones which contain <*> in it if a token is not the first one in its template
    1. By using a CountVectorizer from sklearn we encode each template: CountVectorizer(vocabulary=vocab).fit_transform(templates)
  1. Looks for similar vectors with cosine_similarity function from sklearn and creates a group of templates to merge for vectors which are similar on more than 90%
  1. For each group of similar templates he creates a unique template:
    1. Mike initiates final template as an empty list [] at the beginning
    1. For each group of similar templates Mike compares tokens of every template position-wise:
      1. If tokens are all equal, he appends it to the final template
      1. If tokens are not equal, he appends a <*> to the final template
    1. He stops comparing tokens once he reaches the end of the shortest template of the group
  1. Using hashlib Mike obtains the EventId for each template in the set of final templates: hashlib.md5(final_template.encode("utf-8")).hexdigest()[0:8]
  1. Mike outputs a pandas.core.frame.DataFrame of final templates

Gale

Type: class

Purpose: Match raw log with its template

Intro:

Despite the fact that Drain manages to create templates for a set of logs it is not able to say for a new raw log, coming, let's say, from a stream, to which template it corresponds to. Also, the problems associated with the fact that Drain should initially store large files in the operating memory, cast doubt on the possibility of using it for template matching. In order to quickly determine which template best suits the new raw log, having a templates dictionary (Template : EventId) at our disposal, we created Gale.

How it works?

It looks for a cosine similarity between vector representation of preprocessed raw log and existing templates and assigns it an EventId of the most similar template

  1. Gale transforms stored templates to vectors:
    1. each template by CountVectorizer
    1. He uses CountVectorizer from sklearn to get vector representation along with a custom analyzer- a function which preprocesses a raw log with regex used in Drain for the particular log type and gets rid of a special token <*> 
    def log_analyzer(self, text):    
		text = logprocessing.process_with_regex(text, self.logfile.regex_list)    
		return [word for word in text.split(" ") if word != "<*>"]
  1. He transforms the new log to vector by using the same vectorizer used in step 1
  1. He computes the cosine similarity between the vector representation of the raw log and the vector representation of stored templates
  1. He assigns the new raw log with a template with highest cosine similarity if it's above 90%, otherwise we declare it as "novelty"
