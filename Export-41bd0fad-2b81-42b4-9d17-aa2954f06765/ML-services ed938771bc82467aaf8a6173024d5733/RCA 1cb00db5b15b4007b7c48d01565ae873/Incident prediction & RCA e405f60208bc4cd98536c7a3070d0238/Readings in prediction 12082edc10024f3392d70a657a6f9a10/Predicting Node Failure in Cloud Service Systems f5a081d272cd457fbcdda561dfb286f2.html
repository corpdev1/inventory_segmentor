Important take-aways for PacketAI

  • This is yet another paper that highlights the importance of working with features designed based on domain knowledge. This is very important despite taking a data driven approach. Also, it is good to figure out a sufficient set of features. In the case of PacketAI, features based on domain knowledge can be very important, when we need to jump start the system with limited data.
  • The paper uses features that describe how a node interacts with the adjacent nodes. In our case, we can make use of the dependency graph and get such features. We have seen such graph based modeling in the context of prediction in this paper, also.
  • Data imbalance is a common problem in IT incidents. The number of positive cases is much lesser than the number of negative ones.
    • When there is data imbalance, sampling based approaches like SMOTE may lead to many false positives (as observed by this paper). So this paper uses a ranking based formulation along with sampling to deal with data imbalance.
    • Careful choice and interpretation of algorithm performance metrics are needed when there is extreme data imbalance.
  • Ranking not only helps with imbalanced data. It also helps with the goal of particular application: when the nodes are ranked according to their proneness to failure, the ranking can be used for: 1. allocating a VM to a healthier node, 2. live migration of a VM from a sick to a healthier node.
  • They recommend training the model frequently. They do it daily. This is needed to adapt to the changes in the system - software updates, adding/removing nodes etc. They also state that having too much of historical data is not helpful.
  • This paper deals with node failure prediction in a cloud system. However, the ideas (temporal features, spatial features, ranking) are more general. Could we use it to predict failure of a particular technology?
  • Section 6 on related works list several papers through which we can better understand about various causes for failure in IT infrastructure. This will help us with data generation and also, to boot strap our algorithms with domain knowledge when enough data is not there.

The goal of the paper

The setting is a large scale cloud infrastructure. The goal is to predict failure of a node in such an infrastructure.

Details about machine learning

  • Considers both temporal features and "spatial" features.
  • These features lead to node failure. The relationship is complex and requires a data driven approach.
  • Handle each set of features separately.
    • Avoids feature conversion that could result in loss of information.
  • LSTM for temporal features.
  • Random forests for spatial features.
  • The approach that uses both works better than using just each of them.
    • Of the two they found spatial features to be more predictive of node failure.
  • Vector based intermediate representations of the LSTM and random forest classifiers, are used as inputs to the ranking algorithm.
  • They especially want to use features that are early indicators of failures. The features collected closer to the time of failure may not have predictive power. Thus they train with a horizon of six hours.

Regarding data imbalance

  • There is too much imbalance in the data (less than 0.1% nodes contain failures, i.e., ratio between failure to healthy is less than 1:1000).
  • Sampling based approaches like SMOTE did not give good enough results. Not good enough to handle severe data imbalance: many false positives after balancing.
  • Use all faulty nodes as positive samples. Sample from healthy nodes to have a 1:20 ratio.
  • Data imbalance has been encountered in software engineering faults, also. The paper points to references.

Ranking based formulation

  • Helps with data imbalance.
  • Gives an output (nodes ranked according to proneness to error) that is usable by this particular application.
  • Uses LambdaMART: Boosted tree version of learning to rank algorithm (refer Learning to Rank for Information Retrieval)
  • LambdaMART has been replaced by FastRank and the results are comparable. The approach is robust to what ranking algorithm is used.
  • The number of top nodes deemed as faulty is chosen based on cost sensitive criterion, where precision is valued more than recall.

About cross validation

  • In the context of online prediction, cross validation could lead to over optimistic results during development.
  • One reason could be because of limited data. When an incident happens on a large cloud system many nodes could fail at the same point in time. Some of these failures could become part of the training data and the system will perform very well on the nodes that are part of the validation set.
  • Online defect prediction for imbalanced data: Another reference discussing this point.

About validation metric

  • Comments on “Data Mining Static Code Attributes to Learn Defect Predictors” show that high true positive rate and low false false positive rate do not ensure high precision if the number of negative samples (in our case healthy nodes) are much more than positive cases (faulty nodes).
  • Also, refer Comments on ’Researcher Bias: The Use of Machine Learning in Software Defect Prediction’.
  • The paper uses Precision/Recall values and the ROC curve to validate the algorithms.
  • They also point to other metrics like cumulative lift chart (CLC) and fault-percentile-average (FPA). Refer A Learning-to-Rank approach to software defect prediction.

Comparison with other ML algorithms

  • Refer Automated Parameter Optimization of Classification Techniques for Defect Prediction Models about comparing different algorithms using default settings.

About features and causes of failure

  • Temporal features:
    • More specific to the particular node.
    • Performance counters, IO throughput, resouce usage, response delays, sensor data, OS events, log/alert data aggregated as time-series (log event counts, error/exception event counts, system event counts).
    • 137 in total.
  • Spatial features:
    • Models how the nodes implicitly/explicitly interact with each other.
    • deployment segment, update domain, shared router, rack location, resource family, load balance group, batch operation group, policy group, OS build group etc.
    • 82 in total.
  • Failure causes
    • Software and platform failures: software crashes, OS crashes, network outage, misconfigurations, memory leak, hardware breakdown, application bugs, disk failure, service exception, overheating, software incompatibility.
    • Also, Software update is a repeated cause of failure. We are seeing that at PacketAI also, when we update the agent.
    • According to domain experts in Microsoft, the number of root causes for node failure is over one hundred.
    • Refer section 6 (Related work) about references that discuss about failure causes.
