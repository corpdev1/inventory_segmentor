Important take-aways for PacketAI

  • Representing information from metrics, logs and traces in the form of alerts. Alerts are a more light weight representation of the information from metrics, logs and traces (other papers: AirAlert).
  • It looks like useful alerts can be created without too much effort. In the results section of the paper, most of the alerts (not all) are based on important KPIs like latency and system resources like CPU, memory and disk I/O. This means that if we could focus on these small set of signals, we could:
    • Analyse and present the output of MAD and LAD in terms of alerts.
    • reduce the number of signals presented to the user.
    • make faster progress on RCA and prediction.
  • Apart from the alerts mentioned above, the other alerts seem to be technology specific (e.g., JVM GC mentioned in the paper), which may be derived from logs. There is a good chance that based on domain knowledge and business related KPIs of the technologies, a manageable number of alerts can be prepared per technology type (one per database systems, web servers, messaging sytems, programming languages).
  • Even though alerts are supposed to be less in number compared to metrics and logs, the paper also mentions that there can be a lot of alerts. They don't go into details but mention papers regarding alert correlation, clustering and alert prioritization (see section on Processing alerts).
    • We could see whether we can use some ideas to reduce the number of MAD anomalies.
    • We could see whether these ideas can be used for clustering/compressing logs.
  • Explainability algorithms like LIME can be useful for presenting the output in terms of ranking of the features. We could see whether we can use it for:
    • RCA, deep log.
    • Getting this to work will require supervision but we can see whether we can make it more and more semi-supervised over time.
    • There seem to be papers that have extended these ideas for explainability of unsupervised learning algorithms.
      • We could see whether it is usable for MAD.
        • Ranking various anomalous metrics that are anomalous simultaneously.
        • Ranking various anomalous metrics over a time window (e.g., one day).
      • We could see whether it is usable for log cluster.
  • Could representing textual information using topic models, help with better interpretability for log cluster and deep log?
  • The system uses features that can be measured from the system like alert count, alert count according to technologies, time of day, number of servers with anomalies etc (refer section 3.1.2). Could we use more of such features to present MAD output better? Already we are using duration, deviation and inter-arrival time in SIRE.
  • Three of the incidents that are described can be created by us in SockShop. See Details about the incidents.
  • Even though the paper mentions getting alerts from metrics, logs and traces, the experimental results are based on metrics and logs. It looks like an encouraging sign to create value without APM. Need to check how true this possibility is by looking at other papers like AirAlert.

Details about machine learning

The main part of the system is a binary classifier that looks at an observation window and predicts whether there will be an incident or not in a prediction window.

Features

  • Textual and statistical (domain specific).

Text modeled as a vector using topic models.

  • All the alert contents within a time window are treated as a document by concatenating these contents after stop words removal and tokenization.
  • These time windows are called instance windows. There are multiple instance windows within an observation window. See multiple instance learning below.
  • The size of the vector representation is equal to the number of topics. Number of topics chosen using coherence score (Exploring the space of topic coherence measures, 2015).

Statistical (domain specific) features

  • Alert counts (based on different contexts like alert counts w.r.t. a technology etc), time of the alert, inter-arrival time, other domain knowledge based features.
  • Features identified based on data analysis and domain knowledge.
  • Features could vary according to technology.

Multiple instance learning

  • Distinguishing between helpful and noisy instance windows of an observation window during test time.
  • In training data, if there is an incident occurring within the prediction window, the corresponding observation window is labeled as positive. Otherwise, it is labeled as a negative.
  • Considering the observation window (60 minutes) as a whole would lead to loss of information. Some parts of the observation window have more strong alerts and should be given more weight.
  • Instance windows are sampled from the observation window. Thus, each observation window is a bag of instances. Feature vectors as described above are obtained for each instance window. These feature vectors need to be combined in a weighted manner.
  • The instance windows from the training data are used to determine the weights of the instance windows during test time. In order to do so, the instance windows from all the positive observation windows in the training data are clustered based on Hierarchical Clustering. In the resulting clustering, the clusters with more points are supposed to represent omen instance windows. They are supposed to represent the main incident causing instance windows from the training data. Each instance window from the test observation window is assigned to a cluster in this clustering and given a weight equal to the size of the cluster.
  • A well cited AIOps paper using MIL: Log-based predictive maintenance, 2014. (173 citations)

Dealing with class imbalance

  • Number of prediction windows with incidents is much lesser than windows without incidents.
  • SMOTE oversampling strategy. The minority class (positive windows) is over-sampled by creating synthetic examples through finding k-nearest neighbors along the minority class.

Binary classifier

  • XGBoost can be trained incrementally.
  • Fast inference time (40 ms).

Data

  • 11 real-world online service systems in a large commercial bank, which supports more than one hundred million users and includes hundreds of service systems. For each system, engineers provided us three-year alert data and incidents.
  • Number of incidents varies from 26 to 227 across these systems. Number of alerts can vary between 6766 to 127619.
  • A model is trained for each service system.

Parameters of the system

  • t_l : lead time. 10 minutes.
  • t_p : prediction window.
  • w : observation window. 60 minutes.
  • delta t : sliding window step. Prediction every 10 minutes.

The prediction window size (t_p) directly affects the labeling quality. Refer sections 2.3, 4.5 and 5.2.

  • During training, too large a prediction window size may lead to an increase of false-positive observation windows during labeling, while too small may lead to missing some positive windows.
  • They show choice of prediction window for only two systems (section 4.5): 70 and 90 minutes.

Presenting the output

  • The formulation is in the form of binary classification: whether incident will occur or not in the prediction time window.
  • The nature of the incident needs to be inferred based on the ranking of the features by LIME.

Regarding transferability of the results

  • So far, they have trained on data from a bank and tested it on that bank and another bank.

Details about the incidents

  • Long service response time caused by slow SQL. Caused by database index fault led to a long time for execution of several large SQL statements. Before the incident happens, the system successfully predicted it based on database related alerts. HOW CAN THIS BE PREDICTED?
  • Frequent failed transactions caused by fullGC. Buggy code created many objects occupying too much heap space and let to frequent fullGC. The system predicted it based on some resource METRIC alerts (e.g., memory usage and JVM heap usage) and JVM garbage collection LOG alerts.
  • Service degradation due to unexpected stress. CPU utilization of related servers influenced by an unexpected burst of user requests. (CPU utilization can be judged based on METRICS.)
  • Server hang-up. Server was unresponsive due to system overload. In this case, the system overload was caused by running scheduled tasks. Predicted based on server resource METRICS (e.g., I/O waiting time and CPU utilization).
