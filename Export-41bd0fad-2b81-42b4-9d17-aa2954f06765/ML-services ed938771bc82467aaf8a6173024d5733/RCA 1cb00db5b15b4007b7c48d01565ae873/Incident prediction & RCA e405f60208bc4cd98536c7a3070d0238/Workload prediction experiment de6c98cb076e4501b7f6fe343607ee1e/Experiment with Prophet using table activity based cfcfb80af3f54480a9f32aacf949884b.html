Note: Before going further, let us keep this point in mind: Prophet can be used by training over a time window and predicting into the future w.r.t. to that time window. There is no possibility for making predictions at a later point in time, without training again based on the past time window w.r.t. that point in time. There is no possibility of incrementally updating the model either:

  • https://github.com/facebook/prophet/issues/716
  • https://github.com/facebook/prophet/issues/46
  • https://github.com/facebook/prophet/issues/1290

Thus, using Prophet in an online setting can be expensive. One work around is to reduce training time by reducing the size of the past time window. Some experiments on this aspect can be found below.

In these experiments we will test based on a horizon size of half an hour. While reading the literature on latency prediction in database systems, we came across 1 hour horizon often. So far, we have been testing on 5 minute horizon, 30 minute horizon is a good trade-off.

For Prophet to work, we have to provide a column having time of occurrence of each sample in datetime format. In our case, our samples are equally spaced. It doesn't matter if we don't specify the exact spacing of 10 seconds. For convenience of generating the datetime values, the samples are labeled w.r.t. days starting from January 1st 2010.

In our experiments, the target variable is: total wait time.

The exogenous variables (additional regressors) are:

  • mysql#performance#table_io_waits#count#fetch: which is according to 10 buckets over which the tables will be distributed.
  • mysql#status#bytes#received
  • mysql#status#bytes#sent
  • mysql#status#questions: number of client statements executed.

Prophet is used in two stages:

  • Four instances of single variable prophet to predict the exogenous variables.
  • One instance that takes in the future frame containing values of the exogenous variables and makes prediction on the the target variable (total wait time).
