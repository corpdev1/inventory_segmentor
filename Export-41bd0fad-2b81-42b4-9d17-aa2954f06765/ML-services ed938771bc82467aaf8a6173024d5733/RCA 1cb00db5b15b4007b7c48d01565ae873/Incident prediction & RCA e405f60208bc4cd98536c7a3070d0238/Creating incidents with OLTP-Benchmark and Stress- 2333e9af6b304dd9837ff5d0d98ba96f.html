Papers like DBSherlock and FluxInfer create database incidents using OLTP-Benchmark and Stress-ng. OLTP-Benchmark works with any JDBC compliant database. Its installation has some steps and they are documented in their website. The official website of Stress-ng seems to recommend building it from source across a wide range of platforms. Nevertheless, Stress-ng can be apt installed in Ubuntu, also.

“[TPC-C] involves a mix of five concurrent transactions of different types and complexity either executed on-line or queued for deferred execution. The database is comprised of nine types of tables with a wide range of record and population sizes. While the benchmark portrays the activity of a wholesale supplier, TPC-C is not limited to the activity of any particular business segment, but, rather represents any industry that must manage, sell, or distribute a product or service.”

The OLTP-Benchmark creates workload by running an executable called oltpbenchmark along with a configuration file. In all our experiments involving the OLTP-Benchmark, we work with a database called tpcc.

Note: If we know that the database already exists, then its name can be mentioned in the configuration file. For e.g., if tpcc in MySQL, then we mention tpcc within DBUrl in the configuration file: <DBUrl>jdbc:mysql://localhost:3306/tpcc?useSSL=false</DBUrl>

In order to create and populate a database called tpcc, one runs the command:

./oltpbenchmark -b tpcc -c config/sample_tpcc_config.xml --create=true --load=true

The config file used in this step must also have an existing database name mentioned in DBUrl. DBUrl will be like this: <DBUrl>jdbc:mysql://localhost:3306/EXISTING_DATABASE?useSSL=false</DBUrl>. In case you don't know the name of any existing database, create an empty database called dummy_db by running create database dummy_db; in the MySQL Command-line client will work. It can be later deleted as drop database dummy_db;.

To run the scripts mentioned below, make sure you copy the xml config files into the folder called config within the OLTP-Benchmark project. The shell commands, shell and python scripts should be run from the same folder as the executable oltpbenchmark.

Note: In DBUrl if you don't add ?useSSL=false you may get the following error:

WARN: Establishing SSL connection without server's identity verification is not recommended. According to MySQL 5.5.45+, 5.6.26+ and 5.7.6+ requirements SSL connection must be established by default if explicit option isn't set. For compliance with existing applications not using SSL the verifyServerCertificate property is set to 'false'. You need either to explicitly disable SSL by setting useSSL=false, or set useSSL=true and provide truststore for server certificate verification.

Case 1: Configuration for workload spike (Only increasing number of transactions to 50000. Number of terminals is the same.):

This configuration file can be run as follows:

./oltpbenchmark -b tpcc -c config/sample_tpcc_expt.xml --execute=true -s 5 -o outputfile

It creates a workload, where the first ten minutes is a normal load, followed by ten minutes of high workload.

In order to create a workload spike that involves increase in both the number of transactions and the number of terminals, a bash script, which calls two config files one after the other can be used. It is not clear how to increase the number of terminals within the same config file. tpcc_normal.xml creates a normal load (10000 transactions, 2 terminals) and tpcc_workload_spike.xml creates a workload with 50000 transactions and 128 terminals.

Case 2: Memory Saturation can be created by running:

stress-ng --class memory --all 1 --timeout 300s

Here, 1 instance of all types of stressors in the memory class are run in parallel. By increasing the number of instances, more memory stress can be created.

The timeout parameter determines for how long the incident happens.

Case 9: Poor physical design

Good physical design is needed for efficient execution of SQL statements. For example, indexes are used for performing efficient SELECT operations on tables. If a SELECT statement is to pick only a small number of rows via a WHERE clause, a suitable index will considerably reduce the number of rows that are visited. Thus, one example of poor physical design is to create an index for a table on which mostly INSERT statements are executed. See here for more details:

  • https://stackoverflow.com/questions/2955459/what-is-an-index-in-sql
  • https://dev.mysql.com/doc/refman/8.0/en/mysql-indexes.html
  • https://dev.mysql.com/doc/refman/8.0/en/table-scan-avoidance.html
