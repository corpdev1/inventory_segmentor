Aggregating/coarsening time-series data over time windows

@Hariprasad Kannan wrote:

  • Aggregating the data over a time window could help with:
    • Reducing false positives with sparse data.
    • Reduce noise in general.
    • Save computational power.
    • Better visualization.
  • Need to choose the right window over which to aggregate the data.
    • 1 minute, 2 minutes, 5 minutes, 10 minutes, 20 minutes, 30 minutes, 60 minutes.
  • Larger window will help with all the four advantages listed above.
    • However, too large a window is not useful for timely anomaly detection.
  • Could vary according to nature of the metric (CPU, network, Disk I/O. Maybe, across technologies also.).

Some points to note about using ELK for visualization:

  • One way to create plots is to create a Line Visualization.
    • When searching for indexes for this Line Visualization, it is not clear how to associate a particular component from a host to an index. For e.g., when searching for mysql, only one index (one each for metrics and logs) is found. Which MySQL does this correspond to? Answer: It is averaged across the MySQL instances.
    • The solution for the above is by adding a search filter in the Line Visualization. However, the index name has to be typed.
    • Also, this option allows only 3 hours or more aggregation window for a timeline of two weeks.
  • Another option, is to create a visualization in Managed ELK by modifying an existing visualization or by selecting TSVB (Time Series Visualization Builder) instead of Line based visualization and saving it with a new name. In such visualizations, there is a convenient option to filter by index of a given component and there is flexibility regarding aggregation time window.

Note: For the 3 weeks cases, some of the plots were generated with 20 days of data and not 21.

Note: Each of the metrics is in the form of groups. For Docker metrics, the groups can be of size: CPU - 16, memory - 2, disk I/O - 2, network -4. While looking at the plots, all the cases of each group were looked at. If one plot is similar to all the plots of that group, only that plot is included here. This is usually true for CPU metrics. For network, metrics w.r.t. bytes and packets are similar.

Note: For Linux metrics, there are several Disk I/O metrics per disk on the machine. Also, there are additional network metrics (dropped and error).

Observations

  • Up to a scale of two days, no pattern is noticeable across technologies as the aggregation window is increased from 1 minute to 1 hour.
  • Aggregation over 1 minute windows will surely help to suppress frequently occurring small spikes.
    • As noted here, small variations are suppressed.
    • More test results here.
  • Similarly, aggregation helps to suppress noise (like white noise) in the time-series.
    • It can be observed by looking at the same time-series across larger aggregation windows.
  • Aggregation helps to reduce noise during seasonality identification. Aggregation over 5 minutes windows will help with hourly seasonality identification. Aggregation over 1 hour windows will help with daily seasonality identification.
    • So far, this is based on visual inspection. While performing the seasonality identification experiments, it became clear that it helps to suppress variations that are small compared to the scale at which time period is investigated. This helps with clearer FFT and autocorrelation function.
    • For e.g., we can notice in the case of RabbitMQ that aggregation is revealing a periodicity in the CPU metrics. Need to check whether this periodicity happens always.
  • Regarding trend, we notice cases (especially, Linux system metrics) where the time-series take lesser values during weekends and public holidays. Even with lesser values, these time-series continue to show the daily periodicity. Specific metrics showing this behavior are noted here.
    • Check here for experiments with existing packages for trend analysis.

Regarding sparse time-series

  • Aggregation at a suitable scale renders a time-series to become non-sparse. For e.g., the false positives in Docker metrics observed here are eliminated by aggregating over 1 minute time windows.

Use for seasonality identification

Aggregation is part of the broader topic of looking at time-series at different scales.

Looking at time-series at different scales can be used by PacketAI for seasonality identification. Anodot looks at the time-series at three different scales and identifies periodicity at each scale. Also. their algorithm is designed to identify only one periodicity in a given time-series. They are achieving the different scales via band-pass filtering.

Doubts

  • For RabbitMQ, it is possible to associate Docker based system metrics (CPU, memory, disk I/O, network) with the component along with RabbitMQ metric set. Is it possible to do the same for MySQL? Right now, we are looking at the Linux system metrics which is topologically linked with the MySQL.
  • Linux system metrics (linux6040eafa3a9e9f0012cebfd4) of docker0 (refer topology here) has very regular disk I/O behavior (see here). Which component(s) does this correspond to?
  • Many seasonal metrics are present in Linux and Docker components. A few docker based metrics in Redis and RabbitMQ are periodic. Otherwise, a few MySQL metrics are periodic. It will be good if we can see more seasonal metrics directly from the technologies (either CPU, memory, disk I/O, network for those technologies or other metrics for those technologies).
