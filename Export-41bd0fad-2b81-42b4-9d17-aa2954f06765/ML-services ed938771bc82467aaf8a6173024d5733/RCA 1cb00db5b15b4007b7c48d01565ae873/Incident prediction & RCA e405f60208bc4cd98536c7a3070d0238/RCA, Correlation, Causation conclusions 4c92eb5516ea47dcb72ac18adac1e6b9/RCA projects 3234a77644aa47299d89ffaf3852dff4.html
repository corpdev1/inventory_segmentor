In-app RCA

In-app RCA aims to explain anomalies of an application, system, database by only using its own metrics

PoC iSQUAD

iSquad creates clusters of similar incidents. Each cluster is labeled by the root cause of the incidents. When a new incident happens, iSquad computes similarity between the new incident and existing clusters.

code

Procedure

Learning:

For any component X (mainly databases):

  1. Detect anomaly on KPIs of X
  1. Encode anomalous pattern for metrics of X
    1. spike up
    1. spike down
    1. level shift up
    1. level shift down
  1. Compute clusters of similar incident with adapted cosine similarity
  1. Label each cluster with it corresponding root cause

Inferring:

  1. Detect anomaly on KPIs of a component X
  1. Encode anomalous pattern for metrics of X
  1. Compute distance to clusters and infer root cause

Documents

https://drive.google.com/drive/folders/1lGttfQ_uTCD0bEEJP-5Mq5qG-1qkln8A?usp=sharing

Conclusions

The accuracy of iSquad as shown here varies with the window interval choosen around the anomaly as it impacts the identification of the pattern. Globally  These results show that the techniques for anomaly type identification and incident encoding as proposed by iSquad paper are not robust enough for a complete unsupervised RCA.  We need better time series feature extraction and better incident encoding that is less impacted by the extracted interval.

Microservices RCA

Microservices or node-based RCA aim to detect the anomalous node within a set of interconnected nodes. A node can be an application or a host(docker or physical server). First, it builds a dependency graph (also called service map, causality graph …). Then, when an anomaly is detected at some node (mainly front app), the algorithm go over nodes to detected the origin of the anomaly.

Conclusions

The algorithm is quite simple and efficient. It computes the correlation of high kpi (request duration or process duration time) and make links between front ms and potential anomalous ms. In the experiments, PC algorithm did not give satisfying results. It is necessary to find a better solution to compute non communicating nodes. Our topology can apparently do that.

Granger causality test (explanation)

Requirements for metrics:

  1. Stationary
  1. linear continuation

Results

Test platforms:

  • Sockshop

    Tests on sockshop are with general metrics and opentelemetry metrics

    We stress resources of containers and we compute causality test between opentelemetry metrics (request durations) and system metrics

  • Affluences

In all tests, we compute correlation and causality when anomalies happen.

NB: We consider Anomalies raised by mad after noise reduction.

On Affluences

  • Correlation:
    • 65 % of pairs of anomalies within 5 minutes have flux correlation higher than 0.6
    • For all pairs of highly correlated metrics, more than 80 % of their anomalies  do not happen within a short window
  • Causality:
    • Pairs of anomalies that happened within 5 minutes: 191
      • 65% have granger causality p value less than 0.05 with maxlag at 5
    • 25% anomalies on a metric A are followed (or simultaneously) by an anomaly on a metric B such that A gcause B.
      • Proportions are different between different metrics

On Sockshop:

  • Causality:

    For microservices that have big traffic like catalogue. Causality test identified only catalogue metrics as cause of the performance behavior. For other microservices, the causes are less accurate. These microservices have their request duration mostly constant with spikes.

PoC on abnormal behaviour correlation (Anodot inspired)

description

steps:

  1. Encode time series to binary vector
    1. 0 is normal behavior
    1. 1 is abnormal behavior
  1. Hash binary vector by “Locality sensitive hashing”
  1. Compute similarity
    1. Cosine similarity
    1. Clustering with Latent dirichlet allocation
