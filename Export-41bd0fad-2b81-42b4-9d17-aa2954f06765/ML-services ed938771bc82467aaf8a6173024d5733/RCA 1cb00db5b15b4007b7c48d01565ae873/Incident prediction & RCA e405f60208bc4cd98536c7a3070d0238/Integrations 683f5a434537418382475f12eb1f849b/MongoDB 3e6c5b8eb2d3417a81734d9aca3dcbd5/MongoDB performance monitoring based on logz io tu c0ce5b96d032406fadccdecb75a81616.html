The following metrics could be mapped to high-level KPIs like latency (ops.latencies) and number of errors.

Throughput

mongodb.status.ops.counters.query The total number of queries received since the mongod instance last started

mongodb.status.ops.counters.getmore The total number of getmore operations received since the mongod instance last started.

mongodb.status.ops.counters.insert The total number of insert operations received since the mongod instance last started

mongodb.status.ops.counters.update The total number of update operations received since the mongod instance last started.

mongodb.status.ops.counters.delete The total number of delete operations received since the mongod instance last started

mongodb.status.global_lock.active_clients.total Total number of the active client connections performing read or write operations

mongodb.status.global_lock.active_clients.readers The number of the active client connections performing read operations

mongodb.status.global_lock.active_clients.writers The number of the active client connections performing write operations

ops.counters.query and ops.counters.getmore commands return metrics that indicate the number of read requests received from the time the mongodb (a process that handles data requests and manages data access) instance last began. On the other hand, ops.counters.insert, ops.counters.update, and ops.counters.delete return the number of write requests received.

These throughput metrics are important since they can be used to avoid many performance issues, such as resource overloading. To get a general overview of your MongoDB cluster activities, you should first look at number of read/write clients and the number of db operations that they perform.

Things to monitor: Check if requests are accumulating faster than they are being processed. The relationship between the amount of current active clients and your database load.

From the Datadog article on MySQL: The current rate of queries will naturally rise and fall, and as such it’s not always an actionable metric based on fixed thresholds. But it is worthwhile to alert on sudden changes in query volume—drastic drops in throughput, especially, can indicate a serious problem.

Client connections

mongodb.status.connections.current The number of connections to the database server from clients. This number includes the current shell session. Consider the value of available to add more context to this datum

mongodb.status.connections.available The number of unused available incoming connections the database can provide

mongodb.status.connections.total_created A count of all incoming connections created to the server. This number includes connections that have since closed.

One of the most important metrics is the number of client connections. This includes current active connected clients and the unused connections as well.

An unexpected rise in the client connections metric can occur if the connection is not handled well or if there is an issue inside of the MongoDB driver that is used for handling the connection. Tracking the behavior of these metrics will allow you to set the relevant summary metrics such as the average amount as alerts’ thresholds.

Memory metrics

mongodb.status.memory.virtual.mb The amount, in megabytes (MB), of virtual memory used by the mongod process

mongodb.status.memory.resident.mb The amount of RAM, in megabytes (MB), currently used by the database process

mongodb.status.extra_info.page_faults The total number of page faults that require disk operations. Page faults refer to operations that require the database server to access data that isn’t available in active memory.

Similar to the storage metrics, memory metrics are important to monitor because overloading RAM memory within your server(s) is never good. This can lead to the slowing or crashing of your server, which will leave your cluster weakened. Or, even worse, if you have only one dedicated server, MongoDB can dramatically slow down or even crash.

Storage metrics

There is no definitions for metrics. The metricbeat documentation only states that dbstats provides an overview of a particular mongo database. This document is most concerned with data volumes of a database.

mongodb.dbstats.collections

mongodb.dbstats.data_size.bytes

mongodb.dbstats.file_size.bytes

mongodb.dbstats.index_size.bytes

mongodb.dbstats.storage_size.bytes

Another set of very important metrics is related to storage. dbstats provides an overview of a particular mongo database, especially, data volumes of a database.

A large drop in data_size can also indicate there are many requested deletions, which you should investigate to confirm they are legit operations.

The information about page faults is not matching between what is given in the logz.io page and in elastic.co.

According to elastic.co: The total number of page faults that require disk operations. Page faults refer to operations that require the database server to access data that isn’t available in active memory.

According to logz.io: The number of page faults or the number of times MongoDB failed to get data from the disk.

mongodb.replstatus.lag.max Difference between optime of primary and slowest secondary

All secondary nodes must be on sync with the primary and therefore the sync between primary and secondary nodes must be done as quick as possible to keep the replication lag close to zero.For example if the primary node crashes a secondary node takes over his role as primary. If the there’s a high replication lag while the primary node is gone, there’s might an issue with data integrity.All metric values for each node can be found inside attribute “members” of replication set status.

How to monitor: It can be done by calculate the time difference between primary node “optimeDate” minus secondary node “optimeDate”. The result will be the replication lag in milliseconds.

Critical value: A first warning notification should be send if replication lag is higher than 60 seconds and a high priority notification if lag is higher than 240 seconds.
