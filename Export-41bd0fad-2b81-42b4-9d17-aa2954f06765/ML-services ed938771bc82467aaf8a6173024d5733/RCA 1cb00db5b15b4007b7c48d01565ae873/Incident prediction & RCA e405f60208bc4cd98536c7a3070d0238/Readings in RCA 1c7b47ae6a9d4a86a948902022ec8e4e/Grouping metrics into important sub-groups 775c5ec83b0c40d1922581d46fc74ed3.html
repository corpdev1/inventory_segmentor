Grouping metrics into important sub-groups

@Hariprasad Kannan wrote:

Generally, people (DBSherlock, FluxInfer etc) seem to look at the following subcategories of metrics (CPU, RAM, Disk I/O, Network). In the case of database systems, people are looking at Lock contention, also.

  • CPU usage.

    It will be good to directly obtain CPU metrics for the MySQL application from https://www.elastic.co/guide/en/beats/metricbeat/current/exported-fields-system.html

    Even otherwise CPU usage can be well approximated by:

    • mysql.performance.events_statements.count.star: Number of summarized events.
    • mysql.status.queries: The number of statements executed by the server. This variable includes statements executed within stored programs, unlike the Questions variable. It does not count COM_PING or COM_STATISTICS commands.
  • RAM usage.RAM is mainly used for the buffer pool. We can look metrics that are under mysql.status.innodb.buffer_pool.*. For e.g., mysql.status.innodb.buffer_pool.bytes.data is "the total number of bytes in the InnoDB buffer pool containing data", while the ratio mysql.status.innodb.buffer_pool.pages.data/mysql.status.innodb.buffer_pool.pages.total could give a close estimate of how much the space allocated for the buffer pool is actually utilized.
  • Disk I/O.mysql.status.innodb.buffer_pool.pages.flushed: Flushing is a standard operation in database systems that leads to disk I/O.mysql.status.innodb.buffer_pool.pool.reads:

    The following could also be useful:mysql.status.cache.table.open_cache.hits: The number of hits for open tables cache lookups.mysql.status.cache.table.open_cache.misses: The number of misses for open tables cache lookups.mysql.status.flush_commands: No information available. Check empirically.

    Need to understand what this means:mysql.status.cache.table.open_cache.overflows: Number of times, after a table is opened or closed, a cache instance has an unused entry and the size of the instance is larger than table_open_cache / table_open_cache_instances.

Note: RAM usage and Disk I/O are closely related, as pointed out by the paper "Performance and Resource Modeling in Highly-Concurrent OLTP Workloads".

  • Network connectivity with the clients.We don't yet have metrics which are explicitly named as network metrics. However, the network is used to communicate with the clients. Thus, we could make use of the following two metrics:mysql.status.bytes.received: The number of bytes received from all clients.mysql.status.bytes.sent: The number of bytes sent to all clients.
  • Lock contention.Direct metrics are not yet available.

    The following could be useful:mysql.status.delayed.writesThere are other related metrics:mysql.status.delayed.errors, mysql.status.delayed.insert_threadsNo information is available yet in the web-page. Need to check with experimental data and understand.

    Could less number of commits (mysql.status.handler.commit) mean more contention?

    Could number of connections be related to lock contention?For e.g.:mysql.status.connection.errors.internal: The number of connections refused due to internal errors in the server, such as failure to start a new thread or an out-of-memory condition.mysql.status.connection.errors.max: The number of connections refused because the server max_connections limit was reached. thread or an out-of-memory condition.

    Need to check whether the following will help with estimating lock contention:mysql.status.innodb.buffer_pool.pages.misc: The number of pages in the InnoDB buffer pool that are busy because they have been allocated for administrative overhead, such as row locks or the adaptive hash index.mysql.status.handler.external_lock: The server increments this variable for each call to its external_lock() function, which generally occurs at the beginning and end of access to a table instance.

    In Filebeat, there are some slow related fields that could be useful:mysql.slowlog.lock_time.sec: The amount of time the query waited for the lock to be available. The value is in seconds, as a floating point number.mysql.slowlog.innodb.rec_lock_wait.sec: How long the query waited for locks.
