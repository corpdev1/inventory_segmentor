Important concerns for Packet AI:

  • The future workload is in terms of queries. We have to obtain metrics that we can use from these queries. For e.g., table names, action on the table (read/modification). We may have semantically parse the queries to get these information.
  • Packet AI wants to predict incidents, especially anomalous ones. Most (if not all) of the works in workload prediction seems to be concerned with smoother changes in the workload that can be predicted and actions like resource provisioning can be taken.

    Even for the spike workload that they show in this paper, they train the model (Kernel regression) with historical data in which the spike happens. Also, the spike is a periodic (annual) spike, not an anomalous incident. The behavior that drives the spike is more well defined: more and more students submitting applications as the deadline nears.

    Kernel regression cannot extrapolate and needs to see a similar spike at least once before. It is possible to get better performance for unseen spike incidents with other algorithms but still enough training data will be needed for such algorithms also.

Paper summary

  • The paper "Self-driving database systems" talks about two categories of features that characterize queries in a workload: physical and logical. Physical: resource consumption and run time metrics of that query. Logical: what tables it reads/affects etc. This paper shows one more way to characterize queries: its arrival rate history. It captures both logical and temporal behavior of the queries.
  • Each query is preprocessed to extract a template version of the query. The templates with equivalent semantic features are aggregated to reduce the number of unique templates.
  • For all the templates the number of queries that arrive per template over a given time interval is tracked.
  • For a given query template 10k time points in the last month of a template’s arrival rate history forms a feature vector. Based on cosine distance between these feature vectors, the query templates are further clustered. The centers of the clusters are the average arrival patterns of all the query templates in that cluster. All the query templates of each cluster are retained.
  • An online variant of DBSCAN is used to cluster the query templates based on arrival rate based feature vectors. At the end there is a huge reduction when comparing the number of queries to final clusters. Each cluster is represented by a representative query template.
  • For forecasting, the system records the number of queries executed per minute for query templates from each cluster. The prediction algorithm is an hybrid of an ensemble model (Linear Regression + RNN) and Kernel Regression. Depending on the predicted load from each of the two models, one of the predicted values is chosen. The choice between the two models is to ensure better forecasting during spikes. KR performed better for the spike workload but they also note that KR has seen the spike earlier.
  • They show results with three types of workloads: 1. Seasonal, 2. An increasing trend towards a spike, 3. An increasing trend with a shift offset.
  • They show results with prediction horizon of 1 hour, 1 Day and 3 Days. They talk about aggregation windows of 1 minute, 10 minutes, 20 minutes, 30 minutes, 60 minutes, 120 minutes. Note: KR also aggregates over 1 hour interval.
  • The predicted workload is in terms queries from each cluster. They plug in values (from history) to required fields in the query template.
  • The predicted workload is used for the task of automatic index selection.
  • They also show comparison with an earlier logical features only based approach. Out of two experiments, the two approaches show similar results in one case and in the other case the arrival rate based approach is better.

In order to implement in Metric beat

  • The subset of metrics under mysql.performance.events_statements.* is w.r.t. query digest. According to MySQL documentation, the digest is expected to be a hash value (https://dev.mysql.com/doc/refman/5.6/en/performance-schema-statement-digests.html). What we are observing in the raw Kafka topics sent by Metribeat is a query template. This can be sent to the algorithm. Unlike arrival time of each query template, what we get is the time interval in which this query template finished executing and other metrics like max and average latency.
  • Keeping track of the entire query template can be memory intensive. Right now, our aggregator is not keeping track of query templates. If we enable this output, then the query template has to be placed in the field called 'subject'. Right now, there is a maximum limit to the size of the value that is associated with 'subject'. We have to see the effect of disabling the maximum size limit.
  • As such we need to associate query information with metrics under mysql.performance.events_statements.* because of the following reasons:
    • Metricbeat also runs SQL statements to obtain metrics from the performance schema. These are also recorded under mysql.performance.events_statements.*. They should be filtered out.
    • In order to compute metrics like average wait time across all client queries, we need to keep track of average wait times per query template and then multiply them by the number of occurrences of that query template and then average across all client queries. In order to do this it is enough to store query templates as hash values which is more memory efficient.

    State of the art approaches from the ’small data’ domain rely on past workload history to predict important changes in the workload characteristics. This may be good enough in those situations where the same, or similar, jobs are being executed day to day. In the big data space, however, analytic jobs tend to focus more on exploration and experimentation. This makes big data workloads less cyclical and repetitive than those being run on the more traditional ’small data’ systems, making it difficult to leverage the past history to predict the workload type and performance.
