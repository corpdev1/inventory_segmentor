Reminders

  • the ultimate goal of PacketAI is to predict incidents and point to the root causes
  • a major step towards our ultimate goal is: detect anomalies in real time
  • these anomalies may snowball into big incidents but also may be just interesting abnormal behaviours without large impact (ie. warnings, interesting info)
  • the biggest value for user is clearly in early spotting of anomalies that might snowball into large incidents (see early anomalies here)
  • an incident is only ultimately judged by the end user - we have many cases where we strongly thought the anomaly is a clear TP and the user ranked it as FP
  • before the incident is rated as such by the user, we only use the term anomaly (when it is statistically significant it is an anomaly, when it impacts the user it is an incident)

In theory, the problem would be formulated as minimising False Negatives (missed real anomalies) and minimising False Positives (alerted non-real anomalies), or max(recall) and max(precision).

  • min(FNs)
  • min(FPs)

However, from user conversations, our experience and domain practices, it is clear that FPs are much cheaper than FNs, in other words, it is much more acceptable to receive some false positives than it is to miss real incidents. This translates to the need to focus on recall more than precision, hence the problem can be relaxed:

  • min(FNs)
  • FPs < X

where X is a FP tolerance threshold

The idea is to use the FP tolerance margin to relax the problem and more easily achieve min(FNs). In other words, we let algorithms be sensitive as long as they don't consume the FP tolerance margin.

Evaluation of an anomaly alert

There are three evaluation layers

Statistical evaluation

An anomaly can be evaluated "statistically" by applying the basic definition of an anomaly. Note that here we talk about the intuitive statistical definition:

“An outlier is an observation which deviates so much from the other observations as to arouse suspicions that it was generated by a different mechanism.” source

In our case, the different mechanism could be a bug, a config change, a human error, a hardware defect ...etc

Guessed domain evaluation

In addition to the statistical evaluation, PacketAI team can use domain knowledge to filter out probable FPs, ie, statistically significant anomalies that likely do not "make sense" to the end user. This requires understanding of the whole system generating the anomaly as well as understanding of the target infrastructure. Note that this kind of evaluation is only a guess from our side and in no case should be regarded as conclusive.

User provided evaluation

The ultimate evaluation is the user-provided one, as the user has more knowledge about the impact (or probable impact) of the anomaly, as they have much more context than any solution provider.

Thoughts on gate keeping anomaly alerts

It is reasonable to imagine a gate-keeping system for alerts where Packet engineers first receive the alert and only release it to end users if it "makes sense". There are many practical issues with this:

  • the ultimate issue with this is that only the user is able to judge whether or not the alert "makes sense" for them (see reminders above)
  • other practical issues include:
    • it is unfeasible to analyse alerts in a time frame that is short enough to not compromise the real-time nature of our value (5 min) (see some alert evaluations here and here)
    • if, hypothetically, this level of mechanisation of alert evaluation is achieved, it would be better to inject it into the algorithms directly (incident manager service)

Emergency alert/model-stop

What if for some reason (for eg, algorithm bug, data pipeline bug ...), large numbers of FPs is being generated and may lead to consuming the FP tolerance margin?

In this case, it is not useful to investigate FP alerts individually. it is however necessary to completely silence the alerts on the affected source of data (KPI, component) until the issue is understood and fixed. This feature is already built and can be used by both PacketAI team and the end user.
