Introduction

A log can be processed in the following ways (and more):

Grok - parsing the log using regular expressions (e.g., timestamp, IP address etc). Tokenization - Obtaining tokens from the raw log or the content string obtained from the Grok. Advanced Parsing - e.g., static and dynamic part, to create a template. Named entity recognition. Representation - e.g., embedding vector, useful for other ML tasks.

There are multiple tasks and even for a given task (say, parsing), we see multiple ways, with pros and cons depending on the nature of the logs.

If we have to summarize all these tasks and algorithms in a short manner, we could use an umbrella term like log analysis. However, there are many parts to log analysis and depending on the situation, we need to address these parts adequately, to get a better final result. This paper, even though from 2011, could still give a nice perspective.

Logs are semi-structured with considerable variability across different contexts. Directly obtaining a vector representation of logs, in the spirit of sentence embedding in NLP, even though desirable, could face serious challenges because of the variability in the structure of the logs and the difficulty in recognizing the nature of the various tokens.

It is better to take as much help as possible from the many ways to process logs, both in terms of different ways achieving different end goals and different ways for the same end goal. For e.g., this paper says "There is still no log parser that performs well on all log data. Therefore, we suggest users to try different log parsers on their own logs first." A few lines from an earlier related paper: "Log mining is effective only when the parsing accuracy is high enough. Because log mining can be sensitive to some critical events. 4% parsing errors on critical events can cause an order of magnitude performance degradation in log mining." This may be an exaggerated statement but shows how the different parts of log analysis influence each other.

In NLP also, people analyse the text using multiple (related) ways (named entity recognition, part of speech tagging etc) and combine the outputs in some way according to the end goal. It is true that NLP people also work on systems that performs two or more tasks in a joint manner. Those papers still recognize that there are these individual tasks and then try combine them (e.g., Joint Parsing and Named Entity Recognition). For our goal of log parsing, we could combine multiple ideas in the form of one idea post-processing the results of the other or in the form of consensus clustering.

We need to invest more efforts to make progress in log analysis. There is a considerable amount of literature that we should try to make use of. There is a critical mass level of effort that is needed to start making progress in log analysis. We have to read and experiment with some more ideas that are already in the literature. It will be good if we can do this from time to time. This effort will help to address various challenges and do more useful things with logs.

Aiming to analyse custom logs that are too complex may also not be needed. We could give feedback to the customer, to improve their custom logs in such a situation. For e.g., take a look at sub-section called "Log quality" in section V of this paper.

Tokenization

Tokenization itself is a big topic. We need to make some simplifying assumptions. As noted in the introduction, if there are logs that are very hard to even tokenize, we could give feedback to the customer.

What are some log specific words and characters to look out for: , : Brackets like () (could we assume that they will come in pairs?) Words like: status, state, addr, http, HTTP url like strings Port numbers like :8080 Refer to Table 2 of NuLog paper for possible symbols based on which we can tokenize the log.

It will be good to leverage Grok as much as possible to recognize sub-parts of the logs. This preprocessing of the log to identify entities like IP address etc has been pointed out in the two papers offering guidance by LOGPAI (see below).

Some papers recommend removing all special characters and numbers by the end of tokenization and entity recognition.

Papers on log parsing

There are many papers. Even a lesser known paper like "A search-based approach for accurate identification of log message formats" (Messaoudi et al, ICPC 2018) has many citations. Usually, each paper is based on one core idea/approach (for e.g., see the classification of ideas in the papers "Tools and Benchmarks for Automated Log Parsing" and "Self-supervised log parsing".). It will be good to be aware of a broad set of ideas and see how we can possibly combine them.

The papers "Tools and Benchmarks for Automated Log Parsing", Zhu et al, arxiv 2019 and "An Evaluation Study on Log Parsing and Its Use in Log Mining", He et al, 2016, appear to be good guides. The authors are behind LOGPAI.

Embedding based representation

Contextual embeddings

Even though Word2Vec models the context of a word (either continuous bag-of-words or skip-grams), people are trying to improve how the context is modeled.

From the paper Learning and Evaluating Contextual Embedding of Source Code:

"... the subtle differences in the meaning of a token in varying contexts are lost when each word is associated with a single representation. Recent techniques for learning contextual embeddings (McCann et al., 2017; Peters et al., 2018; Radford et al., 2018; 2019; Devlin et al., 2019; Yang et al., 2019) provide ways to compute representations of tokens based on their surrounding context, and have shown significant accuracy improvements in downstream tasks, even with only a small number of task-specific parameters." "To deal with varying word context, contextual word embeddings were developed (McCann et al., 2017; Peters et al., 2018; Radford et al., 2018; 2019), in which an embedding is learned for the context of a word in a particular sentence, namely the sequence of words preceding it and possibly following it."

  • Some of the references from the paper. Please, check the paper for the others: CoVe (Context Vectors), "Learned in Translation: Contextualized Word Vectors", McCann et al, NeurIPS 2017, "Deep contextualized word representations", Peters et al, NAACL-HLT 2018.

To understand more:

  • How much more powerful is this compared to the context modeled by Word2Vec (continuous bag-of-words (CBOW) and skip-gram) or the triplet based context used in Log2Vec?

Notes about papers

Take aways

  • Need to combine multiple ideas/algorithms - it requires a lot of progress (if at all it happens) for deep learning to completely replace other algorithms for log parsing and representation.
    • The algorithms could be sharing the target goal (e.g., parsing) or could help each other (e.g., entity recognition could help parsing).
    • Either some algorithms could act as pre/post-processing for others or the outputs could be combined.
    • Two ways to combine Drain with DL based representation:
      • Compute vector representation based on the template, instead of the log. e.g., Template2Vec, "Robust and Transferable Anomaly Detection in Log Data using Pre-Trained Language Models".
      • Take inspiration from papers like LogBERT and see whether two similar logs that are assigned separate log keys by Drain, could still have nearby vector representation.
      • Need to ask @Marwen Sallem: Generally what is the range of number of templates that are identified by Drain for a topic?
    • Check whether the merging of template groups given in the paper "A Directed Acyclic Graph Approach to Online Log Parsing" can be implemented and tested.
      • It is a simple logic based on the longest common subsequence.
    • The above paper, which is an extension of Drain by the same authors, mentions this line "Drain frees developers from the burden of parameter tuning by allowing them use Drain with no pre-defined parameters."
      • Need to understand this point better. @Marwen Sallem was mentioning some hyper parameters to tune.
    • Check the approach Logram (a recent, very good method according to a survey paper).
      • See whether it can be applied on the output of Drain.
  • Should the log be split into header and content? How to tokenize?
    • Some papers don't split into header & content and only tokenize based on simple white space. However, the same research group has another paper the same year, where they recognize special strings like IP addresses, dates,
    • Other papers recommend splitting into header and content. For e.g., according to IBM/Drain3: "It is recommended to extract structured headers like timestamp, hostname. severity, etc.. from log messages before passing to Drain3, in order to improve mining accuracy." In other words, they recommend splitting the log into header and content.
    • If splitting into header and content is too difficult, we should at least recognize standard strings/entities like dates, IP addresses, the string indicating level, logger name, host name, keywords like addr, status, email addresses etc.
    • Check this feature called Masking in IBM/Drain3: https://github.com/IBM/Drain3#masking
    • Break words into smaller sub-words as a preprocessing step: camel case, WordPiece, as part of the model (Mimick in Log2Vec).
      • Note: In the literature there is a strong connection between WordPiece tokenizer and BERT (need to understand better).
    • Merge adjacent wild-card tokens as one wild-card token.
  • Use heuristics:
    • This point is related to using multiple algorithms.
    • Partition logs into sub-groups according to information like the value of the level string.
    • Leverage ideas in existing literature. We are already trying many ideas that are present in the literature: finding frequent (sets of) tokens.
    • There could be more. e.g., papers like LogParse: Making Log Parsing Adaptive through Word Classification.
  • Deep Learning based representation learning:
    • Make representation learning as part of a larger task like anomaly detection.
      • e.g., LogAnomaly, Self-Attentive Classification-Based Anomaly Detection in Unstructured Logs, Log-based Anomaly Detection Without Log Parsing, LogBERT, Robust and Transferable Anomaly Detection in Log Data using Pre-Trained Language Models.
    • Leverage more ideas in language modeling like contextual embedding, Transformer (especially the encoder), BERT, GPT-2, XL-Transformers, embedding based on synonyms and antonyms (Template2Vec, Log2Vec) etc.
      • Language models especially could directly lead to sentence embedding.
    • Explore more global embedding techniques like sentence, paragraph and document embedding techniques.
  • There is a sequential relationship to the logs generated by a system. This is because logs are generated by computer programs and there is a logical flow in the execution of programs. It will be good to work more on modeling this sequential relationship. We should build further on the DeepLog work that we have done.
  • If we sense a too difficult set of logs (difficult to tokenize, too many template groups), we could give feedback to the customer to write better formatted logs.
  • Understand more about log compression (there are many papers).
  • The topic of unstructured text needs to be explored further. This can help us to overcome several challenges. Please, check here.
