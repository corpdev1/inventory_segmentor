Tools and Benchmarks for Automated Log Parsing

Zhu et al, arxiv 2019

  • Categorize the methods mainly as those based on frequent pattern mining, clustering and heuristics (exploiting nature of logs).
  • From the results, we can briefly conclude that log parsers should take full advantage of the inherent structure and characteristics of log messages to achieve good parsing accuracy.
    • AEL, IPLoM, Drain.
  • There is still no log parser that performs well on all log data. Therefore, we suggest users to try different log parsers on their own logs first.
  • At Huawei, to reduce the efforts of engineers, a platform (called LogKit) has been built to automate the log analysis process, including log search, rule-based diagnosis, and dashboard reporting of event statistics and correlations. A key feature of this platform is to parse logs into structured data.
  • In sub-section "Success stories", they describe four ways by which they improved the performance of Drain, when they deployed in Huawei. Especially, preprocessing (using filters like Grok filters) and partitioning (grouping logs according to a higher level property like the level) could be useful to us.
  • In sub-section "Potential improvements", they discuss three aspects to address.
    • For us, "state identification" could be the first thing to target. SARA is already doing something similar.
    • Length variability: In real world logs, it is possible that logs belonging to one template are of variable length. We are also observing this in our data-sets. Probably, we can post-process in some way.
  • Findings from their earlier paper "An Evaluation Study on Log Parsing and Its Use in Log Mining", 2016:
    1. Current log parsing methods could obtain high overall accuracy especially when log messages are preprocessed with some domain knowledge based rules.
    1. Clustering-based log parsing methods could not scale well with the volume of logs and the tuning of parameters (e.g., number of clusters) is time-consuming.
    1. Log mining is effective only when the parsing accuracy is high enough. Because log mining can be sensitive to some critical events. 4% parsing errors on critical events can cause an order of magnitude performance degradation in log mining.

Log2Vec

Meng et al, ICCCN 2020

  • They represent the log as a weighted average of vector representations of the words.
  • In order to get the embeddings of the words, they have a loss function based on synonyms, antonyms, triplets and also, Word2Vec based context window.
  • They also handle OOV words using the approach in the paper "Mimicking Word Embeddings using Subword RNNs".
  • Further leads about individual tasks:
    • TransE model is the most effective representation method for triplets.
    • Universal antonyms can be found in WordNet, which is a lexical database for English.
    • Relation triples can be extracted from processed logs using dependence trees, which is a prevalent semantic parsing method.
  • Data-sets
    • Spark, HDFS, Windows, Hadoop.

      These data-sets are relatively less challenging.

    • Other data-sets: BGL (What supercomputers say: A study of five system logs, 2007).
    • Logs produced by switches in a top cloud service provider.

      Clustering results are shown on this data-set only. The results don't appear to be very good.

Self-supervised log parsing

Nedelkoski et al, arxiv 2020

  • Learns the representation based on masked language modeling (MLM).
    • "Cloze Procedure": A New Tool For Measuring Readability", W L Taylor, 1953.
    • "Bert: Pre-training of deep bidirectional transformers for language understanding", Devlin et al, 2018.
    • The architecture shown in the paper appears to be an application of the transformer based architecture trained on a loss based on masked word prediction.
  • All logs are padded such that they will have the same length M (= max(|ti|) + 1, ∀i), which is the maximal number of tokens across all log messages within the log dataset added by one, and |ti| is the number of tokens in the ith log message. Also, logs are appended with a token called <CLS>. A token called <SPEC> is used for padding.
    • Not sure why all the logs should be of the same length.
  • Output during test time: Vector based representation of the log and a template (static and dynamic tags) based representation of the log.
  • It looks like the representation of the <CLS> token of the log (which is the first token of the modified log) is expected to represent the log. Need to understand this part.
    • From the paper: "Since the last vector embedding of the <CLS> token is used for prediction, it is forced to summarize the log message. Otherwise, it would not be able to solve the masked token prediction task well enough across all tokens. We hypothesize that the constant part of log templates will constraint the model to learn similar <CLS> token embeddings when log messages are of the same template."
  • Log template extraction
    • Log is passed through the trained model, where each word is masked one after the other.
    • The idea for obtaining the template is that a high confidence prediction of the masked word means that the word is a static part of the log template otherwise, dynamic parameter <*>.
  • Results shown using metrics based on "Tools and Benchmarks for Automated Log Parsing", Zhu et al, 2019. Their method has high accuracy and robustness to data-sets.
  • Transformer based approach takes care of:
    • The generated vector representations should be closer for log messages belonging to the same log template and distant for log messages belonging to distinct log templates.
    • Token embeddings are adjusted during training to represent the semantic meaning of tokens depending on their context.
  • Nice properties of the approach:
    • Simple tokenization approach.
    • Each token is predicted using all the other tokens in the log, along with positional information. Better way to model context compared to triplets based approach of Log2Vec.
    • By-product of vector based representation of the log and the representations of nearby logs are expected to be close to each other.
  • Possible weaknesses:
    • Not sure how their approach can be affected by very long logs. All the logs will be padded to this length. Even though handling long lengths is one of the strengths of the transformer architecture.
    • Could two logs with several dynamic tokens still have nearby vector based representations?
  • About their tokenization approach: White space based tokenization. "In contrast to several related approaches that use additional hand-crafted regular expressions to parses parameters like IP addresses, numbers, and URLs, we do not parse any parameters with a regex expression. Such an approach is known to be error-prone and requires manual adjustments in different systems and even updates within the same system."
  • Doubts
    • What is the parameter ϵ\epsilonϵ﻿?
    • What is the size of the training, validation and test data-sets for each of the data-sets?

LogAnomaly: Unsupervised Detection of Sequential and Quantitative Anomalies in Unstructured Logs

Meng et al, IJCAI 2019

  • Approach called Template2Vec (baseline in Log2Vec paper).
    • Log2Vec is an extension of this work. Log2Vec uses the ideas of synonym and antonym based embedding and averaging the token embeddings. Template2Vec considers only the words in the matched template, while Log2Vec considers all the words in the original log. Log2Vec has some additional terms regarding triplet based loss and OOV representation.
  • Uses FT-Tree for initial parsing.
    • Forms log template groups offline. Periodic retraining.
  • Aims to capture both sequential and quantitative behavior of a set of logs. Highlights the importance of sequential behavior of logs, which happens because of the sequential execution of programs.
    • LSTM based model.
  • During test time, incoming log is matched to the closest existing template group (even if it is very approximate).
  • Uses "Integrating Distributional Lexical Contrast into Word Embeddings for Antonym–Synonym Distinction" for word embeddings that emphasizes the nature of synonyms and antonyms.
    • Called dLCE.
    • Recommends adding domain specific synonyms and antonyms.

LogBERT: Log Anomaly Detection via BERT

Guo et al, arxiv 2021

  • Anomaly detection in a sequence of log keys.
  • Uses Drain to match logs to log keys.
  • The log key representations are learnt by the model: "Each self-attention makes each key attend to all the log keys in an input sequence and computes the hidden representation for each log key with an attention distribution over the sequence."
  • Similar learning of embedded representation of log keys happens in the LAMA paper, also. Need to ask @Marwen Sallem about his observations. Since, LogBERT uses masked token prediction using bi-directional information, the performance could be better.
  • Similar to a few other papers, an extra token is added to the beginning, whose learned embedded representation is expected to correspond to the entire sequence.
  • During training, the representation of the sequences are encouraged to be close to a center. Each sequence is represented by the token added to the beginning of the sequence. The center is the average of the representations of the beginning extra token of all the log sequences. Thus the log sequences are assumed to be normal behavior.
  • Doubt: Averaging the representation of all the logs may not be desirable. We could partition logs (based on the value of the level etc) and average representations of each partition.

Self-Attentive Classification-Based Anomaly Detection in Unstructured Logs

Nedelkoshi et al, ICDM 2020.

  • Anomaly classification which assumes that normal logs will be clustered compactly.
  • Need to understand better: "Add domain bias on the anomalous distribution to improve detection [19]. We provide such bias by employing easily accessible log datasets as an auxiliary data source." "The auxiliary dataset helps to learn a better representation of the normal data while regularizing against overfitting."
  • An extra token is added to the beginning (like the Self supervised log parsing paper), which is used to summarize the entire log.
  • During training, it looks like they label the target data-set as normal and auxiliary data-set as abnormal.
    • From the paper: "Not using any anomaly data from the target system for learning purposes in our experiments."
  • The model applies two operations on the input tokens: token vectorization (token embeddings) and positional encoding. The subsequent structure is the encoder of the Transformer module with multi-head self-attention, which takes the result of these operations as input. At the output of the encoder, are the transformed vector representations of the initial tokens.
  • The representation of the appended prefix token is utilized in the objective function for clustering.
    • Gaussian radial basis function in binary cross entropy loss.
    • Many anomaly detection papers utilize this spherical loss. e.g., LogBERT: Log Anomaly Detection via BERT.
  • Tokenization: https://www.nltk.org/ Used for tokenization. This is what they say about what they do for tokenization: The message is first filtered for HTTP and system path endpoints (e.g., /p/gb2/stella/RAPTOR/). Lower case transformation of all characters is applied, and all of the ASCII special characters are removed. The log message is split into word tokens. We remove every token that contains numerical characters, as they often represent variables in the log message. Additionally, we remove the most commonly used English words that are in the stop words dictionary of NLTK (e.g., the and is).

Log-based Anomaly Detection Without Log Parsing

Le and Zhang, arxiv 2021

  • Existing methods usually analyze only message content and remove other information (header). In this paper, NeuralLog uses all textual information such as verbosity, component, and content to extract the semantic meaning of log messages.
  • Subword tokenization using WordPiece: To deal with OOV words.
  • Employs the feature extraction function of pre-trained BERT to obtain the semantic meaning of log messages.
    • (Need to understand the architecture better) "Each layer generates embeddings for each subword in a log message. We use the word embeddings generated by the last encoder layer of BERT in our work. Then, the embedding of a log message is calculated as the average of its corresponding word embeddings."

Robust and Transferable Anomaly Detection in Log Data using Pre-Trained Language Models

Bogatinovski and Ott et al, 2021

  • Unsupervised approach. Code: https://github.com/haraldott/anomaly_detection_main
  • Uses Drain, also. Represents a log as a template and as a vector.
    • It is the log template that is mapped to an embedding vector.
  • Uses sentence level embedding instead of word level embedding. Directly map a log template to its embedding.
    • Shows comparison between language models BERT, XL-Transformers and GPT-2 for the log sentence embedding.
    • Pre-trained versions of these models are used. Helps with cold starting on unseen log data, according to them.
    • According to them, using a language model to get the sentence embedding is better than weighted averaging of word embeddings.
    • GPT-2 with a regression based approach gave best F1 scores. However, BERT is more stable.
  • During anomaly detection:
    • The number of classes is equal to the number log template groups.
    • This approach allows for the incoming log to be close to one of the existing template groups, even if its template doesn't match with any of the groups. It assigns a template group to the incoming log based on the pairwise distance of the vector representations.
    • If the incoming log neither has a directly matching template nor a close-by log vector representation, then it is directly marked as an anomaly.
    • Classification approach: If incoming log is matched to an existing template group, it is marked as anomaly based whether the bi-LSTM is able to predict this template class.
    • Regression approach: Works directly with the embedding vectors.
    • They have found classification based approach to be better.
  • Doubts:
    • Are sentence embeddings of the logs learnt using pre-trained models (similar to LogBERT etc) or the pre-trained model directly gives the sentence embedding of a log?
    • What exactly happens to adapt a model learnt on data-set A to data-set B, using few shot learning (Section III.C Model transfer)?

Learning and Evaluating Contextual Embedding of Source Code

Kanade et al, 2019

  • https://github.com/google-research/google-research/tree/master/cubert
  • Source code of computer programs are more structured than logs, still the idea of contextual embedding can be tried by us.
  • Even though Word2Vec models the context of a word (either continuous bag-of-words or skip-grams), people are trying to improve how the context is modeled.
  • "... the subtle differences in the meaning of a token in varying contexts are lost when each word is associated with a single representation. Recent techniques for learning contextual embeddings (McCann et al., 2017; Peters et al., 2018; Radford et al., 2018; 2019; Devlin et al., 2019; Yang et al., 2019) provide ways to compute representations of tokens based on their surrounding context, and have shown significant accuracy improvements in downstream tasks, even with only a small number of task-specific parameters." "To deal with varying word context, contextual word embeddings were developed (McCann et al., 2017; Peters et al., 2018; Radford et al., 2018; 2019), in which an embedding is learned for the context of a word in a particular sentence, namely the sequence of words preceding it and possibly following it."
  • Some of the references from the paper. Please, check the paper for the others: CoVe (Context Vectors), "Learned in Translation: Contextualized Word Vectors", McCann et al, NeurIPS 2017, "Deep contextualized word representations", Peters et al, NAACL-HLT 2018.
  • To understand better:
    • How much more powerful is this compared to the context modeled by Word2Vec (continuous bag-of-words (CBOW) and skip-gram) or the triplet based context used in Log2Vec?

Automated IT System Failure Prediction: A Deep Learning Approach

Zhang et al, Big Data 2016

  • About tokenization and masking:
    • Tokenization based on only single empty space as delimiter: Without speciﬁc knowledge or human inspection, it will be easily unfair to use or not any pre-deﬁned tokenizer for the entire set of heterogeneous log data. Thus, a very general delimiter should be used. The use of such delimiter should avoid interfering with the possible, even unknown, delimiters from the log data, or should it introduce confusion into the original data.
    • Recognize special units like IP addresses and URLs as a whole even if they are all delimited by multiple single empty spaces.

A Directed Acyclic Graph Approach to Online Log Parsing

He et al, 2018

  • Extension of Drain, by the same people. Approach to merge log groups.
  • The Drain that we use most likely doesn't have these extensions (discussed this with @Marwen Sallem). Not sure if implementation is available.
  • However, IBM/Drain3 (an enhancement to Drain) is available: https://github.com/IBM/Drain3
    • Found this feature called "Masking" in IBM/Drain3 page: Replace some message parts (e.g numbers, IPs, emails) with wildcards. This improves the accuracy of template mining.
  • According to IBM/Drain3: "It is recommended to extract structured headers like timestamp, hostname. severity, etc.. from log messages before passing to Drain3, in order to improve mining accuracy." In other words, they recommend splitting the log into header and content.
