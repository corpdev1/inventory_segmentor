Objective: discuss the issue of receiving negative metric values

Context

@Marwen Sallem and @Valentin Lapparov were analyzing data which @Valentin Lapparov generated by installing MongoDB and metricbeat locally on laptop and they found that a lot of metrics contain negative values. We have already seen negative values for CPU and @dengke li tried to investigate in vain more about it. This issue has serious consequences on the detection algorithms since such points add serious perturbations to the statistical characteristics of the data used during anomaly detection by MAD.

@Marwen Sallem succeed to reproduce the problem of negative CPU values on docker by doing a series of restarts. So we suspect that the problem is coming essentially from derivatives metrics where the points are computed : currrentValue - previousValue at the restart time, the currentValue is 0, and hence the output becomes simply negative

Possible root cause of this problem

1. Kafka offset

After the investigation, @Valentin Lapparov found that the issue could came from Kafka. When Kafka re-joins the consumer group it fetches the last topic offset which is outdated for some reason. As a result, Kafka consumes old data which then leads to negative values since we take derivatives of the incoming metrics.

2. Metric naming convention

Currently we have the following naming convention for metrics: {subject} | {metricbeat dataset} | {metric name in metricbeat)}

Example: SeriesDB.series|mongodb.collstats|mongodb#collstats#commands#count

The choice of the subject field is very important since it allows us to distinguish between the sources of metrics with the same name. Depending on the technology it could be a process id, a database name etc...

@dengke li, @Marwen Sallem and @Valentin Lapparov found that the subject of MongoDB metrics for the mongodb.dbstats dataset was set to the number of collections instead of the name of the database which caused the data collision (see example below)
