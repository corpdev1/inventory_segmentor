MongoDB metrics limits

Date@December 11, 2020 17:00
SpeakerValentin LapparovAbdelhadi Azzouniddengke liMarin RadmanHariprasad Kannan
Subject(s)Discussion

Objective: Discuss the issue of metric number for mongoDB. We were discussing the issue of metrics for different technologies (for mongo in particular) with @dengke li @florent marmol @Marin Radman during this day and we all agree that we need to filter out the number of metrics since the current architecture is not scalable: for each collection (table) inside of MongoDB we receive 18 metrics and hence the total amount of metrics is N * 18, where N is the number of collections.

Possible solutions:

  1. One of the possible solutions for mongoDB would be instead of treating metrics from different collections separately to take the sum of corresponding metrics. This solution has an advantage: we will reduce the number of metrics and regardless the number of collection the user might have, this number will not change. On the other hand, this might, and probably will, impact the predictive power of MAD since metrics will become more general. For instance, while we were doing the demo for MongoDB, we created anomalies on one particular collection of MongoDB and showed these anomalies. After the change (taking the sum) we will not see metrics for this collection but will see the sum for all collections. It implies that if we have several collections generating load at the same time, collections with more important variance will take more attention of the model than the small ones.
  1. We can restrict the number of tracked collections and propose to the client to choose X collections to monitor. Once this number is fixed we can provision the max. possible number of metrics to treat.
  1. We can filter the metric set down to the most important ones. This option requires to define the necessary metrics for both detection and prediction tasks.
  1. We can maintain information about transactions in the form of clusters. We can limit the number of clusters. We can update the clusters in an online manner. We then need to maintain the information regarding which cluster the transaction belongs to.
  1. A simpler possibility than clustering is to have a limited number of buckets (say, 10) and distribute all the tables uniformly across these buckets. We can keep track of number of reads and number of modifications to these buckets. Time taken per table for reads and modifications could also be discarded because we anyway keep track of total time via other metrics.

The paper "Performance and Resource Modeling in Highly-Concurrent OLTP Workloads" models transactions as follows:

The input data consists of one row per transaction. Each row contains a set of transaction features. The feature set consists of 2 attributes for each table in the database, one for the number of rows read from and one for the number of rows updated/inserted in each table (many of these features will be zero as most transactions do not access all the tables).

According to their approach, we need to maximum keep track of five values per collection. We need to check how others are modeling workload.

The reason we need this information is to model the nature of the workload. In order to do that information about what tables are accessed is also important. Global numbers like total latency or total number of reads, writes may not be not sufficient. For e.g., hundred inserts to one table and one insert each to hundred tables is expected to perform differently.

The clustering approach is to represent the activity in a high dimensional space and to cluster the activities into a limited number of cluster. Here the activity is over a period of 10 seconds and it is given to us by Logstash and the number of dimensions in the high-dimensional space is equal to the number of tables X 2. The 2 is because of keeping track of both number of reads and number of modifications to each table that happens during that period of activity (10 seconds). So, we represent a given activity as a point in this high dimensional space. The memory issue that we want to resolve is happening if we retain all the points in this space. So, instead we can just keep track of which cluster the activity belongs to. The cluster centers need to be updated in an online manner. This is a more difficult approach to implement compared to the bucket based approach. It may involve retraining etc. Also, this approach has less to offer to MAD. It will help prediction. However, it is considerably cheaper from a memory point of view. For each activity, we just need to keep track of which cluster it belongs to and we maintain the clusters separately. In the case of the bucket based approach we need number of bucket X 2.

We can keep track of number of reads and number of modifications to these buckets. Time taken per table for reads and modifications could also be discarded because we anyway keep track of total time via other metrics.
