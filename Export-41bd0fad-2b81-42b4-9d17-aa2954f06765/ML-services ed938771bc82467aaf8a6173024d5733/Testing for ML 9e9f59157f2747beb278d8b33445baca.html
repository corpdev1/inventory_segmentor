Summary

  • To start with we can focus on two broad activities: 1. Validation tests to assess the potential of an algorithm, 2. Release tests for updates being made on the algorithms.
  • The documentation and supporting materials (like code) of the validation tests help with the assessment of the algorithm and also, importantly, to reproduce the tests at a later point of time.
  • Generally, a test could be reproduced if we have information about the following four aspects: the input data, the code, hyper parameter settings, performance metrics.
  • Please, try to collect as much information as possible about the above four aspects. Several points have been mentioned about each of them in the below documentation.
  • A tip: Engineers are hard pressed for time to create sufficient documentation. When presenting the results to the team, seek reviewer comments, which will help to fill gaps in the documentation quicker.
  • Describe all the sub-parts, steps and hyper-parameters of the final algorithm in one place. Either in the style of LaTeX Algorithms or as a flow chart (similar to the system diagrams for MAD, LAD etc). This is especially important for algorithms that have been deployed.
  • Release tests are very important. Please, check this blog post and notes below.
  • For release tests, it is better to keep track of test cases as and when we come across them. This will lead to considerable time saved by searching less for test cases at a later point in time. For e.g., for regression tests, when a new idea is implemented to address a particular issue, the particular cases involved could be immediately used for regression tests. Test cases based on customer feedback are important in general and could be used to ensure minimum acceptable behavior of the system.

This task started by focusing on ways in which the validation tests for the ML algorithms and their documentation can be improved. Subsequently, the focus is on implementing release tests for ML algorithms to ensure that their behavior confirms to an acceptable level of performance.

Resources for guidance

Testing for machine learning systems covers various aspects. Here we will mainly focus on performance from an ML point of view and the factors that affect it (data-sets, hyper-parameters etc).

  • The ML Test Score: A Rubric for ML Production Readiness and Technical Debt Reduction
    • Found via https://ml-ops.org/content/mlops-principles#testing
  • Machine Learning Testing: Survey, Landscapes and Horizons
  • Hidden Technical Debt in Machine Learning Systems
  • There are many more interesting resources that we can refer to over time. There are ideas like behavior testing for ML systems that are getting a lot of attention. For e.g., papers [1], [2], [3]; online articles: [1], [2], [3], [4], [5], [6], [7].

From section III of The ML Test Score: A Rubric for ML Production Readiness and Technical Debt Reduction:

Regarding validation tests: System and test details to be documented

The target problem

  • Description of the problem addressed.
    • It could be addressed by a new feature to improve an existing system.
    • It could be addressed by re-training an existing system on a more suitable data-set.
  • The inputs that the system is expected to work with.
  • The expected outputs.
    • Relate the output to quantifiable metrics like misses and false positives.
  • Is it possible to quantify the impact of model staleness for this problem?

Description about the ML system

  • We will refer to this as system under test (SUT).
    • A new system. A new feature for an existing system. A retraining of an existing model.
  • Describe how it works together with other existing systems.
    • For e.g., a new feature in time series anomaly detection that requires other systems like SIRE and DBSCAN.
    • The settings for these other systems need to be mentioned.
  • The inputs and outputs of the SUT.
  • Description of the algorithm.
  • Model hyper-parameters.
    • Specify all their values.
    • Indicate whether these are tuned parameters.
      • For e.g., In MAD, for Skyline, it is good to know whether uniform weights or optimal weights were used.
  • Specify if the model expects input of a minimum amount (for e.g., one week of data).
  • How the feature/model could be updated: periodically retrained offline, online.
    • If periodically retrained offline, what is the frequency?
    • For our applications, it is difficult to imagine a model that requires very infrequent retraining.

Description about the baselines

  • When testing a new feature/system: describe the baseline system(s) to which it is compared.

How is the data obtained?

  • How was the data obtained while performing the tests and how to obtain the same at a later point of time: Was it from a live Kafka stream, which has been backed up on S3? Is it from S3? Is it via ES queries? How to reproduce the queries?
  • Are additional processing done on the data? Is it raw or stashed?
  • In what form is the data expected? As offline files or as Kafka streams? If Kafka stream, how to recreate the stream using the restore service?
  • If standard offline data-sets were used, mention how it can be downloaded.

Information about data labels

  • Mention whether labelled data was used during training and/or testing.
  • If the labels during testing was decided visually, please mention it.
    • This happens often while deciding about anomalies in time series.

Ways in which the performance of the model have been measured

  • Whenever possible, obtain metrics for both the SUT and the baseline system(s).
  • Numerical metrics: False negatives (misses), False positives, Precision, Recall, F1/F2 score.
    • Generally, requires labelled data.
    • False negatives and false positives could be indirectly assessed by comparing total number of anomalies of SUT with baselines.
    • Plots like histograms, ROC curve etc.
  • Data oriented plots.
    • Can work without labelled data. Visual inspection to assess performance.
    • There are situations when several anomalies may fire in a cluster of timestamps. In the absence of a logic to group them as one anomaly, the numerical metrics will be badly affected. It is better to look at the plot of the time-series with the anomalies and understand the performance of the algorithm.
    • Describe all the items plotted: Could be through a legend or could be summarized in the beginning.

Notes about the data-sets in the test results

  • Attach details about the data-sets and the test cases.
    • For e.g., * Names of the company, the component, the metric etc. * Date-time information.
    • This greatly improves understanding of the results.
    • The variety in the test cases will be easier to discern.
    • This will help to re-run the tests at a later point in time.
  • How many test cases are used to show the results?
    • Even if the number of test cases is less, they could be useful if they are sufficiently challenging.
  • What is the nature of the data-set(s)?
    • For e.g., In the logs literature HDFS is an easy data-set. In our experiments, Affluences RabbitMQ logs is an easy data-set.
    • Is there a reasonable level of challenge and variety in the test cases present in the data-set(s)?
  • How many positive cases (anomalies) are present in the test case and what is the length of the test case?
    • To keep track of data skewness.
  • Additional notes about the data-set if it is from a client:
    • Does it have missing data.
    • Does it have glitches caused by restarts etc, which look like anomalies?
    • Are there incidents during this time period? Which of these incidents were validated by the client?

Stage at which model performance has been tested

  • Offline: With standard data-sets and with client data.
  • Online: In a staged manner, while releasing the feature. To be done routinely to check model drift.

Compare test setting with online deployment

  • Indicate whether or not test setting is same as or very close to deployment setting.
  • If there are some critical differences, please indicate them.

Discussion about the performance from ML point of view

  • This is very important.
  • To understand the strengths and weaknesses of the system.
  • To summarize the take-aways from the test exercise.
  • If possible describe a few misses and false positives in more detail.
    • This helps to understand the algorithm better.
    • This helps to choose test cases for regression tests.
  • Keeping track of technical debt: potential issues to watch out for, areas of improvement.

Link to performance in terms of efficiency, memory, speed and throughput

  • These performance metrics are a separate topic. If there are links between model performance to these issues, please, indicate it.
    • For e.g., if the accuracy of the model is very good but it is very large and occupies a lot of memory.

Deployment status of the algorithm

  • If deployed:
    • When?
    • Motivation to deploy, given the strengths and weaknesses of the system.
  • The deployment status needs to be actively updated. This will help to keep track of:
    • When a feature is superseded by another.
    • If a feature is rolled back, mention why?

Further requirements regarding reproducibility of tests

  • One of our main goals is the reproducibility of the tests. Apart from the points described so far, please, watch out for the following points also.
  • If the test is based on a standalone project, then share the project (either attach the script(s) to the notion page or link to a separate github repo).
  • If the test requires a huge software system (say, MAD or LAD), describe how to set it up locally from the remote repo (branch, tag).
  • How is the input served to the system? Should the input be in the form of a Kafka stream or can it be offline files?
    • For e.g., it is preferable to work with Kafka streams for MAD related tests.
  • Specify any additional processing of the inputs.
    • For e.g., In LAD some algorithms work with the content (which needs the grok pattern to be extracted), while some algorithms work directly with the raw log.
    • If additional processing is part of a larger system (for e.g., MAD) and it can be assumed to be present for this SUT, mention that the input is to be given to the larger system.

Some more tips

  • Actively seek reviewer comments: The engineer may not have enough time to clearly provide the details in the first draft. With the help of reviewer comments, missing details can be added later.
  • Add a summary at the beginning of the test document with the most important high level points.
  • Often cross reference to other Notion pages, so that details about algorithms, other experiments etc are readily accessible.
  • Use tables wherever possible.
    • Structure the tables such that, it is easy to obtain summaries like total number of cases.
  • About plots:
    • Make the plots with sufficient resolution.
    • Plot date-time information clearly.
    • Try to make animated gifs like here to understand the difference.
    • TODO: Create a Notion page where people can add and refer to matplotlib and plotly tips and tricks.
  • Add a date in the Notion page to indicate when the test was done. Add dates when making updates.
  • Mention Jira ticket.

Regarding release tests

  • Resources: [1], [2], [3].
  • Regression tests: Keep track of ideas implemented (for e.g., absolute delta for LogFrequency) and related data-sets to improve system performance. Use these data-sets to create regression tests for the ML algorithms.
    • Especially useful are test cases with unacceptable behavior that are now handled by the new logic.
  • Behavior tests: Please, refer Effective testing for machine learning systems by Jeremy Jordan.
    • Design tests according to specific logic that you expect the algorithm to learn.
    • The three important categories in such tests are tests for invariances, tests for directional expectation and tests for minimum functionality (could include regression tests).
    • Invariances: Artificially pushing the data-set in directions that should not affect the algorithm and see whether the algorithm's output still doesn't change.
    • Directional expectation.
    • Minimum functionality: To ensure a guaranteed level of performance.
      • Apart from the test cases used for regression tests, we could use simpler test cases on which the algorithms are expected to work well.
      • Also, test cases marked as significant anomalies by the client could be used to ensure that they are not missed.
  • Another test is to look for situations when the models could become stale.
    • Depending on the system, minimum functionality tests could be used here.
  • Another aspect that needs further understanding is to organize the above tests according to specific "skills" that we expect the algorithm to learn.
  • The following aspects could be captured while documenting the test cases:
    • Information about the client name, component name etc; date range; challenge level; additional comments. Check here for the csv file prepared for testing the LogFrequency classifier.
