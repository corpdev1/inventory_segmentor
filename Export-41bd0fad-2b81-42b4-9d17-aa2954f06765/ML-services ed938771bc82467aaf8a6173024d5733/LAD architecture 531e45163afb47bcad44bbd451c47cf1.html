Introduction

LAD, Log Anomaly Detection is the service that monitors the log data. The goal is to apply Anomaly Detection algorithms which are based mainly on Machine Learning in order to detect abnormal behaviour.

To start using LAD, you need to follow this documentation.

LAD as a Microservice

Data flow

LAD is a part of Bephor, the packetai monitoring solution.

In order for LAD to receive logs and output anomalies, many steps occurs as explained in the diagram below :

The steps :

  1. A user installs the agent on one or many hosts
  1. A user ask to monitor 1 or many components
  1. The agent start to collects logs with filebeat and send them to kafka : infraID-agentID-log-componentID-raw
  1. Logstash consume the log topics from kafka, process them and send them back to kafka as described here : infraID-agentID-log-componentID-stashed
  1. The activator microservice reads the names of the log topics and send them to a kafka topic called log-activator
  1. LAD consume the log-activator to collect the topic names it needs to process
  1. LAD apply ML AD algorithm for each topic
  1. LAD outputs the results to kafka on a mllog topic : infraID-agentID-mllog-componentID
  1. Minima consumes the mllog topics and display them to the dashboard

Data transformation

Data transformation is a crucial part for LAD. Since they are semi-structured, it is easier to parse the logs and structure them in a way that facilitates applying ML algorithms

For this, we use mainly groks from logstash that are a set of regex rules to parse text.

A typical data transformation is as follow :

Input:

2020-10-08 12:06:55 systemd INFO VM 45 migrated to server II3

Output:

{ 
	"@timestamp": "2020-10-08T12:06:55",
	"process_id": "systemd",
	"loglevel": "INFO",
	"content": "VM 45 migrated to server II3",
	"timestamp_unix": 1602151784
}

High-Level Design

The architecture of LAD is a Client-Server architecture :

  • Client : Consume the log-activator topic to collect the topic names. And for each collected topic, it sends a request to one of LAD servers with the minimum load
  • Server : For each received topic, it launches a new detection pipeline

In other words, LAD has 1 client and could have many servers. Each server is responsible for running N topics detection pipelines. When the number of topics increases beyond the maximum number of topics that can be processed by 1 server, the Monitor below is responsible for creating a new server.

Server

This service is composed of two main parts

Server.py

A http server :

  • launch a detection.py process whenever it receives a request with the corresponding topic name
  • store the launched topics on a database and update the load=number−of−topicNload = \frac{number-of-topic}{N}load=Nnumber−of−topic​﻿ where NNN﻿ is an environment variable and 10 by default. The Monitor uses this field to decide whether to add a new LAD server.
  • when it restarts, it reads the data stored in the database and relaunches a detection.py process for each topic

Detection.py

Below are the steps for Detection module:

  1. Read stashed topic from kafka
  1. Aggregate the topic into batches of 1 minutes
  1. At the processing step, send data to Drain service to get the templates
  1. Drain sync with Database if new template
  1. Drain write to Database if new template
  1. Processing module get templates from Drain
  1. Processing send request to Sentiment server
  1. Processing get the sentiment scores from Sentiment server
  1. Processing send request to Rarity server
  1. Processing get the rarity score from Rarity server
  1. Processing send templates to Kafka
  1. Processing send processed messages to Models module
  1. Models sync from Database logfrequency state
  1. Models write to Database if change in logfrequency state
  1. Models send mllog topic to kafka

Client

This is a lightweight service responsible for activating LAD server with topics :

  • consumes log-activator to collect the topic names
  • check if the topics belong to the right infra-id
  • checks if the topics were already treated
  • if the above conditions are met, it chooses the server with the minimum load and sends the appropriate request

Monitor

The monitor service is useful when all the LAD servers are overloaded (load>1load>1load>1﻿)

It checks every N seconds the load on all the servers. If all of them are overloaded, it will send a message to Kafka that will trigger an argo pipeline to create a new lad-server.

LAD Models

LAD uses multiple number of AD algorithms to achieve a good detection. These models and algorithms are theoretically described mainly here.

The diagram above shows how LAD calls the different algos. As described, many algos are accessible directly through code level, the others are accessible via http request to servers.

The models are also different in terms of learning. Some of them are online, which means they learn continuously. The others need to be trained before they are used as explained here.

Note: the isAnomaly and anomalyScore fields are required in the output message the for all LAD algorithms

LogFrequency (Online)

Detects a change in the number of logs.

  • input : number of logs
  • processing : apply anomaly detection on the time series of the number of logs
  • output : True if the number is anomalous, False otherwise

Sara (Online)

Detects logs with negative sentiment (error, critical, failed, ... )

The algorithm is described here.

  • input : a list of contents
  • processing:
    • clean the logs
    • compute the rareness of the logs
    • get the sentiment of each log by querying the http sentiment server
    • average the two score
  • output : if average score is larger than threshold = 0.5, raise an anomaly

Template Extraction (Offline)

The template extraction is based on Drain , its benefits are :

  • Compress logs
  • Provide features for some ML models
  • Could be displayed in dashboards for the clients
  • Detect new log patterns (OOL)

  • input : log content
  • output : log template

LogCluster

Detect abnormal group of templates

Theoretical details about the model are here

  • input : list of templates
  • output: whether a list is anomalous

DeepLog

Detect anomalies in the sequence of logs

Theoretical details about the model are here

  • input : a list of templates
  • output : an anomaly on the sequence of the logs and its explanation

Log Patterns Alerting

Detect drift and presence in log patterns

  • input: log counts
  • output:
    • Presence: anomaly if log count is not equal to zero
    • Drift: drift detected based on LevelShift algorithm
