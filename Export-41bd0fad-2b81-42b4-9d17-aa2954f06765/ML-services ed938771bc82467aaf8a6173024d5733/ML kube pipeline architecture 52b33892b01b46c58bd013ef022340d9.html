1.model serving prediction api call from mad/lad

mad/lad check metatdata in db, and use its incoming topic to get INFERENCE_SERVICE and svc from metadata to construct endpoint to get prediction from model server inference service.

2. initial model servers creation

once topic models are ready on S3, we can send one message contains a list of topic to kafka, argo pipeline will trigger a model server, and each model server will load its corresponding list of topic models from S3 and serve them as inference service, and update modelserver endpoint svc for db metadata

3. new model rolling update

once same topic models are renewed by training pipeline and updated on S3,

two solutions:

  1. solution1

we can send s message contains a list of topic to kafka and indicate a key as 'roll', argo pipeline will trigger a new model server, and each model server will load its corresponding list of topic models from S3 and serve them as inference service, and update modelserver endpoint svc for db metadata, then we should wait 3 mins to manually delete the old modelserver for these topics.

The http service is always available for lad during this rolling update.

2. solution2

since each modelserver is deployment, we can use kube deployment's rolling update, like

kubectl scale deployment $name —replicas=0 -n argo-events

kubectl scale deployment $name —replicas=1 -n argo-events

or

kubectl edit deployment $name -n argo-events, then add or modify some useless environment varibale to trigger rolling update

but this rolling update way will have some service not availbale issue, espcially when the topics are many, and during rolling update, before topics are download and load to memory, it takes 1s*number_topics time before the service is available

4. training pipeline scheduling(need to be discussed with ML members)

training scheduling script should launch job for each topic to get training data and training and push model to S3 under its topic folder, then job should be finished and deleted

for a bunch of new topics, once training data is accumulated enough, after training models pushed to S3, should also push related info(unique model server name, list of topics, loaded as False) to db metadata

5. MAD, LAD

solution A.

argo create one statefulset(pod) for one topic

disavantage: too many pods, and one node can maximum take 57 pods, even the resource is much available

solution B. (current used in prod by valentine)

client, server mode, client detect each topic and send it to existing statefulset server,

another component called 'monitor' will monitor the topic load for each server, and decide to create new server

avantage: one server can hold much more number of topic

Some tech details and decision for lad clien-server solution:

  1. update new topic for a server to DB for each topic message, because server restart can happen at anytime, if in db, one server don't have its compet topics, then it will lost this topic when restart
    1. should not be done inside of one topic process of one server, because the processes is executed in parallel, and erase for each other if they both apply to same server mongo document
    1. Can be done in lad client side
    1. can be done in server api side, this is what i choose
    1. server once restart(can be on another node), should load its complet topics from db
  1. restart topics for a server , when the server is restarted
    1. get topics from db, and launch topic process asychronised way or use request.post to localhost inside of api.py
  1. lad client should avoid duplicate topic because of different error or rolling update
    1. if consumer error happens before post, then it will take the topic again, if happen between post and commit, then it will not taken into account, because we have available_topics to filter(normal it is supposed to be executed just after the post), if error happens after commit, then everything is ok
    1. if it is the cluster or human operation cause the client deployment total failed (i think happens ) or rolling update client deployment, then restart,

      if this(error or rolling termination) happens before post, then it is ok,

      if between post and commit, then the topic should be updated to db by lad server, and when you restart deployment, you can get this topic from db and update it to available_topic, then the topic will be avoid to be duplicate process

      (for this case, if you implement the topic updating_to_server in client side, you have to do it just after post method, but still have risk,if error happens just between post and this method)

      if happens after commit, then everything is ok

    1. lad client only read data from db, only lad server can write to db, to assure db table no overwritten risk

Data storage

objective: it is best to have a shard storage across different node in different AZ, in this case, if our pod restart on another node, it can still get its previous data from its shared storage

potential solution:

  1. mount using hostpath:

data is stored in node level, so if a pod restart from another node, then it will not access its previous data

according to kube doc, it is not recommended to use in production environment

2. mount from ebs volume:

There are some restrictions when using an awsElasticBlockStore volume:

  • the nodes on which pods are running must be AWS EC2 instances
  • those instances need to be in the same region and availability zone as the EBS volume
  • EBS only supports a single EC2 instance mounting a volume

so it means one volume can support only one node, if a pod restart from another node, then it will not access its previous volume, in this case, i don't see the advantage of using ebs compared with hostpath

3. S3:

here we use S3 to back our data, and if a pod restart from another node, and it can't find its previous data, it will download previous data from S3, then start from that data offset

upload and download detector pickle file(contains 22490 points,1000metrics), both take about 2.9s, from memory write to disk take 1s, load from disk take 0.24 s

current solution taken: use hostpath to share data for all pods of same node, if pod restart from another node, and it can't find its previous data, it will download previous data from S3, then start from that data offset

MAD LAD Kafka review

client level consume from metric-activator and log-activator, it is more critical, because each lost or duplicate message means lost or duplication of one component processing

For kube lad:

client: group_id=lad, enable_auto_commit=False, auto_offset_reset="earliest"

Then manually commit with a avaiblble_topic, so even rolling update, it will start from offset, and the list avaiblble_topic can assure to skip duplicate message

Server: it is same kafka conf, so even with rolling update, server topic process start from previous offset, and in order to receive its topic name, in api.py, there is step to get topics from db

For kube mad(one topic one pod ):

client side is controlled by argo, for worker side, each pod receive topicname during pod creation, if we do rolling update the pod(statefulset), the new pod still keep the topic name, so it can continue running, and start from the latest offset

in term of consumer groupid, since our topic process consume its own topic, so in topic level, different topic consumer's target is already separated, so it doesn't matter if different topic consumer process use same groupid or not, even with groupid=None(it will use default group.id=test-consumer-group).

Comparison between above offline model serving design and other model solution

other model solution:

  1. each topic process, once got kafka message, it try to fetch its own topic models parameters from S3, if exist new one, it download to disk, and then load model to memory.

    once a new model parameters arrives, it also need to delete old model in memory

    I think all these operations together takes time, because we now have gale, logcluster, deeplog, and it is not very scalable if we have more models in future. and in future, we can have one model to server multiple topic case, in this case, the two topic should have same model in their own process memory

    and put deeplearning model in same memory with online processing part, i think it is risky, if have memory leak issue, then the online part failed, client can't get any response.

above offline model serving design don't have above time issue, because before the new model is totally up, online part can still use old model, and once the new model is ready, it can switch without any delay, and separate offline model including deeplearning model with online part as a new microservice, i think it is less coupled and safer.

And it is scalable and flexible for future models: more models or one model for multiple topic etc

all new implement on model side can be done in this microservice without impact on online microservice which directly relate to reponse to client
