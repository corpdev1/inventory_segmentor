Written by @Khmayes Abouda

Intro:

Template extraction algo.

Template (aka log event) = constant part of a log message.

Task:

Given a list of logs, output their corresponding templates/events.

Main idea (based on empirical yet debatable assumptions):

Assumptions:

  • All logs of the same template must have the same (token*) length.
  • All logs of the same template must start with the same token.

Based on that, the idea behind Drain is to group logs of the same length AND that start with the same token.

How?

The main idea is to organize log messages in a tree structure. According to some rules that will be detailed later, logs are divided into log groups while traversing the leaf nodes. Therefore, one leaf node represents one log group (and also one log event). Internal nodes represent decision rules to follow in the search process.

After encountering a list of log groups (via traversing internal nodes), a template is assigned to a new log message by choosing the most suitable log group.

In the following sections, for simplicity reasons we confuse these terms (log group = log event = template).

Algo steps:

1- Preprocessing step:

Before looking at the tree, Drain simplifies raw logs by eliminating unnecessary tokens. This is done by user predefined regular expressions. Eg: IP addresses, file paths, etc ...

2- Tree search:

Notations: we define an n-th layer node as a node whose depth is n

This step contains two substeps:

  1. Search by log message length (built on the assumption that all logs of the same template must have the same (token*) length): 1-st layer nodes divide logs based on their lengths. Eg: for "Receive from node 4", we go from the root to the internal node "Length 4".
  1. Search by preceding tokens (built on the assumption that all logs of the same template must start with the same token): n-th layer nodes with n > 1 divide logs of different tokens in the beginning positions of the log message (2nd layer → first token, 3rd layer → second token, and so on ...). Eg: for "Receive from node 4", we go from "Length 4" to "Receiving", then from "Receiving" to "From".

    *As a detail, the number of layers that encode the first tokens in the log message is (depth−2)(depth-2)(depth−2)﻿. Therefore, we traverse (depth−2)(depth-2)(depth−2)﻿ the internal node in this step.

Note: For logs starting with an alphanumerical/digits a special internal node (wildcard <*>) is defined to avoid branch explosion. Eg: "120 bytes received" will fall under that internal node.

4-Update tree (only if no match has been found):

In this case, a new log group is created, with the log message as log event. If it does not already exist, a 1-st layer node of its length is created, a 2-nd layer node of its first token and a wildcard * node in the 3-rd layer.

Model parameters:

  • maxChild: max number of children per node → Avoid branch exploding
  • depth: Tree depth
  • similarity_threshold: parameter to validate candidate template.

Conclusion, Pros/Cons

Pros: Compution speed

Organizing logs in a tree structure means a fast search, ie, instead of comparing a new log to all discovered templates one by one, the tree fastens and guides the search by the rules defined in its internal nodes.

Cons:

  • Strong assumptions → Weak generalization power → Potential bad performance on some types of logs/templates.

  • Other potential problems
    • All the logs start with a different token (→ 2nd assumption is not satisfied)
    • Logs that have no whitespace (→ Viewed by drain as a single token)
