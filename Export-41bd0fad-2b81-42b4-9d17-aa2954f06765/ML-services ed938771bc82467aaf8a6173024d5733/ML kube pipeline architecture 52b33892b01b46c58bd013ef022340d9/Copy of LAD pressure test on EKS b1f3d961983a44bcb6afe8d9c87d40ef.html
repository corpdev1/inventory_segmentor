Goals

  • Test model serving delay for inference
  • Test rolling update of Model Server
  • Estimate the ressources consumption for LAD

Context

  • The aggregator is included in LAD
  • The training is not taken into account since it will be on a different environment
  • Logcluster Model for each topic is served on one kub's deployment, ready to be called by LAD

Data

  • Created a data generator based on apache access logs : https://gitlab.packetai.co/marwen/log-client-generator
  • The generated log patterns where created by : https://pypi.org/project/log-generator/
  • The code is flexible in terms of :
    • Number of topics
    • Number of maximum/minimum number of logs per minute
    • Number of clients
    • Number of the generated days
  • Push data to kafka
  • The format follows the format of the aggregator
  • Launch the creation of the topics in parallel

Characteristics

  • Number of topics : 44
  • Number of logs / Minute : 800-1200
  • Duration : 1 Hour
  • General Purpose EC2 Instance : 4CPUs / 16GB
  • 1 Machine can hold 57 POD

Results

Model Server

1 modelserver takes 44 Topic :

  • 711M RAM
  • 1.4 CPU

Maximum Topics : we can create any number of modelserver, each modelserver support any number of topics.

Rolling update

First Solution : Kube Deployment Native Rolling Update

50 seconds to download 44 Models sequentially from S3 and load them to memory

The service is not available during this time

Second Solution :

Create new Deployment with new endpoint for each rolling update and delete the old one

Can keep the old Modelserver alive about 3 mins to wait for the update

solution: kube's deployment rolling update

Rolling update takes : 50 seconds to download 44 Models sequentially from S3 and load them to memory

Note : the service is not available during this time

there is 50s when the model is loading topic from S3, during this period, the model serving service is not available

Based on test result, choose another safe solution which generate a new modelserver and then switch endpoint in DB, and keep the old modelserver alive about 3 mins(in case some lad topic process can have time to update the new endpoint)

LAD

First Solution : 1 POD takes 1 Topic Argo detect each topic message in log-activator, and then trigger each one LAD pod to handle the process

  • 70-80M RAM
  • 15-20M cpu
  • Maximum POD/Topics : 57

Second Solution : Topic Dispatch Solution LAD Client + LAD Server : LAD Client dispatch topic to different LAD servers based on actual pressure

  • 2.7GB RAM
  • 280m CPU
  • Maximum Topics : >> 57
