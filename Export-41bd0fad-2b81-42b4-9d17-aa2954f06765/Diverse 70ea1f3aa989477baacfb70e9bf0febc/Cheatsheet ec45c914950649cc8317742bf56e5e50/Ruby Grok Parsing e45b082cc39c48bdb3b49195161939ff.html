Ruby Grok Parsing

Prerequisites

Logstash runtime version: JRuby 9.2.13.0

Equivalent for local dev: Ruby 2.5 or Ruby 2.6.10

Advantage of jruby: real multi thread with GIL, so the concurrency is a bit better than the native ruby

Dev Guide

Dependencies

# Code Repository File Structure
logstash
|_conf_gen_ruby
|_conf_fb

conf_gen_ruby folder contains the code to generate the groks.

There is a Gemfile which contains all the dependency we need to develop the lib.

Run following command to install dependencies

# install dependencies using ruby
bundle install
# install dependencies using jruby, I do not know how to install all so I do it one by one, check the gem file for the lib name and version
jruby -S gem install LIB_NAME -v VERSION

Usage

Copy the folder into the target pipeline’s folder and then require_relative to include the lib into the original code we need.

# Dockerfile fb_Dockerfile
# ...other lines
COPY ./conf_fb /etc/logstash_tmp/conf_fb
COPY ./conf_gen_ruby /etc/logstash_tmp/conf_fb/conf_gen_ruby
# ...other lines

# RUBY file filter_fb.rb
# ... some other imports
require_relative 'conf_gen_ruby/config_loader'

def filter(event)
# ... some other code

# for the moment we force the infra id and component id as the unique key combination. we will change it later to be more dynamic
run_grok(event, event.get("[@metadata][infraID]"))
# ... some other code
end

Once we use this lib, we could totally remove the dependency of the conf gen and use the new conf without any grok inside

GrokBot API Integration

In order to use grokbot api integration, need to set env var 

GROK_LOADER=grokbot

There is three steps to generate the groks

  1. load the grok config using grok_config_fetcher.rb GrokConfigFetcher is a http client wrapper to do grok update by interval. It is used when GrokLoader ’s source is configured as http It will do sha1 to check if the content is changed comparing to the previous fetch, and then do update if changed. Env Var Used:
    GROK_FETCH_INTERVAL: update check interval by second, by default is 30
API_ENDPOINT: endpoint of grok api, default is 'https://grokapi.packetai.co/groks'
# Query params used in api
CLIENT_NAME: the packetai deployed cluster name, like metron, gcpstage etc
INFRASTRUCTURE_ID: infra id 
CLUSTER_NAME: client's cluster name sent from their log data
AGENT_ID: agent id
# Auth token
TOKEN: X_INTERNAL_TOKEN used for auth
  1. build the grok hash map using grok_loader.rb GrokLoader is Singleton. When it is firstly initialized, it will try to load the groks config from either local file or remote server. Then it will build the grok hash map with the unique key generated by the infraid and componentid. When building the grok, it will use the lib from logstash/filters/grok which is the same as we used in the real logstash. The lib is installed from 'logstash-lib', '1.3.2' Env Var used: GROK_SOURCE : could be file or http GROK_FILTERS_PATH : used when GROK_SOURCE is configured as file
    # example code when generate the grok£
grok = LogStash::Filters::Grok.new(
    "patterns_dir" => ["/etc/logstash-patterns"],
    "match" => { "message" => job['config']['groks'] },
    "overwrite" => [ "[grok_parsed_msg][content]" ],
)
grok.register
  1. run the grok detection using config_loader.rb ConfigLoader basically init a GrokLoader .

How to build the grok wizard hash tree

The example show the logic when building the groks hash map.

The following data contains infra1's two groks with two totally different filters.

Filters are key values pairs. Key is based on the log lines’ flatten field name. Values is an array of distinct value.

All the key values pairs in the filters object will be used to build a unique entry for the grok.

Any log line who has the specific fields and contains the value described in the values array would match the grok entry.

[
 {
    "groks": {
      "groks": [
        "%{GREEDYDATA:content}"
      ]
    },
    "infrastructureId": "infra1",
    "filters": {
      "topic": ["v1"],
      "host": ["v2"]
    }
  },
  {
    "groks": {
      "groks": [
        "%{NUMBER:content}"
      ]
    },
    "infrastructureId": "infra1",
    "filters": {
      "appName": ["v3"],
      "namespace": ["v4"]
    }
  },
]

Some technical details about how we build the tree:

There are two trees used for the grok wizard integration.

First tree is the key map tree, basically we will analyse all the config’s filters and generate all the possible entry which is used to identify the unique component in order to apply the groks.

e.g. when we use the grok config above, there are two entries:

{
	"topic-host": ["topic", "host"],
  "appName-namespace": ["appName", "namespace"]
}

Then we will try to analyse if the log line contains those fields per entries and try to find the corresponding grok config inside the grok tree.

A grok tree is a simple key value hash map.

Key in the grok tree is built based on the filter’s field & value and joined by “-”

example of the key. topic:v1-host:v2

appName:v3-namespace:v4

For the moment we fix the values array’s length to be exactly one.

Later we will support multiple values in the value array, so it will result in multiple entried for a grok if the values contains multiple values.

e.g. the following example will generate four entries

{
  "filters": {
		"f1": ["v1", "v2"],
    "f2": ["v1", "v2"]

  }
}

// f1:v1-f2:v1, f1:v1-f2:v2, f1:v2-f2:v1, f2:v2-f2:v2
