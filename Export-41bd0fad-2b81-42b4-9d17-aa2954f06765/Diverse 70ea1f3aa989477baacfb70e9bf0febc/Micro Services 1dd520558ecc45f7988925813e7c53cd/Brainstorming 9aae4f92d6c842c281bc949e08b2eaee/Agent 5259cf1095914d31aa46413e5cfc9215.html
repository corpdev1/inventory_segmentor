Agent

Problems

  • Too difficult to manage the beats configuration (yaml) at Agent
    • too big yaml configuration.
  • Debugging is too difficult
    • Is the generated beats configuration correct ?
  • Health check
  • Restart of the agent
  • Data separation at the agent
  • collect agent/beats configurations
  • Agent crashed report
  • Beats logs are not being sent yet to us.
    • we have only our agent logs available at /etc/packetai/log/agent.log
    • no mechanism to recover from agent crashing
  • Agent configurations is too big
  • Agent source code is too big to manage beats config
  • It's not possible to multiple process of same name.
    • ex: multiple python process, multiple php process
    • for each process they should inject some environment variables, something similar to Dynatrace
    • It's low priority
    - module: system
  metricsets: ["process"]
  processes: ['python']
  process.cgroups.enabled: false
  processors:
  - add_fields:
      fields:
        componentID: packetai123456789
      target: fields
  • How to simplify Agent integrations ?
  • Integration message results in restart of all the beats on all hosts.
    • How to minimise the Restart of beats ?
  • How to solve module.event on agent ?
  • Routing Kafka topics
  • Global Configuration of beats?

Solutions:

  • Too difficult to manage the beats configuration (yaml) at Agent
    • We have other configurations for non logical components. Generally they are located at /etc/packetai/filebeat/modules.d/*.yml or /etc/packetai/metricbeat/modules.d/*.yml
    • Monitor all docker containers by default.
    • Write all the data to one topic
      • Data separation can be done at Backend side
    • If we do data separation at Agent, we must use either Labels (for Logical components) for Docker based, we could also use component ID (we must add this componentId for each module we enable).
    • What should we do about languages ?
      • find a way to monitor a process.
