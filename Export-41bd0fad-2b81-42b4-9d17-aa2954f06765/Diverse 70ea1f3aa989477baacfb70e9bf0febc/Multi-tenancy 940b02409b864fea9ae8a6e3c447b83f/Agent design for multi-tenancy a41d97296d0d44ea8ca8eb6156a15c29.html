Several of our other micro services are designed to work with multi tenancy. check below page:

Current workflow (single tenancy)

  • During our agent installation we download kafka client certificates and store them at /etc/packetai/certs folder on client VM
  • the current workflow of the agent is as follows
    • beats writes to Kafka directly: beats writes to several kafka topics based on component id. i.e. writing several topics: infraid-agent-log-componentid-raw and infraid-agent-metric-coponentid-raw
    • process exporter writes to kafka topic: infraid-procs
    • actions-listens listens to kafka topic: infraid-actions
    • heartbeat is sent to becky via HTTP endpoint

New workflow for multi tenancy

  • In the new workflow beats(filebeat,metricbeat) writes to HTTP endpoint (Agent-Ingester) with auth token , which then writes to Kafka topic
    • Agent-router can separate to several topics(based on components) for ML algosa
  • Process exporter write to HTTP endpoint(Agent-Ingester) with Authentication token, which inturn writes to Kafka topic
  • action listener queries HTTP endpoint periodically for Latest actions, which will query DB(mongor or postgresql) for latest actions to be sent to the agent

Another workflow with Kafka exposing to Internet

In this workflow we expose kafka to internet, it's somewhat similar to single tenant workflow

On Agent side most of the workflow remains the same. However the workflow will be changed at becky side(red lines).

  • when the user sign-up, we need to create client certificates to this user.
    • After generating these certificates we need to upload them to s3 bucket.
  • We need to apply ACL to kafka. which controls which kafka topics user can create and which kafka topics users can write to: check this page for more details (https://docs.confluent.io/platform/current/kafka/authorization.html)
  • One additional step that is required, during the client installation we download the correct kafka certificates that belong to the user on becky side( we need to implement this)

drawbacks:

  • Kafka exposed to internet, it's easy to create several kafka topics, which could overwhelm the Kafka server and distrupt the whole service. which includes other tenants on this kafka
  • Kafka is prone to DDoS attack, which could impact all the tenants.
  • Handling Kafka client certificates are hard. How to disable 1 client certificate ? all the issues related to certificates needs to be handled

Rolling plan
