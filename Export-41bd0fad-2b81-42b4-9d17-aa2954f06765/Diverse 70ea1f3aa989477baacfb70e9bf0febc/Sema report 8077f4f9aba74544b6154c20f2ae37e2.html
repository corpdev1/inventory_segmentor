Code Quality

  1. The organization’s total line count is in the 14th percentile of all organizations Sema has analyzed until now. The organization has no repositories that exceed Sema’s benchmark for a large repository (within the top 5% in all the repositories analyzed by Sema). Large repositories are often candidates for refactoring, but other repositories could be, too. Are any refactorings planned or underway? If they are, how much work is left to do?

  1. Testing
    • The scan estimates Code Owner’s unit testing coverage to be 47%. What does Code Owner believe the unit testing to be?
      • We have discussed this with Centreon
    • Sema identified test code within 1 repository as files with “test” in its name. Does this represent the organization’s approach to automated testing to mitigate this finding?
      • Yes almost all the files will contain test in their names. for example for golang the test files will be named as*_test.go
      • All python tests have a prefix test_*.py
    • Does the organization use In-code unit testing, higher-level automated testing (Selenium, Cucumber, etc.), manual testing, user acceptance testing, or any other testing methodology?
      • We use Unit testing, Integration testing. We also use Selenium to do end2end tests. The general workflow as follows: 1) PR is created, Unit tests are run automatically 2) PR is peer reviewed and approved 4) PR is merged to dev branch 5) Once merged, unit tests are run automatically, and runs the acceptance or end-2-end tests using github actions.
    • Are there any business reasons to not invest in automated test coverage, such as business prioritization, absence of customer issues, etc.? What is your overall philosophy regarding overall testing, including unit testing, integration testing, automated testing, and acceptance testing?
      • We do have automated test coverage. Our overall philosophy is to continuously test new features (acceptance, unit and integration) and make sure there are no regressions on the overall product, especially on the ML side (end to end testing)
  1. Is a line-level scanning tool such as SonarQube in place? This is recommended for companies with >100 current developers or when third-party development shops are used, for the development team.
    • we have Sonarcloud, Dependabot and Snyk. We also run Sysdig to align with one of our large clients
  1. 107 instances of 54 technologies were identified, including two versions of jQuery. Is there a process in place to regularly catalogue and assess technologies, including potential upgrades? Does the Code Owner have any evidence that engineering effectiveness, product security or user experience is affected by the multiple versions of software products?
    • This is a valid tech debt point. Since we work on microservices in independent folders, over time, versions diverge. At our scale we are not significantly affected by the multiple instances/versions of the same technology. Hence, we didn’t yet put in place a process to catalogue technologies and tools. This might come as we scale up.
    • However, we think that it is a good time to start a process to assess technologies security-wise. Today, this is done ad-hoc by subscribing to CVE feeds and some important repos such as Opensearch repo (to keep track of issues).
