Template Indexer - ES update / performance test

Objective

Update ES index doc with one or two new fields by search on logID

Theory

Test1: local python process to search, insert, update 1000 production message on one index-61fbaa1b269bb800140dd629-affluences-log-kubernetes-2022.03.30 (it has about more than 1 million logs )on staging ES

Time\msg=500msg=1000msg=1500msg=2000msg=4000comment
sequential search30sfor dependant queries - not applicable in our case
sequential in place update by query101s
sequential search+insert to new index100s
sequential partial update 71s
sequential search+ one bulk insert whole doc to new index36s
sequential search+ one bulk update on original index36s
async search4s8.389s16.499s
async search + partial update (our production)10s17s
async search + one bulk insert whole doc to new index 2.580s5.2047s7.328s10.40319.696s
async search + one parallel bulk insert whole doc to new index 2.139s4.231s6.195s8.348s16.483s
async search + one bulk update on original index (default bulk update)2.356s5s7.907s10s19.365s
async search + one parallel bulk update on original index2.191s4.368s6.227s8.518s16.621

From above, we can see `async search + one parallel bulk update/insert on original index` is the best choice and it is search take time, bulk update/insert take very little time

another solution: template indexer don’t do search, it only insert (log_id, template_id, componentID) to a new index `template` , then it is frontend should query this index and original index to associate the two driven by on-demand,

actually in order to show the page `patterns`, front only need to query this new index `template` to know the log numbers for each template_id

note:

  1. async partial update is the current version 1.1.1 on production
  1. production speed is faster than my local to staging env speed

Update @April 8, 2022

  • The symptom of issue is large lag on ES template-indexing
  • the lag is mainly coming from refresh and write queues
  • higher refresh intervals would not necessarily improve the perf as it enlarges queue impacting writing capacity of logstash
  • The reason is: unbalance of load across cluster: one node is struggling and impacting overall perf
  • the reason of unbalance is: ES does not balance load but only balances shard numbers

Solution

  1. create 2 new nodes
  1. wait for load to rebalance
  1. remove struggling node
  1. rebalance manually across remaining nodes
