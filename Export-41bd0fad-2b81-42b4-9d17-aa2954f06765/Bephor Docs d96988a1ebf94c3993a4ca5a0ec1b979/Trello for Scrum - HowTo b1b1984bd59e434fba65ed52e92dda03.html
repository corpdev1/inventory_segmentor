Trello for Scrum - HowTo

Last Edited Time@July 20, 2020 2:04 PM

A list of points that should be respected when using Trello as a Scrum agile tool.

  • Someone to check that everybody uses Trello correctly - Weekly/Monthly Sprint Leader
    • this someone could initially be the same person for the first month, so that he/she makes sure everybody understands what has to be done
    • from the second month, everybody could be the Scrum Master for one week following a rotation mechanism. This way everybody experiences what it means to handle the board and should feel more prone to maintain it
    • every task should have (at least) a person associated with it
    • every Monday the previous sprint should be closed, a new one created and the reasons why tasks from the previous sprint are still not completed should be understood and addressed
    • every sprint should be reasonably achievable
    • epics should have a name so that tasks can be associated with the correct epic and it is clear what they are about (atm we only have an "epic" tag there, which means nothing except is part of a bigger task, but which one?)
    • every task should have a description. Typically every task should be associated with an epic and should be treated as a story, which means it should briefly and not too technically describe what the purpose of that task is and what it aims to achieve for the client
  • every time someone changes something, a ticket has to be updated. We should be able to follow the story of a task just by reading it on Trello. Every problem and every solution.
  • every day the standup should be done with the Trello board in front
  • every Monday there should be a meeting to decide tasks for each team. It may last at least 1 hour but at the end a list of tasks for each team for the new sprint should be defined
    • once defined, a sprint should not be changed except for extraordinary circumstances. This means that no new task should be added or removed, and whatever comes up within the sprint (e.g. a new bug) should be addresses in the next sprint
  • every Friday evening the board should be perfectly ready for next Monday
  • tech debt can be left there for now, but it should be reordered by importance.
    • at the beginning of each new quarter, we should get back on this list and understand what can be put into this quarter
    • maybe even checking these elements at the Monday meeting?
  • how to link Tasks with product Objectives?
    • maybe we could give them a label referring to the objective (eg. DevObjective4)?
  • Each OKR subtask as an epic, with the objective assigned as a label
    • one task following each epic and then subtasks with that major task assigned
  • Objective lists are to be considered as belonging to a quarter, hence they are not going to be moved until the end of the quarter. On the other hand sprints, once done, can be moved to another board
  • The definition of "DONE" is that a ticket is completed and validated/tested
