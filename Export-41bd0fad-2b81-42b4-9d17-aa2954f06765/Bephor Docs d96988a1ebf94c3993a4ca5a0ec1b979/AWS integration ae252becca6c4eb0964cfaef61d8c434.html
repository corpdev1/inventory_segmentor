Data collection

  • using metricbeat as an independent agent with Emma, called AWS service
  • as first iteration, we consider AWS as an infra , in the future, we will consider a region as infra
  • user enters his AWS credentials on Minima and activates AWS monitoring; for logs it downloads and activates the PacketAI lambda function file
  • the credentials are sent to the aws service which activates the metricbeat AWS module
  • the AWS service gathers data and sends it to the rest of the regular pipeline
  • this data will follow the usual pipelines: insight pipeline directly to Elasticsearch and the ML pipeline to ML models

Data pipelines

  • AWS is treated as an infra
  • most aws metricsets are treated as components
  • each component (RDS, S3...) has only one metricsets and the AWS data center component has multiple general metricsets
  • the topic names corresponding to these components are named as follows:
    • {infraID}-cloud-s3-raw
    • {infraID}-cloud-rds-raw
    • {infraID}-cloud-rds-overview-raw (maybe?)

Data representation (topology)

DataCenter:

  • AWS is a separate data center node

Network:

  • AWS load balancers are network equipment nodes
  • If there are no network components(load balancers) for hosts we show a virtual network node

Host:

  • If the end service (RDS, S3...) doesn't have a host we show a virtual host node
  • If the host with an installed PacketAI agent is an EC2 instance it is linked to it's AWS load balancer or to a virtual network node

Process:

  • Processes are virtual nodes (managed by AWS)

Service:

  • Managed services (RDS, S3, EBS...) are represented as nodes

Logs with PacketAI Lambda(not completely built yet):

  • User can use the generic PacketAI lambda function to monitor any CloudWatch logs by choosing the targeted log group when activating the trigger
  • Every lambda targets the same ingest endpoint (ingest.packetai.co/{infrastructureId}/aws/events/logs) but each message contains it's individual log group info
  • The ingest service separates the messages based on the log group to individual component pipes (RDS ⇒ RDS component, EKS ⇒ EKS component...)
  • Master topology service recognizes (or gets info) that these components now exist and creates their nodes

Issues:

  • AWS data center metrics/logs coming from multiple pipes(how to handle ML?)
  • Connecting EC2 host components to the AWS data center(or ELB) component
  • Most metricsets use grouped data by technology which is not ideal for ML and should be separated
  • AWS deactivation is read on Becky/Minima and the AWS service but has not been tested
  • No way of activating/deactivating individual AWS service metricsets on Becky/Minima/AWS service/MT

Competition:

*Metricbeat and Filebeat version used: v7.2

ELB:

Option with grouped data and 1 ELB service component:

  • Metricbeat elb dashboard
  • Filebeat elb fileset dashboard
  • Easy to implement in a relatively short time as it extends the current AWS service logic
  • Bad for ML as data is grouped in one pipeline/index

Option with separate data and 1 ELB network component per load balancer:

  • Separate metric/filebeat messages based on a unique identifier into individual components for each ELB
  • Metricbeat ELB metric/fileset doesn't seem to have such a field in exported fields(metricbeat, filebeat)

Data collection(OLD version)

  • using metricbeat as an independent agent with Emma, called aws service
  • as first iteration, we consider aws as an infra , in the future, we will consider a region as infra
  • John will discover that the current instance belongs to a aws env
  • john notifies this info to the aws service in Emma
  • Emma passes the notification to becky/minima
  • a notification is shown to the user
  • if user checks aws monitoring, the action is passed to the aws service in Emma
  • the aws service will start pulling aws data through API
  • this data will follow the usual pipelines: insight pipeline directly to Elasticsearch and the ML pipeline to ML models
