Topology (version 03/2021)

process service:

-We only support processes with known technology (aka services) or responding to a http request (aka applications)

-We can support list of regexes to ignore some applications to be considered as service. Or we can ignore some processes from the topology

-Every applications have a parent service Node. If it does not exist natively as known technology, applications are children of a generic service Node. -We have multiple defined structures to build the topology

  1. Process Node containing a map of Service Nodes
  1. Service Node containing a map of Application Nodes

Every node contains these informations:

  • component ID (container id + command line + open ports)
  • hostname
  • pid
  • parent pid
  • command line
  • connections
  • container id
  • docker labels
  • is logical (it is a logical component ID ?)
  • logical component id (if exists)
  • technology
  • language

topology service

-We defined 2 types of adhoc nodes in the topology service: Host nodes, and net Nodes. Theses nodes are built only to complete the graph of the topology and containing the list

of applications and integrations.

-The topology service listen kafka topic from process service to get the same data structure built in.

-The topology service listen kafka topics about cloud informations like rds/elb.

-The topology service merge the graph cross agents for the same infra.

-The topology service translate topololgy data structure into format for becky/monodb

3. Running the Topology Service

Available flags :

  • debug : Enable debug mode. Disable MongoDB and write the topology in a JSON file located in ./data/.
  • v : Enable verbose mode
  • infraFilter : Run the microservice for a list of infrastructure. Every infrastructure asked should be separated by a comma in the flag. (ex: topologyservice -infraFilter=infraid1,infraid2 )
  • conf : Prints the table of technologies for the hard discovery

Available environnement variables :

Required :

  • APIDEVURL : API's URL
  • MONGO_CLUSTER : Address of the MongoDB server. If multiple addresses are provided, they must be separated by a comma.
  • MONGO_SOURCE : Database name used for authentification
  • MONGO_DATABASE : Name of the database used
  • MONGO_USER : Username of the MongoDB database used for the authentication
  • MONGO_PASSWORD : Password of the MongoDB user used for authentication
  • CERTS_PRODUCER_SERVER_CER : Server cert for Kafka
  • CERTS_PRODUCER_CLIENT_KEY : Client key cert for Kafka
  • CERTS_PRODUCER_CLIENT_CER : Client cert for Kafka

Optional :

  • MONGO_SSL (bool) : Allows to set SSL flag for the connexion to MongoDB. Set by default to true.

5. Kafka communication

Output topics :

  • %infra%-master-topology : Sends a short message to the dashboard to notify every modification of the topology

Input topics :

  • %infra%-%agent%-network-topology : Receive the network topology from the NetworkTopology
  • %infra%-%agent%-discoprocs : Receive a list of process, with their PID, name, and a list of detected technologies. This topic is used for the soft discovery.
  • %infra%-%agent%-proc-topo : Receive the topology of process generated by the ProcessService. Every node contains the process information and their initial position.
  • %infra%-cloud-nodemap : Receive the list of data from the AWSService to build the AWS topology
