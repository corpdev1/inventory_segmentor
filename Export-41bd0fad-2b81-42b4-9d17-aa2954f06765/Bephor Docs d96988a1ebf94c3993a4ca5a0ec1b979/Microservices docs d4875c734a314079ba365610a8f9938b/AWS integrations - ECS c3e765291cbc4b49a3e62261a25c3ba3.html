1. What is ECS?

ECS is AWS's container orchestration service. It is defined through the following concepts:

  • Task: a collection of one or more docker containers with the same business goal, eg: app with two micorservices
  • ECS container instance: "an Amazon EC2 instance that is running the Amazon ECS container agent and has been registered into an Amazon ECS cluster". Container Instance can run many Tasks, from the same or different Services.
  • The ECS container agent takes care of the communication between ECS and the instance, providing the status of running containers and managing running new ones.
  • Service: a collection of one or more instances of the task, can be across multiple ECS container instances. Each service is assigned a single task definition, and you can specify the number of tasks a service will deploy from that definition and attempt to keep running

ECS Cluster: "An Amazon ECS cluster is a logical grouping of tasks or services. If you are running tasks or services that use the EC2 launch type, a cluster is also a grouping of container instances. If you are using capacity providers, a cluster is also a logical grouping of capacity providers".

  • Amazon ECS handles the logic of scheduling, maintaining, and handling scaling requests to container instances. It also takes away the work of finding the optimal placement of each Task based on CPU and memory needs
  • A Cluster can run many Services. If you have multiple applications as part of your product, you may wish to put several of them on one Cluster. This makes more efficient use of the resources available and minimizes setup time.
  • You can deploy containers by using one of two launch types: Amazon EC2 or Fargate. The EC2 launch type hosts ECS containers on EC2 instances. With Fargate, ECS abstracts away the VMs, letting you focus only on ECS services, tasks, and task definitions

2. ECS Monitoring:

2.1. Datadog

2.1.A. what to monitor?

Two metric categories to watch:

  1. resource metrics, related to infra resources: CPU, memory, I/O, network
  1. status metrics, related to app-level (ECS) status: mainly about task counts in different status
  • CPU
  • Memory
  • I/O
  • Network
  • Status metrics

2.1.B. Previous methods (as mentioned by DD):

  • Cloudwatch
  • AWS CLI
  • 3rd parties: mentioned no one explicitly
  • Tools for docker monitoring

2.1.C. The Datadog way:

"you’ll want to monitor your ECS infrastructure to make sure containers are launched, provisioned, and terminated as expected. You’ll also want to monitor the overall health and performance of your ECS containers and virtual machines"

As it does for all AWS integrations, Datadog collects resource metrics from Cloudwatch and status metrics using ECS API and agent (CloudWatch does not surface metrics for the status of services, tasks, or containers).

step1: activate ECS in the AWS integration module

step2: install DD agent on ECS contianer instances:

  • when fargate is used
  • when EC2 is used

Once ECS integration is activated, a default dashboard is shown on UI

Datadog agent has Autodiscovery feature for containers

With APM, you can instrument containerised apps and see service map on UI

Log collection:

Two ways of collecting logs:

  1. Datadog Agent sends logs directly from ECS containers running in an EC2-based cluster, bypassing CloudWatch Logs (and the additional billing the service entails), while also giving you more configuration options and access to logs from the ECS Container Agent.

    details on how to do it: https://www.datadoghq.com/blog/monitoring-ecs-with-datadog/#sending-ecs-logs-from-your-ec2-instances

  1. The second method works with either launch type, and uses a Lambda function to forward container logs from CloudWatch Logs to Datadog. In Fargate, since you’re restricted to CloudWatch Logs, using this method is the only available option.

    details on how to do it: https://www.datadoghq.com/blog/monitoring-ecs-with-datadog/#using-aws-lambda-to-collect-ecs-logs-from-cloudwatch

2.2. ELK

Current AWS module of metricbeat does not contain an ECS metricset.

https://www.elastic.co/guide/en/beats/metricbeat/current/metricbeat-module-aws.html

ELK does not get any cluster metrics from Cloudwatch nor from ECS API

It is however possible to monitor ECS EC2 instances by installing metricbeat on all of them (src: https://www.elastic.co/blog/how-to-monitor-amazon-ecs-with-elastic-observability)

it is also possible to monitor faregate deployment by using a dockerised metricbeat and defining a task (src: https://www.elastic.co/blog/how-to-monitor-amazon-ecs-with-elastic-observability)

For logs, according to this https://logz.io/blog/amazon-ec2-container-system-ecs-log-analysis-part-2/. Logzio provides a dockerized image of their log shippers to be run in the ECS cluster as a new task. Once the task is running, logs are shipped automatically.

3. Summary of state of the art

Metrics: three ways:

  • AWS API based approach for ECS metrics - Datadog
  • Cloudwatch, incurring charges - Datadog
  • containerised agent for containers metrics through a task definition - Datadog, Dynatrace
  • autodiscovery - Datadog, Dynatrace

Logs: one way

  • containerised agent for containers logs through task definition - Datadog, logzio

  • ELK cloud does not do cluster metrics, neither from API nor from Cloudwatch - but metricbeat ECS module is quite good
  • Dynatrace does not get logs - it gets 6 cluster metrics from cloudwatch API (yes, not ECS API)
  • The most complete tool is DD, details in the notion doc
