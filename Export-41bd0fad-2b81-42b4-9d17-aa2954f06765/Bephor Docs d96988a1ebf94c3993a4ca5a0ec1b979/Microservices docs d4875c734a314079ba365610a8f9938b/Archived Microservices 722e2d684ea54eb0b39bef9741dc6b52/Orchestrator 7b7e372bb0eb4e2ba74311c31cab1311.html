Orchestrator

Hadi's comments

In order to pilot microservices, we need a robust and trustable orchestration. That means that if the system is in fault independent services should be able to react on it, maybe store they current state, for systems that aggregates logs or get metrics it's important that they can change the method from sending data to store-it and realease it when the communication is able to be done again.

MicroServices

Registration

Each microservice register to the orchestrator through the endpoint /register with the following informations

{
	"name": "MicroserviceName",
	"group" "MicroserviceGroup"
	"configurations": {
	  "defaultTask": "task-template-name"
		"minTask": 0,
		"optimalTaskNumber": 2,
		"maxTasks": 5
	}
}

Already implemented in the process microservice

States

Microservices can have in they live cycle can have 4 State:

  • Liveness ( Microservice is launched but not ready to recieve any pipeline or data )
  • Readiness ( Microservce is launched and ready to compute data )
  • Error ( Microservice has produce one or multiple errors but still working )
  • Stop

All miroservices has at least API endpoint to communicate those states they also communicate the changes of they state through an event pipeline named microservice-status.

States (liveness and readiness ...) are stored in mongo

State ticks are sent through kafka messages , instead of directly connecting to an orch API

Identification

Each microservices can be identified by an id that is stored in the orchestrator API. If a service launch and has never had a identifier then this service should call the orchestrator API to get a new identifier and a secret linked to it

Action Pipeline

In order to recieve actions from the orchestrator, microservices has 2 ways to produce an action. First they can have they own API: /process/watch?infrastructure={infraId}&agent={agentId} or recieve via a pipeline named microservices-actions through an event with the corresponding format

{
  "id": "55aze-az5az4eaz-45az4az", // Id de l'action
	"name": "process-all",
	"action": "enable", 
	"group": "process", // Microservice Group
	"parameters": {} // Any Data with an objet | Array | String input
}

Action Pipeline Responses

Each actions can produce multiple response but has to produce a response in order to be track as done.

Failure Case

{
  "id": "55aze-az5az4eaz-5aze54",
	"name": "microservice-metrics",
	"action": "fail",
	"group": "ml",
	"parameters": {} // Any Data that can track the failure
}

Sucess Case

{
	"id": "55aze-az5az4eaz-5aze54",
	"name": "microservice-metrics",
	"name": "sucess",
	"group": "ml",
	"parameters": {
		"duration": 12545,
	} // Any Data that can track the sucess with time 
}

Orchestrator

API

The orchestrator API contains the following endpoints:

  • POST /register
  • POST /release
  • GET | POST | PUT | DELETE /tasks
  • GET | POST | PUT | DELETE /microservices
  • GET | POST | PUT | DELETE /microservices/{group}/tasks
  • GET | POST | PUT | DELETE /microservices/{group}/tasks/{identifier}

WatchGuard

The orchestrator check for every services the /liveness /readiness status of each microservices endpoint every 10 seconds it ensure if one service doesn't respond all tasks and workload assigned to this microservice to be assigned to an another one.

Tasks Handlers
