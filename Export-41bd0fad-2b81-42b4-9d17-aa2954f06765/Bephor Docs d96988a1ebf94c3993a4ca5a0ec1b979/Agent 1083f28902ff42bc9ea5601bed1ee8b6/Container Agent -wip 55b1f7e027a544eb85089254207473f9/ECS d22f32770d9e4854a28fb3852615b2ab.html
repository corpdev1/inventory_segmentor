Implementation (22/03/2021)

dockerized agent

Metricbeat mounted volumes from host:

  • /proc
  • /sys/fs/cgroup

These 2 volumes will be used to gather system informations

  • /var/run/docker.sock

These volume is to be able to communicate with dockerd daemon, to gather informations about containers

Filebeat mounted volumes from host:

  • /var/run/docker.sock
  • /var/lib/docker/containers

The volume will be used to gather logs from containers if they are using stdout as output

Ecs native support (1 step)

The goal is to gather metrics and logs of containers and host running in a ECS cluster.

In order to be able to install the dockerized agent on each host of an ECS cluster, we need to provide:

  • The ecs task definition of the agent. Basically how to create the container and which volumes are mounted.
  • The service definition about how to run the task. The main idea is to run the task defininition of the agent in Daemon set mode.

Agentd documentation

1. How to build image

Here the files need to build the agent: - Dockerfile:

FROM golang:1.16 as builder
WORKDIR /builder/
ADD . /builder/
ARG CERTPATH
ENV CERTPATH=${CERTPATH}
ENV METRICBEAT=metricbeat-7.10.1-linux-x86_64
ENV FILEBEAT=filebeat-7.10.1-linux-x86_64

# COPY KAFKA CERTIFICATES
RUN mkdir -p /etc/packetai/assets/certs/
RUN cp ${CERTPATH}/* /etc/packetai/assets/certs/

RUN curl -L -O https://artifacts.elastic.co/downloads/beats/metricbeat/${METRICBEAT}.tar.gz
RUN tar xzf ${METRICBEAT}.tar.gz -C /etc/packetai
RUN mv /etc/packetai/${METRICBEAT} /etc/packetai/metricbeat
RUN rm ${METRICBEAT}.tar.gz
RUN curl -L -O https://artifacts.elastic.co/downloads/beats/filebeat/${FILEBEAT}.tar.gz
RUN tar xzf ${FILEBEAT}.tar.gz -C /etc/packetai
RUN mv /etc/packetai/${FILEBEAT} /etc/packetai/filebeat
RUN rm ${FILEBEAT}.tar.gz

RUN CGO_ENABLED=0 GOOS=linux go build -mod vendor -tags agentd -o packetai-server ./cmd/agent

FROM debian:stretch
WORKDIR /root
ARG APIDEVURL
ARG PAI_API_KEY
ENV APIDEVURL ${APIDEVURL}
ENV PAI_API_KEY ${PAI_API_KEY}
ENV HOST_PROC /hostfs/proc
ENV HOST_SYS /hostfs/sys
ENV DOCKER_API_VERSION 1.40
COPY --from=builder /builder/packetai-server /root/packetai-server
COPY --from=builder /etc/packetai /etc/packetai
COPY --from=builder /builder/cmd/agent/entrypoint.sh /root/entrypoint.sh


RUN apt-get update && apt-get install -y curl jq vim psmisc
ENTRYPOINT ["./entrypoint.sh"]

Important : We can see in the dockerfile that the agent is built with the tag agentd. This tag must alway be present when building the dockerized agent.

Important: We define 2 env variables which are very important for gopsutil`

  • HOST_PROC=/hostfs/proc
  • HOST_SYS=/hostfs/sys

This 2 env variables have a root directory at /hostfs . This is where we need to mount volumes for proc/system informations

entrypoint.sh:

#!/bin/bash
set -o errexit
set -o nounset
set -o xtrace

# COPY APIDEVURL
if [ ! -f "/etc/packetai/apiurl" ]; then
    echo -n ${APIDEVURL} > /etc/packetai/apiurl
fi
# COPY INFRA
if [ ! -f "/etc/packetai/infra" ]; then
    echo -n ${PAI_API_KEY} > /etc/packetai/infra
fi

INFRA=$(cat /etc/packetai/infra)
if [ ! -f "/etc/packetai/identifier" ]; then
    IDENTIFIER=$(curl -X POST "$APIDEVURL/infrastructure/$INFRA/agent" | jq .agentId)
    IDENTIFIER=${IDENTIFIER%\"}
    IDENTIFIER=${IDENTIFIER#\"}
    echo -n "$IDENTIFIER" > /etc/packetai/identifier
fi
export PATH=$PATH:/etc/packetai/filebeat:/etc/packetai/metricbeat
./packetai-server

The command to run the build of the image: 

docker build \
    -t agentd:latest \
    -f ./cmd/agent/Dockerfile_agentd \
    --build-arg CERTPATH=<pathToCertificates> \
    --build-arg APIDEVURL=<apiDevURL> \
    --build-arg PAI_API_KEY=<PAI_API_KEY> .

We use build arguments to build an image dedicated for a client:

  • CERTPATH: is the path containing the 3 ssl certificates, The certificates will be used by the agent, filebeat and metricbeat configurations:
    • producer.client.cer.pem
    • producer.client.key.pem
    • producer.server.cer.pem
  • APIDEVURL: is the becky end point that the agent queries to get the list of kafka brokers.
  • PAI_API_KEY: is equivalent to the infraID of the client.

2. How to run image

docker run \
    -v /var/run/docker.sock:/var/run/docker.sock \
    -v /proc:/hostfs/proc:ro \
    -v /sys/fs/cgroup:/hostfs/sys/fs/cgroup:ro \
    -v /var/lib/docker/containers:/var/lib/docker/containers:ro \
    -v /var/log:/hostfs/var/log:ro \
    --name packetai agentd:latest

To push the image we need to execute 2 commands: The first one to tag the image with the proper ecr repo.

On the task definition page, you can select a taskdefinition, then click Action and create a service.

  1. Select EC2 launch type
  1. Select a revision number of the task definition
  1. Select the cluster where the service will be deployed
  1. Choose a name for the service
  1. Select Type of service DEAMON
  1. Click Next Step until the service is configured

9 Some important notes

9.1 Default path for host

As we are mounting volumes from the host system, we want to separate host path inside docker from the host running the container. By default we choose to use the root mounting point to /hostf/

9.2 Docker version limitation

For certain AMI aws linux images, the docker daemon have an upper limit for docker api version. For now we setup the docker version by using the env variable inside the container: DOCKER_API_VERSION = 1.40 This value can be adapted regarding which AMI use the client.

9.3 Run metricbeat with extra parameter

As we have mounted host system to the mounting point /hostfs we need to configure filebeat

to be able to fetch informations about process from this mounting point. For this reason we need to add an argument when we start metricbeat:

metricbeat -c john_mb.yml --path.home /etc/packetai/metricbeat -e -system.hostfs=/hostfs

9.4 Logical component inside ECS

To build logical components across instances for ecs, we use docker labels. For now we choose the following key: com.amazonaws.ecs.task-definition-family

9.5 Syslogs

Be default we set the following path to fetch host syslogs /hostfs/var/log/syslog*

Depending of the AMI linux running the agent, these files can not exist. The client needs to configure on minima integration page which files should be monitored if needed.
