Design

1. High level description:

The agent is an extensible client-server software based on the microservices architecture.

The agent (john) collects data from the user's IT components and sends it to the microservices backend (Emma).

The agent is made of two parts, a worker (John) and microservices (Emma)

Data travels from the agent through microservices in the following order: (for details about other MSs refer to Microservices)

John is a sensor that sends a list of data that has to be processed by microservices.

John works in three steps:

  • first he discovers the components
  • then it receives actions from the techno MS (specifying the list of components to collect data from) then
  • sends data to kafka topics (Will be updated to send data to Ingest)

The topology contains components and chains of executions. See section 5

Data plugins include filebeat, metricbeat, APM … etc

The set of data related to a chain of execution is called chain data. See section 5

The set of anomalies related to a chain of execution is called a case (or situation), and usually have the same root cause (hence, grouping anomalies based on root cause constitutes a situation). See section 5

2. High level architecture

The agent is made of five main parts:

  • process prober: ps tool
  • network scanner: nmap https://nmap.org/ . The nmap used is a fork with some functionalities (arp scan option) added by Valentin Manes. Warning this code is not uptodate. We should see if we can use the real github repository.
  • log collector: filebeat
  • metric collector: metricbeat
  • and a traces collector: open-distro apm agent
  • The output of Emma (Microservices) is the master graph: a graph containing all components of the IT infra with the links between them
  • The Master graph is written to kafka in topic: infrastructureID_mastergraph
  • Once John is installed, it starts securely sending components list to Emma, Emma then sends the topology (master graph) to Becky to clean then display on Minima

4. Internal Workflow

  • The user installs John by running the installation command (installation sh file is on S3) which installs a .deb package (containing all requirements: filebeat, metricbeat, apm)
  • The user checks the list of components to "monitor"
  • Becky sends this list to Emma (techno MS)
  • Emma sends the configuration commands to the coordinator
  • The coordinator (inside john) setup data plugins (filebeat, metricbeat and APM) with their configuration commands
  • Data plugins start sending data to their specific Kafka topics, each plugin outputs two types of data per component: logs and metrics (NOTE: APM is a type of metrics and only concern application components)
  • Example: logs of nodejs are output on a kafka topic called: infrastructureID_nodejsID_logs

and metrics of processX are output on a kafka topic called: infrastructureID_processXID_metrics
