Leadup

Sequence of events that led to the incident

  • On Saturday 05.11.22 at 20:10 (T0), we received a critical alert on Slack channel #k8s-monitoring-critical metron, about a wrong number of DGraph replicas
    • We received 6 similar alerts within the next hour at 20:17, 20:22, 20:57 (2 alerts) and 21:02 (2 alerts)
  • In parallel we observe an unusual behaviour on template consuming behaviour, starting 05.11.22 at 20:10. As can be seen, the throughout of consumed messages starting fluctuating until Monday 07.11.22 at 09:50 were it skyrocketed before resuming to normal at 15:30.
    • At 09:50 traffic skyrockets and resumes back to normal
  • Finally, a node restarted at 05.11.22 at 20:10. This node hosts a DGraph replica and the vector ingestor.

5-whys root cause identification

Run a 5-whys analysis to understand the true causes of the incident.

  • Why did Metron’s vector agent on all clusters (fr03, etc.) started withholding data sent to PAI vector ingester API starting on T0 (T0=saturday 05.11.21 at 20:10)? The sequence of events is as follows, with a crash loop in steps 3-9:
    1. cluster node crashes.
    1. ingester gets killed (as well as one DGraph replica).
    1. ingester API (HTTP sink) goes offline.
    1. Metron’s vector agent detects that HTTP sink is down and holds back/bufferizes data.
    1. cluster node reboots (first time only) / ingester API restarts
    1. ingester API is back online
    1. Metron’s vector agent detects that HTTP sink is up and releases all held back data.
    1. ingester receives a “tsunami” of data and get OOM-killed by k8s.
    1. back to step 3
  • Why did vector ingestor API started “choking” at T0? Because of a cluster node restart
  • Why did we not receive alerts on ingestor issues at T0? Because we have not set up alerts on the ingester
  • Why did node restart? We do not have the answer yet - need to drill down
