    Comments from call:

    • Can we silence alerts using rules like 1% memory usage becomes 2/3/20% not important as the absolute value is not important and can't cause a breakdown. There could be other scenarios for lower absolute values or see avg/mean for each component and see if it is significant (dont know if this is scalable)
    • Severity in alerts is always close to 90-100% so not really useful to judge the criticity (gchat alert)
    • Affluence does not wish to be alerted (at least we should bring down severity) if :
      • a metric changes slightly value (similar to the observation above regarding 1% change)
      • a metric incident is of short duration and if metric resumes to previous state (eg: memory is flat at 100Mb, undergoes a short spike, then resume to 100Mb)
    • Prefers to have an alert after 30s/1/2 min after an incident but reduce number of alerts
      • If we know critical incidents - app not available - can merit instant alert
      • In case of performance degradation can be 1/2 min late
    • Regarding gross byte value in bytes - MELK - not best. Would prefer see "400Mb" than "400 000 000 bytes" in the graph
    • Can we zoom in automatically for ease of use ?
    • Can we better format logs in daily reports. Can we parse logs to display logs better. Sometimes too long
    • On daily report can the engineer click to go to the logs on ELK to see other logs as well.
